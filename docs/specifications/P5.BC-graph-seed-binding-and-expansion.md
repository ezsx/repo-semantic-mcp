# P5.B/P5.C Graph Seed Binding and Bounded Expansion

## 1) Purpose

This slice makes the P5.A SQLite graph artifact useful for agent-facing
retrieval.

The graph must improve context recall for connected repository questions without
turning `repo_context_search` into a graph browser, hidden planner, or answer
generator. Dense and sparse retrieval remain the primary recall path. Graph
expansion is an optional, deterministic branch that starts from strong
dense/sparse seeds and returns grounded chunks with evidence paths.

The intended route becomes:

```text
repo_context_search(query, subqueries, graph_mode)
  -> current dense/sparse retrieval per query
  -> pre-final-cap retrieval branch assembly
  -> bind strong seed candidates to graph nodes
  -> optional bounded 1-hop graph expansion
  -> graph candidate ranking
  -> RRF fusion of retrieval seeds + graph branch
  -> one final shaping pass for results/file_groups/diagnostics/evidence paths
```

This spec covers P5.B and P5.C together because seed binding, graph expansion,
evidence paths, and graph diagnostics are tightly coupled. It does not add richer
extractors such as imports, framework routes, tests, call graphs, or SQL lineage.

## 2) Current State

P5.A already provides:

- `GraphService`;
- SQLite graph artifact under `artifacts/graphs`;
- `graph_status()`;
- `build_graph()` / `rebuild_graph()`;
- graph summary inside `index_status.v2`;
- graph freshness and source-contract diagnostics;
- graph tables:
  - `graph_metadata`;
  - `graph_files`;
  - `graph_nodes`;
  - `graph_node_terms`;
  - `graph_node_chunks`;
  - `graph_edges`.

The current `repo_context_search` behavior is intentionally graph-free:

- `graph_mode_requested` accepts `off | auto | expand`;
- `graph_mode_effective` is always `off`;
- diagnostics expose `graph_available=false` and `graph_used=false`;
- result branches are dense/sparse/legacy lexical only;
- no evidence paths are returned.

Compatibility note: `repo_context_search` currently defaults `graph_mode` to
`"auto"` while graph expansion is unavailable. Turning that default into active
graph expansion would change existing caller behavior and the MCP signature.
P5.B/P5.C must keep the public default/signature stable and gate active auto
expansion behind an explicit compatibility flag. The preferred implementation
for this slice is:

```text
public default graph_mode = "auto" remains unchanged
SEMANTIC_MCP_REPO_CONTEXT_GRAPH_AUTO_ENABLED=false by default
graph_mode="auto" behaves as graph-free compatibility mode while that flag is false
graph_mode="auto" enables deterministic auto triggers only when the flag is true
explicit graph_mode="expand" requests graph expansion
```

Future releases may consider default auto only after acceptance data shows that
it does not add noisy context for normal agent workflows.

## 3) Non-goals

Do not implement these in this slice:

- LLM planner, query rewriter, or hidden agent loop;
- final answer generation;
- raw graph dump in MCP responses;
- GraphRAG summaries;
- OpenIE triple extraction;
- Neo4j or graph database dependency;
- PPR/typed PPR;
- multi-hop expansion beyond bounded 1-hop;
- full import graph, test target inference, route extraction, call graph, SQL
  lineage, or migration graph;
- reranker or ColBERT;
- automatic `build_graph`/`rebuild_graph` from search/status;
- graph expansion in legacy list-shaped search tools;
- graph branch in `search_v2`.

## 4) Compatibility Contract

Existing tools stay compatible:

```text
semantic_search*
hybrid_search*
search_v2
find_similar_chunk
read_chunk
index_status
```

Only `repo_context_search` receives graph-aware behavior.

All public changes are additive:

- `OriginBranch` adds `"graph"`;
- `RecommendedAction.code` adds:
  - `build_graph`;
  - `rebuild_graph`;
  - `retry_with_graph_expand`;
- `RepoContextResult` adds `evidence_paths`;
- `RepoContextDiagnostics` adds graph diagnostics fields;
- `RepoContextSearchResponse.graph_mode_effective` can become:
  - `off`;
  - `auto`;
  - `expand`.

Internal fusion may use a branch named `retrieval`, but public branch metadata
must not expose `"retrieval"` unless the public `OriginBranch` contract is
explicitly changed. P5.B/P5.C public `origin_branches`, `branch_ranks`, and
`branch_scores` must preserve existing branches (`dense`, `sparse`,
`legacy_lexical`) and add only `graph`.

Legacy list-shaped tools must not return graph results, warnings, sentinel rows,
or new envelope-level diagnostics.

### 5.3 Recommended Actions


Action rules:

- graph missing + user requested `graph_mode=expand`:

## 6) Request Semantics

`repo_context_search` keeps the current request shape. `graph_mode` semantics
become active:

```text
off:
  never call graph branch;
  graph_mode_effective = "off".

auto:
  call graph branch only when deterministic triggers say it is useful and graph
  status is ready; active only when explicitly requested in P5.B/P5.C;
  graph_mode_effective = "auto" if used, else "off".

expand:
  call graph branch when graph status is ready;
  if graph is missing/stale/partial/building/incompatible/error, skip graph
  branch and return the state-specific warning/action;
  graph_mode_effective = "expand" if used, else "off".
```

Graph expansion must never call lifecycle operations. Search/status may read
graph status and graph rows, but may not build, rebuild, or update graph state.

## 7) Graph Availability and Freshness Rules

Graph branch can run only when:

```text
graph_status.available = true
graph_status.expansion_allowed = true
graph_status.state = "ready"
```

Behavior by state:

```text
missing:
  dense+sparse search continues;
  graph branch skipped;
  build_graph action when graph was requested.

stale:
  dense+sparse search continues;
  graph branch skipped for P5.B/P5.C;
  rebuild_graph action when graph was requested.

partial:
  graph branch skipped in this slice;
  return `graph_partial` warning when graph was requested;
  recommend `rebuild_graph`.

building:
  graph branch skipped;
  return `graph_building` warning when graph was requested;
  do not recommend lifecycle action from search because a lifecycle operation is
  already in progress;
  recommend retrying later.

incompatible/error:
  graph branch skipped;
  rebuild_graph action when graph was requested.
```

P5.B/P5.C should be conservative: use graph only when the whole graph is ready.
Path-level stale-edge suppression remains represented in the design and
diagnostics, but actual use of partial/stale graph edges is deferred.

## 8) Graph Auto Trigger Policy

`graph_mode=auto` may enable graph expansion only from deterministic signals.
No internal LLM router is allowed.

### 8.1 Positive Triggers

Enable graph auto when at least one signal is present:

```text
relationship terms:
  related, where used, usage, uses, used by, tests for, docs for, config for,
  deploy for, policy for, handler for, owner, flow, path, route, contract

cross-scope intent:
  query/subqueries mention docs+code, config+runtime, deploy+runtime,
  policy+paths, tests+module, endpoint+handler

infrastructure anchors:
  env var, route literal, config key, CLI flag, file path fragment,
  compose/deploy identifier, policy path

seed distribution:
  strong seeds from more than one file or more than one scope;
  exact infra anchors matched in both code/docs/config-like chunks.
```

Seed distribution is a supporting signal only. It must not enable auto expansion
by itself. `graph_mode=auto` requires at least one relationship, cross-scope, or
infrastructure-anchor signal; seed distribution can then increase confidence.

### 8.2 Suppression Rules

Suppress auto expansion when any rule is true:

```text
graph_mode = off
route_used = exact_handoff
top_k <= 3 and no relationship/infra signal
only one high-confidence exact symbol/path/literal seed and no relationship intent
graph status is not ready
no seed binds to graph nodes
filters are so narrow that expansion would leave the requested include_paths/path_prefix
```

Exact anchor nuance:

- plain symbol/literal/path lookup should not trigger graph expansion by default;
- infrastructure anchors can trigger graph expansion because related config,
  runtime, docs, and deploy context is often the point of the query.

## 9) Seed Selection

Graph expansion starts from a pre-final-cap retrieval seed pool, not from the
entire graph and not from the already capped final `top_k` response.

Defaults:

```text
max_graph_seed_chunks = 20
seed_pool_source = top 50 filtered merged dense/sparse candidates before final top_k
max_graph_candidates = 200
max_hops = 1
max_evidence_paths_per_result = 3
```

Introduce an explicit internal `GraphSeedPool`:

```text
GraphSeedPool
  candidates: filtered RepoContextResult-like rows
  source_branch_ranks: dense/sparse/legacy lexical ranks
  source_query: original/subquery text
  source_query_role: original|subquery
  source_weight: float
  pre_cap_rank: int
```

The seed pool is built after dense/sparse retrieval and filter application, but
before final `top_k`, final `max_results_per_file`, file groups, uncovered
terms, and verification shaping. Final response shaping happens once after
retrieval+graph fusion.

Strong seed rules:

- use only chunks that survived current retrieval filters;
- prefer high-ranked results;
- prefer seeds with exact anchor matches or matched terms;
- include at most `max_results_per_file=1` seed per file unless query has strong
  cross-file intent;
- exclude generated/vendor chunks.

Do not bind graph seeds from unfiltered Qdrant candidates that would not be
visible to the caller. This keeps graph expansion aligned with the agent's
requested scope.

## 10) Seed Binding

Implement a graph branch provider under `services/repo_semantic/graph/`.

Suggested modules:

```text
services/repo_semantic/graph/binding.py
services/repo_semantic/graph/expansion.py
services/repo_semantic/graph/scoring.py
services/repo_semantic/graph/provider.py
```

Binding order:

```text
1. chunk_id -> graph_nodes(node_type='chunk', chunk_id=?)
2. relative_path -> graph_nodes(node_type='file', key=?)
3. symbol_path -> graph_nodes(node_type='symbol', relative_path=?, key=?)
4. heading_path -> graph_nodes(node_type='doc_section', relative_path=?, key=?)
5. matched_terms/exact anchors -> graph_node_terms(normalized_term=?, term_type in allowlist)
```

Term binding should be selective. Do not bind every low-value term from the
query. Initial allowlist:

```text
env_var
route
path
cli_flag
sql_identifier
quoted_literal
exact       # only when token length >= 4 and not a stopword
```

For `graph_node_terms`, prefer terms already present in:

- `SearchResult.matched_terms`;
- exact-anchor analysis;
- sparse analyzer terms that look like infrastructure anchors.

If a seed cannot bind to a graph node, it remains a normal dense/sparse result.
Do not fabricate graph explanations.

## 11) Expansion V1

Expansion is bounded shared-node expansion, not arbitrary graph walking.

For P5.B/P5.C, "1-hop" means:

```text
seed node
  -> one allowlisted edge to a pivot node
  -> chunk projection from that pivot node through graph_node_chunks or direct
     node.chunk_id
```

For shared infrastructure nodes such as `env_var`, candidate support may include
one incident evidence edge from another chunk to the same pivot node:

```text
seed chunk --code_reads_env--> env_var:DATABASE_URL
candidate chunk --config_defines_env--> env_var:DATABASE_URL
```

This is still v1 shared-node expansion. It is not general 2-hop traversal:

- the pivot node must be reached by exactly one edge from a bound seed;
- candidate chunks must be directly attached to the pivot through
  `graph_node_chunks`, `graph_nodes.chunk_id`, or one incident allowlisted edge;
- do not continue from candidate chunks to another pivot;
- apply all seed, neighbor, degree, and candidate caps.

Allowed initial edge types:

```text
file_contains_chunk
chunk_defines_symbol
file_contains_doc_section
chunk_mentions_path_or_symbol
config_defines_env
code_reads_env
```

Optional in this slice if already available from P5.A data:

```text
doc_references_symbol
doc_references_config
policy_applies_to_path
```

Do not add new extractors just to make these optional edges appear. If the edge
type is not present, diagnostics should simply show that it was unused.

Expansion direction:

- use outgoing and incoming edges for allowlisted edge types;
- bind candidate nodes back to chunks through:
  - `graph_nodes.chunk_id`;
  - `graph_node_chunks`;
  - file node -> containing chunks via `file_contains_chunk`;
- do not return standalone nodes without a chunk-backed result.

High-degree protection:

```text
max_neighbors_per_seed_node = 30
max_degree_without_penalty = 20
high_degree_penalty starts after 20
skip node if degree > 200 unless node_type='env_var' and exact anchor matched
```

Filtering:

- graph candidates must pass the same client-side filters as normal results;
- if Qdrant/file filters cannot be applied before graph expansion, apply them
  after candidate-to-chunk projection and report `graph_filter_post_applied`;
- graph expansion must not escape `include_paths` unless diagnostics mark it
  explicitly and P5.B/P5.C should default to not escaping.

## 12) Graph Candidate Scoring

Graph scoring is deterministic and local to the graph branch.

Inputs:

```text
seed_rank_prior
seed_branch_support
exact_anchor_bonus
edge_type_weight
term_binding_bonus
multi_seed_support_bonus
same_file_penalty_or_bonus depending edge type
generated_penalty
high_degree_penalty
```

Initial policy:

```text
seed_rank_prior = 1 / (1 + seed_pre_cap_rank)
exact_anchor_bonus = +0.25
term_binding_bonus = +0.10
multi_seed_support_bonus = +0.15 per extra seed, capped at +0.45
generated_penalty = -0.25
high_degree_penalty = min(0.50, degree / 400)

edge_type_weight:
  code_reads_env: 1.00
  config_defines_env: 1.00
  chunk_defines_symbol: 0.90
  file_contains_doc_section: 0.80
  chunk_mentions_path_or_symbol: 0.75
  file_contains_chunk: 0.55
```

For shared-node evidence with both a seed edge and a candidate/support edge, use
a path-support weight:

```text
path_edge_weight = sqrt(seed_edge_weight * support_edge_weight)
```

For direct one-edge projection, `path_edge_weight = edge_type_weight`.

If multiple paths support the same candidate, keep the best path score for
branch ranking and store up to 3 top evidence paths ordered by path score.

Raw graph scores are used only to rank the graph branch. They are not blended
directly with dense/sparse scores.

After graph candidates are ranked:

```text
branches:
  retrieval    # current merged dense/sparse/multi-query results as one branch
  graph        # graph-ranked candidates

fusion:
  weighted RRF

default weights:
  retrieval: 1.0
  graph: 0.7 when graph_mode=auto
  graph: 1.0 when graph_mode=expand
```

This preserves current dense+sparse order while allowing graph candidates to
enter when strongly supported.

Deterministic ordering:

```text
graph branch rank order:
  - graph_score desc
  - best seed pre_cap_rank asc
  - path length asc
  - relative_path asc
  - start_line asc
  - chunk_id asc

final fused rank order:
  - fused_rrf_score desc
  - best public branch rank asc
  - graph result after retrieval result when otherwise tied
  - relative_path asc
  - start_line asc
  - chunk_id asc

evidence path order:
  - path_score desc
  - seed pre_cap_rank asc
  - path length asc
  - lexical tuple of edge types/node keys asc
```

All SQLite queries that apply caps must have explicit `ORDER BY` clauses that
support this deterministic ordering.

## 13) Result Projection

Graph candidates must be projected back into `RepoContextResult`.

For candidates already present in retrieval results:

- add `"graph"` to `origin_branches`;
- add graph `branch_ranks["graph"]`;
- add graph `branch_scores["graph"]`;
- attach evidence paths;
- do not duplicate the result.

For graph-only candidates:

- build a `RepoContextResult` from the indexed chunk payload;
- `origin_branches=["graph"]`;
- `origin_queries` should include the query that produced the seed;
- `match_type` may remain `"hybrid"` or `"semantic"` only if required by the
  existing model, but the branch metadata must make graph origin explicit;
- `matched_terms` should come from graph-bound terms and snippet matching;
- `verification.required` should be true when exact anchors or stale index
  warnings exist.

Apply dedupe and diversity after final fusion:

```text
dedupe by chunk_id
apply max_results_per_file
preserve global fused rank
rebuild file_groups
recompute diagnostics distributions
```

## 14) Evidence Path Shape

Evidence path examples:

```text
seed: services/api/settings.py:1-4
  -> code_reads_env(DATABASE_URL)
  -> env_var:DATABASE_URL
  -> config_defines_env
  -> deploy/compose/docker-compose.yml:12-16
```

For 1-hop v1, many paths will be shorter:

```text
seed chunk
  -> code_reads_env
  -> env_var node
  -> mentioned chunk
```

Rules:

- every evidence path must start from a real seed chunk;
- every returned graph result must map to a real indexed chunk;
- include edge types, node types, and path/line anchors where available;
- mark `stale=true` only if later slices permit partial/stale graph use; in this
  slice stale graph is skipped, so evidence paths should normally be `stale=false`;
- cap evidence paths and path steps.

## 15) Integration Architecture

Do not paste graph expansion into `SearchService`.

Recommended dependency flow:

```text
SearchService.repo_context_search(...)
  -> context_search.repo_context_search_response(...)
       receives optional read-only graph_context_provider callable
       runs current dense/sparse executions
       asks graph provider for graph branch only after seed results exist
       calls assembler to fuse/project results in one final shaping pass
```

Suggested callable contract:

```python
class GraphContextProvider(Protocol):
    def expand(
        self,
        *,
        graph_mode: GraphMode,
        route_used: str,
        query_items: list[ContextQueryItem],
        seed_pool: GraphSeedPool,
        exact_anchor_analysis: ExactAnchorAnalysis,
        filters: SearchFilters,
        top_k: int,
        max_results_per_file: int | None,
        snippet_mode: SnippetMode,
        include_explanations: bool,
    ) -> GraphExpansionResult:
        ...
```

`GraphExpansionResult` should contain:

```text
mode_effective
results
branch_ranks
branch_scores
evidence_paths_by_chunk
diagnostics
warnings
recommended_actions
```

The provider may depend on:

- a narrow read-only graph interface;
- graph SQLite read APIs;
- chunk read/project helpers;
- filter matching helpers;
- snippet/result projection helpers.

It must not depend on MCP wrappers or mutate graph lifecycle.

Do not pass full `GraphService` into retrieval code. `GraphService` owns explicit
lifecycle methods. Define a read-only protocol, for example:

```python
class GraphReadProvider(Protocol):
    def graph_status(self, *, verify_source_revision: bool = True) -> GraphStatusResult: ...
    def find_nodes_for_chunks(...): ...
    def find_file_nodes(...): ...
    def find_symbol_nodes(...): ...
    def find_term_nodes(...): ...
    def neighbors(...): ...
    def chunks_for_nodes(...): ...
```

The implementation should use read-only SQLite connections where practical, and
must not call `build_graph`, `rebuild_graph`, `update_graph`, or any method that
creates/migrates an artifact during search.

`GraphContextProvider.expand` must use
`graph_status(verify_source_revision=True)` before expansion. It may use a
cheaper non-verified summary only for diagnostics when graph expansion is not
being attempted.

## 16) Graph Store Read APIs

Add read-only methods to graph storage/service:

```text
find_nodes_for_chunks(chunk_ids)
find_file_nodes(relative_paths)
find_symbol_nodes(symbol bindings)
find_doc_section_nodes(heading bindings)
find_nodes_by_type_and_key(node_type, bindings)
find_term_nodes(terms)
neighbors(node_ids, edge_type_allowlist, max_neighbors_per_node)
chunks_for_nodes(node_ids)
node_degree(node_id)
```

These methods must:

- use parameterized SQLite queries;
- be bounded by explicit limits;
- return typed internal dataclasses, not raw sqlite rows;
- never write to the DB;
- tolerate missing nodes by returning empty lists.
- use deterministic `ORDER BY` before applying caps.

Ordering requirements:

```text
find_nodes_for_chunks:
  ORDER BY input seed order, node_type priority, relative_path, start_line, node_id

find_term_nodes:
  ORDER BY exact term-type priority, normalized_term, node_type priority, key, node_id

neighbors:
  ORDER BY edge_type priority, confidence desc, neighbor node_type priority,
           neighbor relative_path, neighbor start_line, neighbor node_id

chunks_for_nodes:
  ORDER BY relation priority, weight desc, relative_path, start_line, chunk_id
```

## 17) Filter Semantics

Graph expansion must respect the same request filters:

- `scope`;
- `path_prefix`;
- `include_paths`;
- `exclude_paths`;
- `file_extensions`;
- `languages`;
- `chunk_types`;
- `domain_tags`.

The graph provider should reuse the same `SearchFilters` construction and
`matches_filters` predicate used by dense/sparse retrieval.

If a graph candidate is filtered out, diagnostics should count it:

```text
graph_candidates_before_filter
graph_candidates_after_filter
graph_filter_post_families
```

P5.B/P5.C should not return candidates outside filters as a clever expansion.
Agents can explicitly retry with broader filters.

## 18) Warnings

New warning codes:

```text
graph_branch_unavailable
graph_missing
graph_partial
graph_building
graph_stale
graph_incompatible
graph_error
graph_auto_suppressed
graph_no_bound_seeds
graph_no_candidates
graph_filter_post_applied
graph_candidate_cap_reached
graph_high_degree_nodes_skipped
```

Severity:

- `info` for auto suppression/no candidates;
- `warning` for requested graph expansion that cannot run, except
  `graph_building`, which is `info` because lifecycle is already in progress;
- `warning` for candidate cap/high-degree skips when graph was used.

## 19) Acceptance Tests

### 19.1 Contract Tests

- `OriginBranch` includes `"graph"`.
- `RecommendedAction.code` includes graph action codes.
- `RepoContextResult` includes `evidence_paths`.
- `RepoContextDiagnostics` includes `graph_diagnostics`.
- `RepoContextSearchResponse.graph_mode_effective` can be `off|auto|expand`.
- new evidence/graph diagnostics models and literal aliases are exported through
  `contracts` and `models.py`.
- public branch metadata never exposes the internal `retrieval` branch.

### 19.2 Mode Behavior

- `graph_mode=off` does not call graph provider and preserves current results.
- omitted/default graph_mode preserves current graph-free behavior.
- `graph_mode=expand` with ready graph calls provider and can add graph results.
- `graph_mode=expand` with missing graph returns warning + `build_graph` action.
- `graph_mode=expand` with stale/incompatible/error graph returns warning +
  `rebuild_graph` action.
- `graph_mode=expand` with partial graph returns `graph_partial`,
  `graph_mode_effective="off"`, dense+sparse results, and `rebuild_graph`
  action template.
- `graph_mode=expand` with building graph returns `graph_building`,
  `graph_mode_effective="off"`, dense+sparse results, no lifecycle action, and
  the building-specific `retry_with_graph_expand` template.
- `graph_mode=auto` suppresses graph for plain exact symbol/path lookup.
- `graph_mode=auto` enables graph for infra anchor + relationship intent.

### 19.3 Seed Binding

- chunk id binds to chunk node.
- relative path binds to file node.
- symbol path binds to symbol node.
- heading path binds to doc section node.
- env var exact anchor binds to env var node.
- unbound seeds do not create fake evidence.

### 19.4 Expansion

- env var query can pull related code/config/docs chunks through graph edges.
- graph candidates respect include/exclude/path/scope filters.
- graph filter counters report before/after values and post-filter families.
- high-degree nodes are skipped or penalized and diagnosed.
- candidate caps are enforced.
- graph-only result has `origin_branches=["graph"]`.
- existing retrieval result gains `graph` branch without duplication.

### 19.5 Evidence

- graph result includes evidence path from seed chunk to candidate chunk.
- evidence path has real chunk/file/line anchors.
- evidence path count is capped.
- tied graph paths/results have deterministic order.

### 19.6 Regression

- legacy list tools remain unchanged.
- `search_v2` remains graph-free.
- missing/stale graph never breaks dense+sparse `repo_context_search`.
- graph branch does not run lifecycle operations.
- search receives only a read-only graph provider.
- full pytest remains green.

## 20) Implementation Order

Recommended order:

```text
1. Add public contracts:
   OriginBranch graph, EvidencePath, graph diagnostics, graph actions.

2. Add graph read APIs:
   bounded SQLite node/edge/chunk lookup methods.

3. Add seed binding:
   chunk/path/symbol/heading/term binders with tests.

4. Add expansion/scoring:
   1-hop allowlisted expansion, scoring, caps, diagnostics.

5. Add graph provider:
   GraphContextProvider returning graph branch results and evidence.

6. Integrate into repo_context_search:
   graph_mode semantics, branch fusion, warnings/actions.

7. Add acceptance and regression tests.
```

Do not start with scoring constants. First make binding and evidence correct.
Ranking should be simple and inspectable in v1.

## 21) Success Criteria

The slice is complete when:

```text
1. Graph expansion is available only through repo_context_search.
2. graph_mode off|auto|expand behaves deterministically.
3. Missing/stale/incompatible/error graph never breaks dense+sparse retrieval.
4. Ready graph can add useful connected chunks for env/config/docs/code cases.
5. Every graph result is grounded by chunk/path/line evidence.
6. Graph branch is bounded by seed, neighbor, candidate, evidence, and result caps.
7. Existing legacy tools and search_v2 remain backward-compatible.
8. Tests cover contracts, modes, binding, expansion, evidence, filters, and stale graph behavior.
```

The most important product bar is not “graph returns more stuff.” It is:

```text
graph returns the specific connected context an agent would otherwise need
several exact searches and file reads to discover.
```
