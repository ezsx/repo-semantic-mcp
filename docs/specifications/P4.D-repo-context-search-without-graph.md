# P4.D `repo_context_search` Without Graph

## 1) Purpose

`repo_context_search` is the new primary agent-facing context retrieval tool.

This slice introduces the future context envelope before graph complexity. It
must sit on top of the already implemented dense+sparse+RRF route and expose the
kind of grounded context a frontier coding agent needs before deciding which
files to read next.

The tool is not a hidden coding agent, not a planner, not a summarizer, and not a
final-answer system. It returns repository evidence, diagnostics, freshness
signals, and operational next actions.

## 2) Scope

In scope:

- public MCP tool `repo_context_search`;
- Pydantic response models for `repo_context_search.v1`;
- multi-query input with original-query injection;
- deterministic merge across query result lists;
- dense/sparse branch provenance derived from current search rows;
- file grouping;
- matched and uncovered terms;
- exact-anchor verification actions;
- warnings and diagnostics copied/merged from `search_v2`;
- recommended next actions for file reads, local `rg`, retries, and rebuilds.

Out of scope:

- graph artifact;
- graph expansion;
- evidence paths from graph edges;
- reranker;
- ColBERT or multivectors;
- hidden LLM query rewriting;
- PRF/HyDE;
- shell-backed exact search inside the MCP;
- lifecycle rebuild/reindex from search.

Graph, rerank, and ColBERT-related fields must either be absent or explicitly
reported as unavailable/off. Do not add model-serving dependencies in this
slice.

## 3) Compatibility

Existing tools remain stable:

```text
semantic_search
semantic_search_code
semantic_search_docs
hybrid_search
hybrid_search_code
hybrid_search_docs
search_v2
find_similar_chunk
read_chunk
index_status
```

`repo_context_search` is additive. Do not retrofit its envelope into legacy
list-shaped tools. Do not rename `search_v2`.

The implementation may reuse internal `search_v2` execution code, but the
public contract is separate:

```text
search_v2:
  search rows + diagnostics

repo_context_search:
  context envelope + query merge + file groups + next actions
```

## 4) Public Tool Contract

MCP tool:

```python
repo_context_search(
    query: str,
    subqueries: list[str] | None = None,
    route: Literal["auto", "semantic", "hybrid", "exact_handoff"] = "auto",
    graph_mode: Literal["off", "auto", "expand"] = "auto",
    scope: Literal["all", "code", "docs"] = "all",
    path_prefix: str | None = None,
    include_paths: list[str] | None = None,
    exclude_paths: list[str] | None = None,
    file_extensions: list[str] | None = None,
    languages: list[str] | None = None,
    chunk_types: list[str] | None = None,
    domain_tags: list[str] | None = None,
    top_k: int = 20,
    max_results_per_file: int | None = 3,
    snippet_mode: Literal["chunk_start", "query_centered"] = "query_centered",
    include_diagnostics: bool = True,
    include_explanations: bool = True,
) -> RepoContextSearchResponse
```

Do not expose `rerank_mode` in P4.D. It can be added later after rerank has an
explicit availability/status contract.

`graph_mode` is accepted now to stabilize the future request shape:

```text
off:
  graph_mode_effective = "off"

auto:
  graph_mode_effective = "off"

expand:
  graph_mode_effective = "off"
  warning: graph_branch_unavailable
  no build_graph action in P4.D
```

Until P5.A, `graph_mode=expand` must not attempt to build, read, or infer graph
state. After P5.A introduces graph lifecycle tools, a future additive revision
may add a `build_graph` recommendation.

## 5) Request Limits

Use the existing P3/P4 caps where possible:

```text
query length:
  same as search_v2

subqueries:
  max 8
  each uses same query length cap
  empty strings ignored
  duplicate strings ignored after trimming
  duplicate of original query ignored after trimming
  dedupe is case-sensitive because code identifiers can be case-sensitive
  if more than 8 unique subqueries remain, keep the first 8 and warn

top_k:
  public max 100
  default 20

filters:
  same normalization and safety validation as search_v2

snippet:
  same snippet and line-match bounds as search_v2
```

The original query is always included and always first:

```text
queries_used = [query] + normalized_subqueries
```

Subqueries are agent-provided. The MCP must not create subqueries through an
internal LLM planner.

Dropped subqueries should produce one bounded warning:

```text
multi_query_subquery_dropped
```

The warning detail may include counts, not the full dropped query text.

## 6) Route Behavior

### 6.1 `route="auto"`

P4.D default:

```text
auto -> hybrid
```

Reason: dense+sparse+RRF is now the baseline route. Exact-anchor-heavy queries
already get sparse-biased RRF inside the hybrid route.

Future versions may add deterministic route tweaks, but P4.D should avoid a
large router.

### 6.2 `route="semantic"`

Use dense semantic retrieval only. This route is useful for conceptual queries
where lexical anchors are weak or misleading.

### 6.3 `route="hybrid"`

Use dense+sparse+RRF through the current hybrid route.

If sparse vectors are unavailable, `repo_context_search` must not silently
pretend full hybrid was used. It should carry search diagnostics and recommend
explicit rebuild when appropriate.

During the current compatibility window, if the underlying `search_v2` still
uses legacy BM25 fallback, `repo_context_search` may reuse those rows, but must
surface:

```text
legacy_lexical_fallback_used
sparse_branch_unavailable
sparse_unavailable_codes
```

### 6.4 `route="exact_handoff"`

Do not search the working tree. Do not shell out to `rg`.

Return an envelope with:

```text
route_used = "exact_handoff"
results = []
recommended_next_actions includes run_local_rg for detected anchors
```

If no exact anchors are detected, return a warning:

```text
exact_anchor_not_detected
```

and recommend retrying with `route="hybrid"` or `route="semantic"`.

## 7) Multi-Query Retrieval And Merge

For each query in `queries_used`, run the selected route independently with the
same filters.

Internal per-query retrieval limit:

```text
internal_top_k = min(100, max(top_k * 4, 50))
```

Do not apply `max_results_per_file` inside each per-query call. Diversity must
be applied after query merge so one query cannot hide globally stronger context
from another.

Final merge:

```text
fusion_method = "multi_query_weighted_rrf"
rrf_k = 60

query weights:
  original query: 1.0
  subqueries: 0.85
```

Use ranks from each per-query result list. Do not blend raw dense/sparse/search
scores across queries.

Deduplicate by `chunk_id`. For a duplicate:

- keep best snippet/line range from the highest-ranked occurrence;
- union `origin_queries`;
- union `origin_branches`;
- keep max dense score and max lexical score in `branch_scores`;
- merge matched terms, capped;
- merge warnings at response level, not per result.

After fusion:

```text
sort by final_score desc
tie-break by best original-query rank asc, if present
then best rank across any query asc
then relative_path asc
then start_line asc
then chunk_id asc
apply max_results_per_file
truncate to top_k
assign final_rank starting at 1
```

## 8) Response Models

### 8.1 Query Usage

```python
class QueryUsage(BaseModel):
    query: str
    role: Literal["original", "subquery"]
    route_used: Literal["semantic", "hybrid", "exact_handoff"]
    weight: float
    result_count: int = 0
    warning_codes: list[str] = []
```

Exact anchors are detected per query and aggregated at response level:

```python
class ExactAnchorUsage(BaseModel):
    query: str
    query_role: Literal["original", "subquery"]
    anchor: ExactAnchorCandidate
```

### 8.2 Repo Context Result

`RepoContextResult` extends the current `SearchResult` shape additively:

```python
class RepoContextResult(SearchResult):
    final_rank: int
    final_score: float

    origin_branches: list[Literal["dense", "sparse", "legacy_lexical"]] = []
    origin_queries: list[str] = []

    branch_scores: dict[str, float] = {}
    branch_ranks: dict[str, int] = {}

    uncovered_terms: list[str] = []
    verification: VerificationHint
```

`origin_branches` must be derived from actual branch participation, not from raw
score values.

Do not infer branch provenance from `dense_score`, `lexical_score`, or
`final_score`: current hybrid rows can carry `0.0` for a branch that did not
participate, and valid vector scores can be zero.

P4.D should preserve branch membership from the internal retrieval execution:

```text
dense branch produced this chunk
  -> dense

sparse branch produced this chunk
  and diagnostics.retrieval_backend == "qdrant_dense_sparse_rrf"
  and diagnostics.sparse_available is true
    -> sparse

sparse/lexical branch produced this chunk
  and diagnostics.retrieval_backend == "legacy_dense_local_bm25"
    -> legacy_lexical
```

Implementation options:

- reuse or extend the internal hybrid execution path so P4.D can see
  `_weighted_rrf` branch membership;
- add private execution metadata before shaping `SearchResult` rows;
- for semantic route, mark returned rows as `dense`;
- for `exact_handoff`, return no branches.

Do not fabricate `branch_ranks`. If numeric ranks are not available, leave
`branch_ranks={}` while still setting correct `origin_branches`.

For semantic route, results usually have only `dense`.

### 8.3 Verification Hint

```python
class VerificationHint(BaseModel):
    required: bool = False
    reason: str | None = None
    recommended_action_codes: list[str] = []
```

Set `required=true` when:

- exact anchors were detected;
- index freshness is stale;
- sparse branch used legacy lexical fallback;
- lifecycle/status says search is degraded but not blocked.

P4.D should not claim indexed results are verified enough to edit. Exact anchors
still require local `rg` or direct file reads.

### 8.4 File Group

```python
class FileContextGroup(BaseModel):
    relative_path: str
    scope: Literal["code", "docs"]
    language: str | None = None
    best_rank: int
    best_score: float
    chunk_count: int
    chunk_ids: list[str] = []
    line_ranges: list[str] = []
    matched_terms: list[str] = []
    origin_queries: list[str] = []
    origin_branches: list[str] = []
    recommended_action_codes: list[str] = []
```

Groups are sorted by `best_rank`.

Bounds:

```text
max file_groups:
  min(20, top_k)

max chunk_ids per group:
  10

max line_ranges per group:
  5
```

`chunk_ids` and `line_ranges` are ordered by final result rank. Do not include
every chunk range for large files.

### 8.5 File Distribution Entry

```python
class FileDistributionEntry(BaseModel):
    relative_path: str
    scope: Literal["code", "docs"]
    result_count: int
    best_rank: int
    best_score: float
```

### 8.6 Recommended Action

```python
class RecommendedAction(BaseModel):
    code: Literal[
        "read_file_range",
        "run_local_rg",
        "rebuild_index",
        "retry_with_hybrid",
        "retry_with_semantic",
        "retry_with_path_filter",
        "retry_with_docs_scope",
        "retry_with_code_scope",
    ]
    severity: Literal["info", "warning"]
    title: str
    detail: str | None = None
    relative_path: str | None = None
    start_line: int | None = None
    end_line: int | None = None
    argv_hint: list[str] | None = None
    cwd_hint: Literal["repo_root"] | None = None
    authority: Literal["local_rg"] | None = None
    tool_hint: str | None = None
```

`run_local_rg` must use argument arrays, not shell strings.

`run_local_rg` actions must be self-contained even when
`include_diagnostics=false`:

```text
argv_hint: ["rg", "--fixed-strings", "--line-number", "--max-count", "20", "-e", "...", "."]
cwd_hint: "repo_root"
authority: "local_rg"
```

`read_file_range` should point to top file groups or top results:

```text
relative_path
start_line
end_line
```

Do not include more than 5 read actions by default.

## 9) Matched And Uncovered Terms

Use current `code_lexical_v2` analysis.

Matched terms:

- union `SearchResult.matched_terms` from final results;
- prefer exact surfaces when present;
- cap by existing explanation caps.

Uncovered terms:

- exact anchor surfaces not present in matched terms;
- high-signal sparse query terms not present in matched terms;
- cap to avoid noisy long lists.

Do not treat common prose words as important uncovered terms.

P4.D can use a simple deterministic stopword list for uncovered-term hygiene.
No ML/LLM step is required.

P4.D uncovered-term rules:

```text
global cap:
  10

candidate terms:
  exact anchor surfaces first
  then sparse query terms with length >= 3

exclude:
  terms already matched case-insensitively
  purely numeric terms
  stopwords

initial English stopwords:
  a, an, and, are, as, at, be, by, for, from, how, in, is, it,
  of, on, or, that, the, this, to, where, which, with

initial Russian stopwords:
  а, в, где, для, и, или, как, на, не, по, с, что, это
```

Golden examples:

```text
query: "where is DATABASE_URL used"
matched_terms: ["DATABASE_URL"]
uncovered_terms: []

query: "connect_flow docs tests"
matched_terms: ["connect_flow"]
uncovered_terms: ["docs", "tests"]

query: "UserRepository.findByEmail permission denied"
matched_terms: ["UserRepository.findByEmail"]
uncovered_terms: ["permission", "denied"]
```

## 10) Recommended Action Policy

Always prefer small, actionable next steps.

### 10.1 Read Actions

For top results/file groups:

```text
read_file_range
  relative_path
  start_line = snippet_start_line or start_line
  end_line = snippet_end_line or end_line
```

Cap at 5.

### 10.2 Exact Verification

If the response-level union of exact anchors is non-empty:

```text
run_local_rg
  argv_hint from aggregated exact_anchor_analysis.argv_hints
  severity warning for exact_anchor_heavy
```

Do not interpolate raw user query into shell strings.

For multi-query requests:

```text
detect anchors independently for each query in queries_used
dedupe response-level anchors by surface + canonical + anchor_type
preserve per-query provenance in exact_anchor_usages
build run_local_rg actions from the deduped response-level union
```

### 10.3 Sparse Rebuild

If diagnostics include:

```text
sparse_manifest_missing
sparse_analyzer_version_mismatch
sparse_encoder_kind_mismatch
sparse_contract_mismatch
sparse_vector_missing
legacy_dense_only_collection
sparse_stats_stale
```

recommend:

```text
rebuild_index
tool_hint = "build_index(force_rebuild=true)"
```

This remains a recommendation only. Do not call lifecycle tools.

### 10.4 Retry Actions

Recommend retries when useful:

```text
retry_with_path_filter:
  len(file_groups) >= min(10, top_k)
  and no path_prefix/include_paths filter is active

retry_with_docs_scope:
  scope="all"
  and docs result count == 0
  and query contains one of: docs, spec, specification, policy, guide, README

retry_with_code_scope:
  scope="all"
  and code result count == 0
  and query contains one of: implementation, runtime, handler, endpoint, test,
  function, class, service

retry_with_semantic:
  route_used="hybrid"
  and exact_anchor_analysis.anchors is empty
  and result count > 0
  and global matched_terms is empty

retry_with_hybrid:
  route=semantic and exact anchors were detected
```

Keep these bounded. Do not flood the response with speculative advice.

## 11) Warning Merge

Merge warnings from all per-query search responses.

Deduplicate by:

```text
code + severity + detail
```

Add P4.D-specific warnings:

```text
graph_branch_unavailable
exact_anchor_not_detected
multi_query_subquery_dropped
repo_context_sparse_degraded
```

Do not hide underlying `search_v2` warnings.

## 12) Freshness And Lifecycle

P4.D must preserve lifecycle safety:

- do not call `build_index`;
- do not call `rebuild_index`;
- do not call `reindex_paths`;
- do not call watcher controls;
- do not switch runtime/backend;
- do not build graph.

`repo_context_search` may call the same readiness checks as `search_v2`. If
search is unavailable, return the existing structured error behavior used by the
service layer.

If search is available but degraded, return warnings and next actions.

P4.D should call `index_status()` internally at most once per response to derive
freshness and degraded-state recommendations. This call must remain read-only
and must not trigger lifecycle operations. Per-query retrieval details still
come from `search_v2` diagnostics.

Add `SearchService.repo_context_search(...)`.

- preserve original query first;
- run one search per query;
- merge by multi-query RRF;
- build file groups and recommendations.

### Slice 3: MCP Tool

Add `repo_context_search` to `services/repo_semantic/mcp_server.py`.

The tool returns `.model_dump()`.

### Slice 4: Tests

Add tests for:

- envelope contract version and route fields;
- original query injection;
- duplicate subquery removal;
- multi-query result dedupe and origin queries;
- exact-anchor `run_local_rg` action;
- `exact_handoff` route returns no search rows and safe actions;
- file groups sorted by best rank;

- sparse unavailable codes become rebuild recommendation;
- `graph_mode=expand` returns graph-unavailable warning but does not lifecycle;
- legacy list-shaped tools unchanged.

## 14) Acceptance Criteria

P4.D is complete when:

1. `repo_context_search` exists as a public MCP tool.

2. It returns `contract_version="repo_context_search.v1"`.

3. `queries_used[0]` is always the original query.

4. Subqueries are accepted, bounded, deduplicated, and merged deterministically.

5. Dense/sparse branch provenance is visible per result.

6. Results are deduplicated by chunk id.

7. `file_groups` summarize top files with bounded line ranges.

8. Exact anchors produce safe `run_local_rg` actions.

9. Sparse unavailable/mismatch states produce rebuild recommendations, not
   implicit rebuilds.

10. Graph/rerank/ColBERT are not used.

11. Existing legacy tools and `search_v2` remain compatible.

12. Tests cover the response shape, merge behavior, next actions, and lifecycle
    boundaries.

## 15) Resolved Review Decisions

1. `route="exact_handoff"` returns zero rows always. If indexed context is
   desired, callers should use `route="hybrid"` and still consume `run_local_rg`
   actions.

2. `repo_context_search` calls `index_status()` internally at most once per
   response for freshness/degraded recommendations. It never calls lifecycle
   tools.

3. `FileContextGroup` includes bounded `chunk_ids` for traceability.

4. `origin_branches` must use actual branch participation from internal
   execution metadata. Numeric `branch_ranks` may still be deferred and empty if
   not naturally available.

5. `max_results_per_file` defaults to `3` for agent context diversity. `None`
   remains available as an opt-in for single-file-heavy result sets.
