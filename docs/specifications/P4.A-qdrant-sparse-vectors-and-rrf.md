# P4.A: Qdrant sparse vectors and RRF

Status: Draft for review

## 1) Purpose

This specification defines the first implementation slice after the final P6
architecture:

```text
replace local query-time BM25 cache + score blending
with Qdrant dense+sparse retrieval + weighted RRF
```

This is the foundation for later `repo_context_search`, graph expansion,
rerank, and ColBERT work.

The goal is not to build the full future architecture in one step. P4.A should
make hybrid retrieval structurally correct:

- dense retrieval stays a first-class branch;
- sparse lexical retrieval becomes a first-class Qdrant branch;
- dense and sparse candidate lists are fused by rank, not raw score blending;
- status reports whether sparse retrieval is available and compatible;
- old dense-only indexes degrade explicitly instead of pretending to be full
  hybrid indexes.

## 2) Source documents

Read these before implementation:

- `docs/architecture/P6-final-architecture.md`
- `docs/research/rag-transfer/P4-rag-stack-transfer-from-rag-app.md`
- `docs/specifications/P3-agent-grade-status-search-and-exact-fallback-specification.md`

Relevant P6 direction:

```text
agent query / agent-provided subqueries
  -> dense raw retrieval over Qdrant
  -> sparse code-normalized retrieval over Qdrant
  -> weighted RRF seed fusion
  -> optional deterministic typed graph expansion from strong seeds
```

P4.A implements only the first three lines.

## 3) Current state

Current `hybrid_search` in `services/repo_semantic/search_service.py`:

- embeds the query;
- retrieves dense candidates from Qdrant;
- scrolls all chunks from Qdrant into an in-process BM25 cache;
- builds a `BM25Okapi` instance over filtered chunks at query time;
- normalizes lexical scores by max BM25 score;
- blends scores as `dense_score * 0.7 + lexical_score * 0.3`;
- returns `SearchResult` rows with `dense_score` and `lexical_score`.

This has three architectural problems:

- lexical recall requires full collection scrolling and in-process scoring;
- dense cosine scores and BM25-style lexical scores are blended despite being
  different score spaces;
- Qdrant collection schema does not expose a sparse branch, so status cannot
  distinguish full hybrid retrieval from local fallback behavior.

## 4) Non-goals

Do not implement in P4.A:

- `repo_context_search`;
- graph storage or graph expansion;
- `indexed_exact_search`;
- ColBERT multivectors;
- cross-encoder rerank;
- tree-sitter extraction;
- full P4.B lexical normalization;
- LLM query planning or query rewriting;
- PRF/HyDE;
- shell-backed `rg` inside MCP.

P4.A may introduce a small baseline lexical analyzer because sparse vectors need
tokens, but the richer code-aware normalization belongs to P4.B.

## 5) Compatibility rules

The P3 compatibility contract remains active:

- legacy list-shaped tools keep returning list-like results;
- `search_v2` keeps returning an envelope;
- lifecycle operations do not run implicitly from status or search;
- old indexes must not be silently treated as full dense+sparse indexes;
- existing dense-only semantic search remains usable where possible;
- exact verification remains a host/local `rg` workflow for coding agents.

P4.A should bump `SEMANTIC_MCP_INDEX_SCHEMA_VERSION` because the Qdrant vector
schema changes from unnamed dense-only vectors to named dense+sparse vectors.

Old schema collections may be read for dense semantic search during the
compatibility window, but only through an explicit legacy lookup path:

- current-version named dense+sparse collections are the primary target;
- previous-version unnamed dense-only collections may be discovered when the
  current collection is missing and the stored embedding contract is compatible;
- named dense collections query with `using="dense"`;
- legacy unnamed dense collections query without `using`;
- sparse schema mismatch must not block semantic-only search;
- full sparse hybrid requires explicit rebuild.

This compatibility rule must be implemented deliberately. A schema bump cannot
silently make old indexes invisible and then report `index_missing` if a
dense-compatible prior collection exists.

## 5.1) Backend abstraction boundary

P4.A must preserve the P2 backend abstraction model.

`repo-semantic-search` must not care whether models are served from:

- WSL native processes;
- native Windows/Linux/macOS processes;
- Docker CPU containers;
- Docker GPU containers;
- llama.cpp / llama-server compatible HTTP endpoints;
- TEI-compatible endpoints;
- custom local HTTP servers such as the existing `gpu_server.py`;
- future managed endpoints.

The MCP runtime works over backend roles and endpoints, not over a specific
deployment topology.

For P4.A this means:

- dense embeddings still go only through the existing `EmbeddingProvider`
  abstraction;
- Qdrant sparse vectors are deterministic local lexical vectors and do not add a
  new model-serving dependency;
- no P4.A code should assume Docker GPU, WSL native, llama.cpp, TEI, or any other
  concrete serving mode;
- backend identity and compatibility remain status concerns, not search-routing
  assumptions;
- future reranker and ColBERT stages must remain optional backend roles with
  endpoint contracts, not hardcoded local processes.

The stable contract is:

```text
SearchService
  -> EmbeddingProvider for dense vectors
  -> Sparse lexical encoder for local deterministic sparse vectors
  -> QdrantStore for retrieval storage
```

Everything behind `EmbeddingProvider` may be swapped by profile/backend config.
P4.A must not weaken this.

## 6) Target behavior

### 6.1 Index build

Full rebuild should:

```text
discover files
  -> chunk files
  -> embed chunks for dense vectors
  -> build sparse lexical manifest per physical collection
  -> encode chunks into sparse vectors
  -> recreate Qdrant collections with named dense+sparse vectors
  -> upsert points with both vector branches
  -> persist dense and sparse contract metadata
```

### 6.2 Hybrid query

Hybrid search should:

```text
query
  -> dense branch with raw query text
  -> sparse branch with lexical analyzer query vector
  -> retrieve dense candidates from Qdrant
  -> retrieve sparse candidates from Qdrant
  -> weighted RRF over branch ranks
  -> apply result shaping, snippets, matched terms, line matches
  -> return diagnostics and warnings
```

### 6.3 Dense query input

Dense query text stays raw. Do not apply identifier splitting or lexical
normalization to the dense branch in P4.A.

### 6.4 Sparse query input

Sparse query input uses the P4.A baseline lexical analyzer.

P4.A analyzer must:

- preserve exact compound tokens when they are useful anchors;
- emit lowercase normalized copies for matching;
- emit split parts for obvious separators such as whitespace, punctuation,
  slash, dot, colon, hyphen, and underscore;
- represent tokens as `(surface, canonical, token_type)`;
- use `canonical` as the sparse vocabulary key;
- keep `surface` only for explanations, matched terms, and exact-search hints;
- be deterministic and versioned.

Vocabulary identity:

```text
surface token: the text form observed or generated by the analyzer
canonical token: lowercase normalized vocabulary key
```

Example:

```text
DATABASE_URL surface -> canonical database_url
database_url surface -> canonical database_url
```

Both surfaces map to the same sparse `token_to_id` entry. This keeps sparse
matching case-insensitive and deterministic while preserving exact surfaces for
diagnostics and local `rg` hints.

Golden examples for P4.A:

| Input | Required emitted tokens |
| --- | --- |
| `DATABASE_URL` | `DATABASE_URL`, `database_url`, `database`, `url` |
| `UserRepository.findByEmail` | `UserRepository.findByEmail`, `userrepository.findbyemail`, `userrepository`, `findbyemail` |
| `services/user/api/connect_flow.py` | `services/user/api/connect_flow.py`, `services`, `user`, `api`, `connect_flow`, `connect`, `flow`, `py` |
| `/api/v1/users/{id}` | `/api/v1/users/{id}`, `api`, `v1`, `users`, `id` |
| `--target-repo-path` | `--target-repo-path`, `target`, `repo`, `path` |
| `permission denied` | `permission`, `denied` |

P4.B may add camelCase splitting (`find`, `by`, `email`) and more language-
aware expansions. P4.A must at least make the table above stable.

P4.B will extend this into full code-aware lexical normalization for camelCase,
routes, SQL identifiers, env vars, CLI flags, and error strings.

## 7) Qdrant schema

### 7.1 Physical collections

Keep current logical scopes:

```text
code -> settings.collection_code
docs -> settings.collection_docs
```

Do not collapse code/docs collections in P4.A.

### 7.2 Named vectors

New collections should use named vectors:

```text
dense:
  type: dense vector
  size: embedding dimension
  distance: cosine

sparse:
  type: sparse vector
  distance/scoring: Qdrant sparse dot product over provided weights
  sparse IDF modifier: disabled / none
```

Implementation must verify the exact `qdrant-client` model types available under
`qdrant-client[fastembed]>=1.9,<2.0` before coding. The intended shape is:

```python
vectors_config={
    "dense": models.VectorParams(size=vector_size, distance=models.Distance.COSINE),
}
sparse_vectors_config={
    "sparse": models.SparseVectorParams(...),  # no server-side IDF modifier
}
```

When querying named vectors, dense queries must specify `using="dense"` and
sparse queries must specify `using="sparse"`.

Qdrant server must be pinned to a known-compatible version instead of
`qdrant/qdrant:latest`. Minimum target for P4.A is Qdrant `1.10.0` or newer
because the future route depends on Query API hybrid/RRF support. The
implementation may pin a higher version after verifying sparse vector behavior
against the local Docker profile.

## 8) Sparse lexical manifest

### 8.1 Preferred design

Use a persisted vocabulary and BM25-style sparse weights.

Manifest is per physical collection because code/docs have different corpora and
statistics:

```text
sparse_manifest:
  contract_version
  scope
  collection_name
  lexical_analyzer_version
  sparse_encoder_kind
  immutable_sparse_contract_hash
  token_to_id
  doc_count
  avg_doc_len
  document_frequency
  bm25_params
  vocabulary_hash
  corpus_stats_hash
  manifest_content_hash
  sparse_stats_stale
  built_at
  updated_at
```

Default BM25 parameters:

```text
k1 = 1.2
b = 0.75
```

The manifest should be stored outside Qdrant so query encoding can happen
without scrolling the collection. A reasonable default location is under
`artifacts/`, keyed by repo/profile/schema/scope.

Hash meanings:

- `immutable_sparse_contract_hash`: analyzer version, encoder kind, BM25
  formula version, token-id scheme, and hash/canonicalization rules. This must
  stay stable across incremental vocabulary/stat updates.
- `vocabulary_hash`: current `token_to_id` mapping.
- `corpus_stats_hash`: current `doc_count`, `avg_doc_len`, and
  `document_frequency`.
- `manifest_content_hash`: canonical hash of the full manifest content excluding
  `built_at`, `updated_at`, and `manifest_content_hash` itself.

Point payloads should store `sparse_contract_id` /
`immutable_sparse_contract_hash`, not the mutable full manifest hash. This avoids
making older points look incompatible after an incremental update appends a new
token or marks sparse statistics stale.

Canonical manifest rules:

- sort file paths lexicographically before building corpus statistics;
- sort chunks by `(relative_path, start_line, end_line, point_id)`;
- on full rebuild, assign token ids in lexicographic canonical-token order, not
  discovery order;
- on incremental update, append new token ids after the current max id and never
  renumber existing ids;
- serialize manifest JSON with sorted keys and compact separators;
- exclude `built_at`, `updated_at`, and `manifest_content_hash` from
  `manifest_content_hash`;
- compute `vocabulary_hash` from canonical `token_to_id`;
- compute `corpus_stats_hash` from canonical `doc_count`, `avg_doc_len`, and
  sorted `document_frequency`.

Two full builds over the same corpus must produce identical token ids,
`vocabulary_hash`, `corpus_stats_hash`, and `manifest_content_hash` even if
filesystem traversal order differs.

Incremental builds are allowed to produce a different token-id order than a later
full rebuild because they preserve existing ids and append new ones. This is
acceptable only while `sparse_stats_stale=true`; full rebuild is the canonical
state.

### 8.2 Sparse vector weights

For each document chunk:

```text
tf_norm = tf * (k1 + 1) / (tf + k1 * (1 - b + b * doc_len / avg_doc_len))
idf = ln(1 + (doc_count - df + 0.5) / (df + 0.5))
doc_weight = tf_norm * idf
```

For a query:

```text
query_weight = 1.0
```

or, if duplicate query terms are kept:

```text
query_weight = query_term_frequency
```

The implementation should start with `query_weight = 1.0` for unique query
terms unless tests show repeated terms are useful.

Because document weights already include IDF, Qdrant sparse-vector server-side
IDF modifiers must be disabled. Enabling a Qdrant IDF modifier would double-apply
IDF and distort sparse scores.

### 8.3 Hashed fallback

Stable hashed sparse indices are allowed only as a fallback if vocabulary
management becomes too heavy for the first implementation.

If hashing is used:

- record `hashing_scheme_id`;
- record hash bit width / modulo;
- expose collision risk in diagnostics;
- do not claim exact-anchor explainability is perfect.

The preferred implementation remains a vocabulary manifest.

## 9) Incremental reindex behavior

Full rebuild creates a compatible sparse manifest.

Full rebuild must handle empty scopes explicitly. If `code` or `docs` has zero
chunks:

- delete the old physical collection for that scope if it exists, or recreate an
  empty compatible collection if Qdrant supports empty named dense+sparse
  collections without points;
- write an empty manifest with `doc_count=0`;
- mark that scope as `intentionally_empty`;
- clear stale sparse stats for that scope;
- report zero points in status without leaving stale points/manifests from a
  previous build.

An intentionally empty scope is compatible, not unavailable. Do not report
`sparse_vector_missing` for a scope that is empty by current include/exclude
policy and has an empty compatible manifest.

Incremental reindex is more subtle because BM25 corpus statistics change when
files are added, removed, or edited.

P4.A behavior:

```text
reindex_paths(paths):
  -> delete old chunks for touched paths
  -> build new chunks
  -> dense-embed new chunks
  -> sparse-encode new chunks against current manifest
  -> upsert new points
  -> mark sparse stats approximate/stale when corpus stats changed
```

New terms may be appended to the manifest. If appending a new term means old
points do not contain that term, that is fine. Existing terms whose document
frequency changes do not require reweighting all old points during incremental
reindex.

Status should then report a nonblocking warning:

```text
sparse_stats_stale
```

Search remains available. Full rebuild refreshes exact sparse statistics and
clears the warning.

This is a pragmatic compromise. Recomputing all sparse vectors on every file
change would make watcher/incremental workflows too expensive.

`sparse_stats_stale` must be durable. Store it in the sparse manifest and expose
it through status after process restart.

Set `sparse_stats_stale=true` when incremental reindex changes the sparse corpus
in any of these ways:

- file added;
- file deleted;
- file changes scope between `code` and `docs`;
- chunk count for a touched file changes;
- term frequencies or document frequencies may have changed;
- deletion-only reindex produces no new chunks.

Full rebuild clears `sparse_stats_stale`.

Incremental reindex against old dense-only or missing-manifest indexes must not
silently create partial sparse state. Required behavior:

```text
if collection is legacy dense-only or sparse manifest is missing:
  do dense-only incremental reindex if the legacy dense path supports it
  mark sparse branch unavailable
  add next action: explicit_sparse_rebuild_recommended
  do not upsert sparse vectors into the legacy collection
```

## 10) Search and fusion

### 10.1 Candidate widths

Initial defaults:

```text
dense_limit = min(max_dense_cap, max(50, top_k * 8))
sparse_limit = min(max_sparse_cap, max(100, top_k * 12))
```

Suggested caps:

```text
max_dense_cap = 320
max_sparse_cap = 500
```

Sparse recall should usually be wider than dense recall because lexical anchors
are cheap and important for code search.

### 10.2 Weighted RRF

Use weighted Reciprocal Rank Fusion:

```text
rrf_score(document) = sum(branch_weight / (rrf_k + rank_in_branch))
```

Initial constants:

```text
rrf_k = 60
dense_weight = 1.0
sparse_weight = 1.2
```

For exact-anchor-heavy queries, later P4.B may choose:

```text
dense_weight = 0.8
sparse_weight = 1.4
```

P4.A can use the fixed default weights and expose the weights in diagnostics.

### 10.3 Score fields

`SearchResult.score` and `final_score` should be the final RRF score for hybrid
results after P4.A.

`dense_score` remains the raw Qdrant dense score when the chunk appeared in the
dense branch.

`lexical_score` remains the raw Qdrant sparse score when the chunk appeared in
the sparse branch.

Do not interpret `dense_score` and `lexical_score` as comparable values.

### 10.4 Match type

Set `match_type` as:

```text
hybrid  -> appeared in both dense and sparse branches
semantic -> dense branch only
lexical -> sparse branch only
```

`exact` remains reserved for a future indexed exact tool or exact-search result
type.

## 13) Status contract additions

Add a compact retrieval status summary to `IndexStatusResult`:

```python
class RetrievalScopeStatus(BaseModel):
    scope: Literal["code", "docs"]
    state: Literal[
        "ready",
        "intentionally_empty",
        "legacy_dense_only",
        "missing",
        "incompatible",
        "unknown",
    ]
    dense_available: bool
    sparse_available: bool
    points_count: int

    dense_schema_kind: Literal["named", "unnamed_legacy", "missing", "unknown"]
    dense_vector_name: str | None = None
    sparse_available: bool
    sparse_contract_compatible: bool
    sparse_unavailable_codes: list[str] = []
    sparse_vector_points: int | None = None
    immutable_sparse_contract_hash: str | None = None
    sparse_vocabulary_hash: str | None = None
    sparse_corpus_stats_hash: str | None = None
    sparse_stats_stale: bool = False
    scope_statuses: list[RetrievalScopeStatus] = []
    fusion_methods_supported: list[str] = ["weighted_rrf"]
    legacy_lexical_fallback_enabled: bool = False
```

For new collections:

```text
dense_schema_kind = "named"
dense_vector_name = "dense"
```

For old unnamed dense-only collections:

```text
dense_schema_kind = "unnamed_legacy"
dense_vector_name = None
sparse_available = false
sparse_unavailable_codes includes legacy_dense_only_collection
```

Global `sparse_available` aggregation:

```text
true only when every non-empty scope is sparse-compatible;
intentionally_empty scopes do not make sparse unavailable;
false if any non-empty requested scope is missing, legacy_dense_only, or incompatible.
```

Add sparse fields to collection contract models:

```text
sparse_vector_present
stored_sparse_contract_hash
stored_lexical_analyzer_version
stored_sparse_encoder_kind
sparse_compatibility
sparse_warning_codes
```

Unavailable codes:

```text
sparse_vector_missing
sparse_manifest_missing
sparse_contract_mismatch
sparse_schema_unsupported
legacy_dense_only_collection
```

`sparse_stats_stale` is not an unavailable code. It is a nonblocking boolean plus
warning. Sparse/hybrid search remains available when sparse stats are stale,
with exact verification recommended.

Sparse-unavailable states must also add a nonblocking next action to
`index_status.availability.next_actions`:

```text
code: explicit_sparse_rebuild_recommended
severity: warning
title: Rebuild index to enable Qdrant sparse hybrid retrieval
tool_hint: build_index(force_rebuild=true)
```

Use this next action for:

```text
sparse_vector_missing
sparse_manifest_missing
sparse_contract_mismatch
sparse_schema_unsupported
legacy_dense_only_collection
```

For `sparse_stats_stale=true`, use the same next-action code and title, but make
the detail clear that this is a quality/statistics refresh recommendation, not a
search availability blocker.

Search availability rules:

```text
semantic search:
  allowed with dense-compatible index
  old unnamed dense vectors are allowed through the explicit legacy dense path

hybrid search:
  full mode requires dense + sparse compatible branches

hybrid search with old index:
  search_v2 returns sparse_branch_unavailable or legacy fallback warning
  legacy list tools may use local BM25 fallback during compatibility window

repo_context_search in future:
  should require sparse branch for route="hybrid"
  should degrade explicitly when sparse is unavailable
```

## 14) Legacy fallback window

Keep the local `rank_bm25` fallback only as a compatibility bridge.

Rules:

- fallback is allowed for legacy `hybrid_search*` tools and `search_v2` during
  one transition window;
- fallback must set `retrieval_backend="legacy_dense_local_bm25"`;
- fallback must set `fusion_method="legacy_score_blend"` unless RRF is reused
  over dense + local BM25 ranks;
- fallback must emit `legacy_lexical_fallback_used` in `search_v2`;
- fallback should not be used by future `repo_context_search`;
- fallback removal should be a later cleanup after sparse rebuild path is stable.

Preferred implementation path: even when fallback uses local BM25, fuse dense
and local lexical ranks with RRF instead of keeping score blending. If that adds
too much risk in P4.A, leave fallback behavior unchanged but isolate it behind a
clearly named legacy execution path.

Use unit tests for analyzer/manifest/RRF. Mock Qdrant where possible for vector
shape and query path. Integration tests against Qdrant are useful but should not
be required for every unit-test run unless the existing test suite already
requires Qdrant.

## 17) Acceptance criteria

P4.A is complete when:

1. New full rebuild creates Qdrant collections with named dense and sparse
   vector branches.
2. New upserts write both dense and sparse vectors for every indexed chunk.
3. Hybrid search uses Qdrant dense and sparse branch candidates.
4. Hybrid fusion uses weighted RRF.
5. `SearchResult.score` / `final_score` represent final RRF score.
6. Raw dense and sparse scores remain visible as branch-local diagnostics.
7. `search_v2` reports `retrieval_backend`, `fusion_method`, branch counts,
   branch weights, and sparse manifest state.
8. `index_status.v2` reports sparse availability and compatibility.
9. Old dense-only indexes do not masquerade as full hybrid indexes.
10. Compatible old unnamed dense-only indexes remain usable for semantic-only
    search through the explicit legacy dense path.
11. Hybrid search on old dense-only indexes reports sparse unavailable or uses
    the marked legacy fallback during the compatibility window.
12. Full rebuild handles empty `code` or `docs` scopes without leaving stale
    collections or sparse manifests behind.
13. Incremental reindex persists `sparse_stats_stale` for edits, deletes, and
    scope moves, and full rebuild clears it.
14. Legacy list-shaped tools remain backward-compatible.
15. No search/status tool implicitly rebuilds index or sparse manifest.
16. Local BM25 full collection scroll is no longer the primary hybrid path for
    compatible new indexes.

## 18) Open implementation checks

Resolve these during implementation before large edits:

1. Confirm exact `qdrant-client` API for named sparse vector collection creation
   under the installed version range.
2. Confirm Docker Qdrant image version supports the selected sparse vector
   schema, then pin `deploy/repo-semantic-search/docker-compose.repo-semantic-search.yml`
   to a known-compatible Qdrant version instead of `latest`.
3. Decide manifest storage path and whether it should be tracked in registry DB
   or as files under `artifacts/`.
4. Decide whether legacy local BM25 fallback should also switch to RRF in P4.A
   or stay as-is behind a clearly marked legacy path.
5. Decide whether schema version bump should be `2` exactly or use the next
   configured version if another migration lands first.
