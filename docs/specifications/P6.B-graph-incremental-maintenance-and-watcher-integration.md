# P6.B: Graph Incremental Maintenance and Watcher Integration

Status: draft specification.

## 1) Purpose

This slice fixes a product-breaking gap in the graph retrieval flow.

The current vector watcher can keep Qdrant dense/sparse chunks current, but the
SQLite graph artifact remains a point-in-time snapshot. After normal
development work, the vector index may become fresh while graph expansion is
disabled because the graph was built against an older source-index contract.

Observed dogfood example on a large private backend/control-plane repository:

```text
graph built_commit:
  010e7c4d09a05e089364ee75cadbe1c3102f43ec

current indexed_commit_hash:
  6d105284fc6238c81b403bd5d5235337579833be

semantic index:
  ready, search_available=true, index_stale=false

graph:
  state=stale, expansion_allowed=false
```

This is a bug for the intended product, not just a diagnostics issue. If graph
retrieval is part of the daily agent workflow, ordinary watcher catch-up must
not leave graph search unusable until a human runs `rebuild_graph`.

The goal is:

```text
Normal incremental repository changes should update the vector index and graph
artifact together, within bounded safe-recovery rules, without full index or
graph rebuilds.
```

## 2) Product Principle

Graph freshness must follow the same practical rule as vector freshness:

```text
small/ordinary changed path set
  -> safe incremental repair/update

large/ambiguous/contract-breaking change
  -> permission-required lifecycle action
```

`rebuild_graph` remains available, but it must be the last answer, not the
default response to ordinary graph stale.

## 3) Scope

This spec covers:

- explicit `update_graph(paths=[...])`;
- graph path-scoped mutation in SQLite;
- watcher integration after successful vector reindex;
- startup reconcile integration;
- safe-recovery policy and bounds;
- graph status semantics after incremental updates;
- e2e fixture tests for restart, branch switch, watcher catch-up, and graph
  allowed/blocked behavior.

This spec does not cover:

- graph schema v2 redesign;
- new extractor edge types;
- tree-sitter;
- typed PPR;
- reranker/ColBERT;
- automatic full graph rebuild;
- graph updates from status/search.

## 4) Current Failure Mode

Current behavior:

```text
start_watcher
  -> startup reconcile
  -> RepositoryIndexer.reindex_paths(touched)
  -> Qdrant chunks updated
  -> registry indexed_commit_hash updated
  -> graph metadata still points to old indexed chunks/source revision
  -> graph_status sees source contract mismatch
  -> graph expansion disabled
```

This is correct from a safety perspective but wrong from a product perspective.
The graph artifact has no incremental maintenance loop.

## 5) Core Decision

Add a bounded incremental graph lifecycle operation:

```text
update_graph(paths=[...])
```

`update_graph` is not a full rebuild. It must:

- never call embedding providers;
- never mutate Qdrant;
- never rebuild the vector index;
- never drop the whole graph artifact;
- mutate only graph rows needed for the provided paths plus bounded shared
  term/global nodes;
- update graph metadata/source-index contract after success;
- produce machine-readable summary and audit trail.

`build_graph` and `rebuild_graph` remain permission-required lifecycle actions.
`update_graph` is a safe recovery action only when its bounds and preconditions
are satisfied. If the update exceeds automatic bounds but remains within manual
hard bounds, the public tool may be retried with `allow_large_update=true` after
explicit operator/user permission. Safe-recovery agents must not set this flag
implicitly.

## 6) API Surface

Add MCP tool:

```python
update_graph(
    paths: list[str] = [],
    idempotency_key: str | None = None,
    allow_large_update: bool = False,
) -> GraphUpdateResult
```

Recommended result:

```python
class GraphUpdateResult(BaseModel):
    contract_version: Literal["graph_update.v1"]
    repo_root: str
    profile: str
    graph_path: str
    operation_id: str | None = None
    lease_id: str | None = None
    audit_id: str | None = None
    idempotency_key: str | None = None
    idempotent_retry: bool = False
    allow_large_update: bool = False
    operation_in_progress: bool = False

    updated: bool
    skipped: bool = False
    skip_reason: str | None = None

    paths_requested: int
    paths_discovered: int
    paths_normalized: int
    paths_required: int
    reverse_dependent_paths_added: int
    paths_updated: int
    paths_deleted: int
    zero_chunk_paths: int
    paths_missing_from_index: int
    paths_skipped: int

    chunks_scanned_total: int
    chunks_for_updated_paths: int

    nodes_deleted: int
    edges_deleted: int
    nodes_upserted: int
    edges_upserted: int

    source_contract_updated: bool
    source_contract_revision_before: str | None = None
    source_contract_revision_after: str | None = None
    graph_state_after: str
    expansion_allowed_after: bool

    bounds_exceeded: list[str] = []
    update_plan_hash: str | None = None
    metadata_only_update: bool = False
    warning_codes: list[str] = []
    recommended_actions: list[RecommendedAction] = []
    status: GraphStatusResult | None = None
```

The tool must normalize and validate paths as repo-relative paths. Absolute
paths, path traversal, empty paths, and paths outside the active repo must be
rejected.

If `paths=[]`, the tool discovers required graph update paths from graph status,
path manifest, graph-vs-index diff, and watcher/reconcile state. This is the
safe recovery path for "watcher is already running, graph is stale".

If explicit `paths` are provided, they are a seed set, not necessarily the
complete update set. The implementation must expand them to the full required
bounded update plan before mutating metadata.

## 7) Preconditions

`update_graph(paths)` may run only when:

- active runtime repo matches requested repo;
- semantic search is available;
- graph artifact exists and is readable;
- graph schema is compatible;
- extractor versions are compatible;
- source-index hard contract is compatible:
  - schema version;
  - profile;
  - collection names;
  - collection readability;
- no conflicting lifecycle lease is active;
- number of normalized paths is within safe bounds;
- current Qdrant collections are readable.

If graph is missing, artifact-level errored, incompatible, or extractor
contract changed, `update_graph` must not run. It should return a
permission-required action for `build_graph` or `rebuild_graph`.

Error granularity:

```text
artifact/schema/metadata/read error
  -> update_graph blocked
  -> rebuild_graph permission-required

path-level graph_files errors with readable compatible artifact
  -> update_graph allowed when affected paths are known/bounded
  -> status recommends update_graph, not rebuild_graph
```

Path-level extraction errors are repairable by this slice; corrupt or unreadable
graph artifacts are not.

Important compatibility rule:

```text
collection name/readability/schema/profile = hard contract
collection point counts / indexed chunk counts / source_revision_hash = updateable contract
```

The current implementation treats the whole `collections` object as hard. P6.B
must split that contract before implementing `update_graph`; otherwise every
ordinary incremental update changes `points_count` and blocks the very recovery
path this spec introduces.

## 8) Bounds

Add settings:

```python
SEMANTIC_MCP_GRAPH_UPDATE_MAX_PATHS = 100
SEMANTIC_MCP_GRAPH_UPDATE_MAX_CHUNKS_SCANNED = 50000
SEMANTIC_MCP_GRAPH_UPDATE_MAX_CHANGED_CHUNKS = 3000
SEMANTIC_MCP_GRAPH_UPDATE_MAX_ROWS_DELETED = 200000
SEMANTIC_MCP_GRAPH_UPDATE_MAX_ROWS_UPSERTED = 200000
SEMANTIC_MCP_GRAPH_UPDATE_MAX_DURATION_MS = 180000
SEMANTIC_MCP_GRAPH_UPDATE_LARGE_MAX_ROWS_DELETED = 1000000
SEMANTIC_MCP_GRAPH_UPDATE_LARGE_MAX_ROWS_UPSERTED = 1000000
SEMANTIC_MCP_GRAPH_UPDATE_LARGE_MAX_DURATION_MS = 600000
SEMANTIC_MCP_GRAPH_UPDATE_DISCOVERY_MAX_PATHS = 1000
SEMANTIC_MCP_GRAPH_UPDATE_DISCOVERY_MAX_CHUNKS = 50000
SEMANTIC_MCP_GRAPH_UPDATE_MAX_REVERSE_DEPENDENT_PATHS = 100
SEMANTIC_MCP_GRAPH_UPDATE_AUTO_BATCH_PATHS = 50
SEMANTIC_MCP_GRAPH_UPDATE_AUTO_BATCHES = 5
SEMANTIC_MCP_GRAPH_UPDATE_ON_WATCHER = True
SEMANTIC_MCP_GRAPH_UPDATE_ON_STARTUP_RECONCILE = True
```

Bounds are configurable and must be echoed in results.

If bounds are exceeded before mutation, return:

```text
updated=false
warning_codes=["graph_update_bounds_exceeded"]
recommended_actions=[permission-required update_graph or rebuild_graph only if update cannot be safe]
```

If bounds are exceeded after partial mutation should not happen in the normal
path. The implementation must plan deletions/upserts first, check bounds, then
mutate in one SQLite transaction.

Large but updateable path sets should use tiered recovery:

```text
<= auto batch bounds:
  safe auto-run one logical update_graph operation with internal row batches

> auto batch bounds but <= hard update bounds:
  permission-required update_graph, not rebuild_graph

permission-required update_graph with allow_large_update=true:
  may use the larger manual row/time bounds, but only after the plan has been
  computed and still fits within configured large-update caps

> hard update bounds or hard contract mismatch:
  permission-required rebuild_graph
```

This avoids prompting for full rebuilds when a large branch switch can still be
handled by bounded graph update.

Batched execution semantics:

```text
one GraphUpdatePathPlan
  -> one update_plan_hash
  -> one lifecycle/audit operation
  -> zero or more internal SQLite row batches
  -> graph_metadata advanced only after every batch succeeds
```

Internal batching is an implementation detail. It must not expose intermediate
`graph_state=ready` or advance `source_index_contract_json` for the full current
source index until all required paths and reverse dependents in the plan are
applied successfully. If any batch fails, metadata remains stale/degraded and
the remaining planned paths stay visible in status.

## 9) Graph Store Mutation

Add graph store methods:

```python
GraphStore.update_paths(
    snapshot: GraphSnapshot,
    affected_paths: list[str],
    source_index_contract: dict[str, object],
    expected_index_revision: str,
    update_plan_hash: str,
    built_commit: str | None,
) -> GraphUpdateStoreResult
```

V1 mutation algorithm:

1. Normalize affected paths.
2. Build a path-scoped snapshot for affected indexed chunks.
3. Collect before deleting rows:
   - `path_owned_node_ids`;
   - `shared_candidate_node_ids`;
   - `affected_chunk_ids`.
4. In one SQLite transaction:
   - delete edges whose `relative_path` is in affected paths;
   - delete edges whose `source_node_id` or `target_node_id` is in
     `path_owned_node_ids`;
   - for shared candidate nodes, delete only edges whose origin path is in the
     affected/reverse-dependent closure unless every owning/reverse-dependent
     path for that shared node is included;
   - delete node_chunks for path-owned nodes;
   - delete node_chunks where `chunk_id` is in `affected_chunk_ids` for all
     node types, including shared nodes;
   - delete node_terms for path-owned nodes;
   - delete path-owned nodes:
     - `file`;
     - `chunk`;
     - `symbol`;
     - `doc_section`;
     - `config_item`;
     - `test_case`;
   - do not blindly delete shared nodes:
     - `env_var`;
     - `route`;
     - `module`;
   - recompute shared nodes from all remaining current references when bounded;
   - otherwise keep shared nodes pathless/canonical and store per-path evidence
     only in edges/node_chunks;
   - do not preserve shared node `relative_path`, `chunk_id`, line range, or
     payload values that point at deleted/affected chunks;
   - prune shared nodes only if they become orphaned and have no remaining
     edges/node_chunks;
   - when pruning shared nodes, delete in this order:
     - `graph_node_terms` for shared pruned node ids;
     - `graph_node_chunks` for shared pruned node ids;
     - `graph_nodes` for shared pruned node ids;
   - delete `graph_files` rows for affected paths;
   - insert/update new `graph_files`, nodes, node_terms, node_chunks, edges;
   - each ready `graph_files` row must store a graph input signature for the
     path, not only a source content hash;
   - update `graph_metadata.built_commit`, `built_at`,
     `source_index_contract_json`, and `graph_contract_hash`.

`expected_index_revision` is the full source-index revision hash for the
post-vector state, not just the git commit. It should include or be derived
from `source_index_contract.revision` including `source_revision_hash`,
collection counts, indexed chunk/file counts, and the registry revision id or
timestamp.

Before committing metadata, re-read the current index revision/registry
revision and assert it still matches `expected_index_revision`. Also verify the
active update plan still hashes to `update_plan_hash`. If Qdrant or registry
changed during planning, abort before commit:

```text
updated=false
skip_reason="source_index_revision_changed_during_update"
warning_codes=["graph_update_retry_required"]
```

This prevents a race where the graph is marked current for a source index that
has already moved on.

If canonical shared-node recomputation cannot be proven within bounds, abort
before metadata advancement:

```text
updated=false
skip_reason="shared_node_canonicalization_incomplete"
warning_codes=["graph_shared_nodes_not_repaired"]
```

For deleted paths, the new path-scoped snapshot contains no chunks. The graph
rows for that path are removed and no `graph_files` ready row is inserted.
Optionally insert a `graph_files` row with `graph_state="deleted"` only if this
helps diagnostics; search must not use deleted path evidence.

Zero-chunk indexed files need special handling. They may exist in the path
manifest but produce no Qdrant chunks and no graph rows. They should not force a
graph update or keep graph stale. If such a path is passed to `update_graph`,
the result should count it as skipped with reason `zero_chunk_path` unless it
previously had graph rows that need deletion.

Idempotent upsert rules:

- `graph_files`: `INSERT ... ON CONFLICT(relative_path) DO UPDATE`;
- `graph_nodes`: `INSERT ... ON CONFLICT(node_id) DO UPDATE`;
- `graph_edges`: `INSERT ... ON CONFLICT(edge_id) DO UPDATE`;
- `graph_node_terms`: delete rows for path-owned node ids, then insert
  `OR IGNORE`;
- `graph_node_chunks`: delete rows for path-owned node ids, then insert
  `OR IGNORE`;
- running the same `update_graph` twice with the same source index and paths
  must leave identical graph rows.

## 10) Snapshot Construction

Add builder support for path-scoped graph extraction:

```python
build_graph_update_snapshot(
    repo_root,
    profile,
    all_chunks,
    affected_paths,
    built_commit,
    include_globs,
    exclude_globs,
    source_index_contract,
) -> GraphSnapshot
```

V1 may build extractor context from all indexed chunks, but it must emit rows
only for affected paths plus shared nodes required by their edges.

Reason: import/doc/test/route extractors need repository context to resolve
relationships, but updating graph rows for every file would be a hidden full
rebuild. Reading all chunk payloads is acceptable for v1 because it does not
embed or mutate Qdrant, but it must be bounded by chunk count/time.

Affected-path emission rules:

- path-owned file/chunk/symbol/doc/config/test nodes: only affected paths;
- shared route/module/env nodes: only when referenced by affected paths and
  only with orphan/ref-count checks;
- edges with `relative_path` in affected paths: yes;
- shared `env_var` nodes and term nodes: allowed if referenced by affected
  paths;
- doc/test/import edges originating from an unaffected path are not rewritten
  until reverse-dependent closure adds that origin path to the update set.

This means v1 update is correct only after reverse-dependent closure is applied
or after the update is explicitly marked degraded/blocked. Path-scoped updates
must not mark graph metadata fully current while unaffected docs/tests/imports
still contain known stale edges.

## 10.1 Reverse-Dependent Closure

Before mutation, expand the update set with bounded reverse dependents.

Starting from directly affected nodes/paths, inspect existing graph edges and
node links to find source paths whose graph evidence may reference affected
path-owned nodes or shared nodes whose ownership changed.

Include bounded reverse dependents for edge types:

```text
doc_references_symbol
doc_references_route
doc_references_path
test_targets_symbol
test_targets_file
file_imports_file
module_imports_module
route_handled_by_symbol
```

Existing graph edges are not enough for every case. When affected paths add,
rename, or remove public symbols, routes, modules, config keys, or env-var
anchors, reverse-dependent discovery must also run a bounded indexed
chunk/term scan for newly resolvable references in unaffected files. If the
scan finds origin paths within bounds, add them to the update plan. If the scan
is truncated or cannot prove completeness, do not mark graph metadata current.

If reverse-dependent paths stay within
`SEMANTIC_MCP_GRAPH_UPDATE_MAX_REVERSE_DEPENDENT_PATHS`, add them to the update
plan. If they exceed safe auto-run bounds but remain within hard update bounds,
safe recovery must stop before mutation:

```text
updated=false
skip_reason="reverse_dependencies_exceed_auto_bounds"
warning_codes=["graph_reverse_dependencies_not_repaired"]
recommended action: permission-required update_graph
metadata must not be marked current
```

If they exceed hard bounds:

```text
updated=false
skip_reason="reverse_dependencies_exceed_hard_bounds"
warning_codes=["graph_reverse_dependencies_not_repaired"]
recommended action: permission-required rebuild_graph only when update cannot
  be bounded safely
metadata must not be marked current
```

Known vs unknown reverse dependency state:

```text
reverse dependencies known but not repaired
  -> degraded graph may run with query-aware path guard

reverse dependencies unknown, scan truncated, or completeness unproven
  -> graph_used=false
  -> skipped_reason="graph_invalidated_paths_unknown"
  -> expansion_allowed=false
```

Search may use degraded graph only when unsafe paths are known and query seeds
and graph evidence do not overlap them.

## 10.2 Update Path Discovery

Add a helper:

```python
discover_graph_update_paths() -> GraphUpdatePathPlan
```

It should combine:

1. Path manifest invalidations after `graph_metadata.built_at`, when manifest
   coverage is complete.
2. Direct graph-vs-index diff:
   - current indexed chunks grouped by `relative_path`;
   - current per-path graph input signature;
   - existing `graph_files.graph_input_signature`;
   - paths present in current chunks but absent from graph;
   - graph paths absent from current chunks and not valid zero-chunk paths.
3. Path-level graph errors:
   - `graph_files.graph_state != "ready"`;
   - `graph_files.error_code IS NOT NULL`;
   - include these paths as required update paths unless they are proven
     zero-chunk/deleted.
4. Watcher/reconcile touched paths when provided by the caller.
5. Reverse-dependent closure from section 10.1.

This fallback is required for migrated or older indexes where path manifest was
missing or incomplete when the graph was built. Without it, safe recovery may
know the graph is stale but not know which paths to update.

The plan must classify paths:

```text
changed_chunk_paths
new_chunk_paths
deleted_graph_paths
zero_chunk_paths
unknown_paths
```

Only changed/new/deleted graph paths participate in `update_graph`. Zero-chunk
paths should be recorded for diagnostics but must not keep graph expansion
blocked.

Graph input signature:

```text
relative_path
chunk ids for the path
chunk content hashes
scope
language
chunk_type
symbol/heading path metadata
start_line/end_line
domain tags or extractor inputs used by graph building
extractor-relevant payload fields
```

The signature may be stored directly in `graph_files` or derived from an
equivalent per-path graph state table. It must cover every indexed chunk field
that can change graph nodes, node_chunks, node_terms, edges, or evidence line
ranges. Plain file content hash is not sufficient.

Backward compatibility:

```text
old graph artifact lacks graph_input_signature for a path
  -> treat that path as changed/unknown for update planning
  -> do not allow metadata-only update based only on content_hash equality
```

Metadata-only update:

```text
discovery complete
hard source contract compatible
required graph row paths empty
no non-ready/error graph_files rows remain
only source revision/count/timestamp metadata drift remains
  -> metadata_only_update=true
  -> paths_updated=0
  -> source_contract_updated=true
  -> graph can become ready without row mutation
```

This covers zero-chunk edits, deleted paths that never had graph rows, manifest
repair, and pure source-index revision movement. Metadata-only update is not
allowed when invalidated paths are unknown, graph input signatures are missing,
reverse-dependent discovery is incomplete, or any non-ready/error `graph_files`
row remains.

Completeness rule:

```text
requested paths are seeds;
required paths are discovered union;
metadata may be updated only when required paths are known and fully covered.
```

If stale graph paths are unknown, discovery is truncated, or explicit request
does not cover the required bounded union after expansion, return:

```text
updated=false
skip_reason="graph_update_paths_incomplete"
warning_codes=["graph_invalidated_paths_unknown" or "graph_update_paths_incomplete"]
```

Do not update `graph_metadata` in this state.

## 11) Metadata Contract

After successful update, graph metadata must reflect the current source index,
not only the touched paths.

Required:

- `source_index_contract_json` rebuilt from current indexed chunks;
- `graph_files.graph_input_signature` current for every ready graph path;
- `indexed_chunks_total` current;
- `indexed_files_total` current;
- `source_revision_hash` current;
- `index_revision.indexed_commit_hash` current registry value;
- collection point counts current;
- `built_commit` updated to current indexed commit when index and HEAD match.
- `update_plan_hash` from the completed full graph update plan recorded in
  audit/status where available.

This is what prevents the current bug: graph source contract remains old even
after vector watcher catches up.

The source contract should expose hard and updateable parts separately:

```python
source_index_contract = {
    "hard": {
        "schema_version": ...,
        "profile": ...,
        "collections": {
            "code": {"collection_name": ..., "readable": ...},
            "docs": {"collection_name": ..., "readable": ...},
        },
    },
    "revision": {
        "indexed_commit_hash": ...,
        "indexed_branch": ...,
        "last_full_build_ts": ...,
        "last_incremental_update_ts": ...,
        "code_points_count": ...,
        "docs_points_count": ...,
        "indexed_chunks_total": ...,
        "indexed_files_total": ...,
        "source_revision_hash": ...,
    },
}
```

Backward compatibility: existing graph artifacts with flat v1 source contracts
must still be readable. Status may translate the old flat shape into the new
hard/revision comparison model.

Extractor warning metadata must remain correct after path-scoped updates.
Implementation must choose one of:

- store per-file extractor warning state and merge/remove warnings by path; or
- run a bounded all-context extractor warning pass before writing metadata.

It must not drop warnings from unaffected files or preserve warnings for fixed
affected files without evidence.

## 12) Watcher Integration

Extend watcher flow:

```text
changed/deleted paths detected
  -> reindex_paths(touched)
  -> sync registry state with post-reindex index revision
  -> if vector mutation succeeded and graph update is enabled:
       update_graph(paths=touched, source_contract=post_reindex_contract)
  -> invalidate status/search caches
```

Startup reconcile flow:

```text
start_watcher
  -> startup reconcile vector index
  -> if reconcile mutated or repaired path manifest:
       update_graph(paths=touched)
  -> start live watcher baseline
```

Important: current `reconcile_index()` must return the touched path list,
including deleted paths, so graph update can use the same path set. If no paths
changed, no graph update is needed.

If `reconcile_index()` did not return touched paths because the stale graph was
created before P6.B existed, safe recovery may call `discover_graph_update_paths`
and update those bounded paths.

The graph update must use the post-vector-mutation source index contract. It
must not read stale registry state and then become stale immediately after
registry sync. Acceptance: after watcher catch-up and graph update, a fresh
`graph_status()` call reports no source revision/count/hash mismatch.

If graph update fails safely:

- watcher must continue running;
- dense/sparse search remains available;
- graph status becomes stale/degraded with exact reason codes;
- result includes permission-required next action only if incremental update
  cannot safely resolve it.

If watcher is already running and graph is stale, safe recovery must still have
a path that does not require stopping/restarting watcher:

```text
ensure_ready safe-recover
  -> discover_graph_update_paths
  -> update_graph(paths=discovered)
```

No separate `repair_path_manifest` tool is part of P6.B. Recovery paths are the
internal safe-recovery `reconcile_index` step, `discover_graph_update_paths`,
and `update_graph`.

If the vector index is already fresh and graph is stale, safe recovery must not
require starting the watcher. The graph-only repair path is:

```text
search_available=true
index freshness is fresh/known
graph update_available=true
bounded discovery succeeds
  -> update_graph(paths=discovered)
```

This covers graph metadata/row drift after process restart or after a previous
watcher catch-up completed before P6.B graph integration existed.

Legacy graph artifacts may have ready `graph_files` rows without
`graph_input_signature`. If the current file content hash still matches the
stored graph row `content_hash`, safe recovery should backfill the missing input
signature in graph metadata and must not treat the path as requiring a full row
delete/upsert. If the content hash differs, the path is a real graph update
candidate and normal bounds apply.

## 12.1 Lease and Audit Composition

External MCP tool call:

```text
update_graph(paths, idempotency_key)
  -> acquire lifecycle lease operation="update_graph"
  -> write lifecycle audit success/failure
```

Watcher-internal graph update:

```text
watcher/startup reconcile lease
  -> vector reindex
  -> registry sync
  -> graph update as sub-operation in same audit detail
```

P6.B chooses this model for watcher integration: watcher-internal graph
updates run as a sub-operation under the already-held watcher/startup reconcile
lease and append graph update fields to the same lifecycle audit record. The
external MCP `update_graph` tool acquires its own `operation="update_graph"`
lease.

The implementation must not attempt to acquire a second conflicting lifecycle
lease while already holding the watcher lease.

Same idempotency key retry semantics:

- if an equivalent operation is in progress, return `operation_in_progress=true`;
- if the previous operation completed successfully, return
  `idempotent_retry=true` plus current graph status;
- if the previous operation failed, return the prior failure and do not start a
  duplicate mutation unless the idempotency key changes.

Active lifecycle lease behavior:

```text
compatible watcher/startup lifecycle lease active
  -> operation_in_progress=true
  -> updated=false
  -> skipped=true
  -> skip_reason="lifecycle_operation_in_progress"
  -> recommended action: retry status/ensure_ready after lease completes
  -> no permission-required rebuild/update action

any other active non-compatible lifecycle mutation lease
  -> operation_in_progress=true
  -> updated=false
  -> skipped=true
  -> skip_reason="lifecycle_operation_in_progress"
  -> recommended action: retry status/ensure_ready after lease completes
  -> no build_graph/rebuild_graph/rebuild_index/update_graph recommendation
     until the lease clears
```

Agents should not escalate to `rebuild_graph` while any lifecycle operation is
already moving the index or graph state.

## 13) Safe Recovery Policy

`ensure_ready --mode safe-recover --start-watcher` may run watcher startup
reconcile plus `update_graph` only when:

- watcher startup reconcile is already explicitly allowed, or watcher is
  already running and bounded graph update discovery succeeds;
- update paths are produced by the same reconcile or by
  `discover_graph_update_paths`;
- graph artifact exists and is compatible;
- bounds are satisfied;
- no rebuild is required.

`ensure_ready --mode safe-recover` without `--start-watcher` may run graph-only
`update_graph(paths=[])` when:

- the vector index is already fresh/known;
- graph artifact exists and is compatible;
- `discover_graph_update_paths` is complete and bounded;
- no vector reconcile is required.

Safe auto-run:

```text
start_watcher
update_graph(paths=[bounded changed paths])

or, for graph-only stale:

update_graph(paths=[])
```

Permission-required:

```text
build_graph
rebuild_graph
update_graph(paths=[too many paths])
graph schema migration
extractor contract migration
```

If watcher is already running and index is fresh but graph is stale,
safe-recovery must not require watcher restart. It should run:

```text
discover_graph_update_paths
update_graph(paths=[discovered bounded paths])
```

If vector index freshness itself is uncertain, safe-recovery may run a bounded
`reconcile_index` step that returns touched paths and post-reconcile index
contract. This step is not a rebuild and must obey the same no-implicit-lifecycle
policy: it runs only from explicit safe-recovery/operator flow, never from
status/search.

The helper must report:

```text
graph_update_attempted
graph_update_succeeded
graph_update_skipped_reason
graph_update_bounds_exceeded
graph_update_idempotency_key
graph_update_operation_id
```

`update_graph` safe recovery must use an idempotency key derived from:

```text
repo root
profile
graph artifact path
source_index_contract.revision hash
source_revision_hash
index_revision.indexed_commit_hash
last_incremental_update_ts or registry revision id
update_plan_hash
sorted required affected paths after reverse-dependent expansion
```

Repeated safe-recovery calls with the same key must not duplicate rows or leave
multiple active leases.

## 14) Status Semantics

Add graph status fields:

```python
class GraphStatusSummary(BaseModel):
    ...
    update_available: bool
    update_required: bool
    update_safe_auto_run: bool
    update_blocked_reason: str | None
    update_path_count: int | None
    update_paths_preview: list[str] = []
    rebuild_required: bool = False
```

Graph stale classification:

```text
source revision mismatch + known bounded invalidated paths
  -> update_required=true
  -> update_safe_auto_run=true
  -> rebuild_required=false

source revision mismatch + no graph row paths + complete discovery
  -> update_required=true
  -> update_safe_auto_run=true
  -> rebuild_required=false
  -> recommended action: metadata-only update_graph

source revision mismatch + unknown invalidated paths
  -> update_required=true
  -> update_safe_auto_run=false
  -> rebuild_required=false
  -> safe recovery should run bounded reconcile_index or
     discover_graph_update_paths before any graph metadata mutation

reverse-dependent closure exceeds auto bounds but stays within hard update bounds
  -> update_required=true
  -> update_safe_auto_run=false
  -> rebuild_required=false
  -> update_blocked_reason=reverse_dependencies_exceed_auto_bounds
  -> recommended action: permission-required update_graph

reverse-dependent closure exceeds hard update bounds
  -> update_required=true
  -> update_safe_auto_run=false
  -> rebuild_required=true
  -> update_blocked_reason=reverse_dependencies_exceed_hard_bounds

compatible watcher/startup recovery lease already active
  -> update_required=true
  -> update_safe_auto_run=false
  -> rebuild_required=false
  -> update_blocked_reason=lifecycle_operation_in_progress
  -> recommended action: retry status/ensure_ready after lease completes

any active non-compatible lifecycle mutation lease
  -> update_required=true
  -> update_safe_auto_run=false
  -> rebuild_required=false
  -> update_blocked_reason=lifecycle_operation_in_progress
  -> recommended action: retry status/ensure_ready after lease completes

hard source contract mismatch from collection/schema/profile
  -> update_blocked_reason=hard_contract_mismatch
  -> rebuild_required=true

extractor version mismatch
  -> update_blocked_reason=extractor_contract_mismatch
  -> rebuild_required=true

graph missing
  -> build_graph required
```

Source revision/count/hash mismatch should not be treated as a hard graph
contract mismatch when the hard contract is compatible and update paths are
known or discoverable. It should route to `update_graph`.

Known bounded stale paths do not always have to disable graph search. Reuse the
query-aware path guard from P6.A:

```text
known invalidated paths + query seed/evidence/candidate paths do not overlap
  -> graph expansion may run in degraded mode
  -> diagnostics recommend update_graph

unknown invalidated paths or overlap with invalidated paths
  -> graph_used=false
  -> skipped_reason="graph_update_required"

reverse dependencies known but not repaired and non-overlapping degraded graph used
  -> graph_diagnostics.warning_codes includes
     "graph_reverse_dependencies_not_repaired"

reverse dependencies unknown or scan truncated
  -> graph_used=false
  -> skipped_reason="graph_invalidated_paths_unknown"
  -> expansion_allowed=false
```

`index_status` and `graph_status` still must not execute lifecycle. They only
report the best next action.

## 15) Recommended Actions

Prefer:

```text
start_watcher
safe_recover
update_graph
run_local_rg
```

before:

```text
build_graph
rebuild_graph
rebuild_index
```

For ordinary graph stale after watcher catch-up, the action should be:

```json
{
  "code": "update_graph",
  "requires_user_permission": false,
  "safe_auto_run": true,
  "destructive": false,
  "expensive": false,
  "reason_codes": ["graph_source_index_revision_mismatch"]
}
```

`rebuild_graph` should appear only when incremental graph update is impossible
or unsafe.

`reconcile_index` is internal to watcher/safe-recovery in P6.B. Do not return
it as an agent-callable recommended action unless a public bounded tool contract
is added in a later spec.

## 16) Query Behavior

`repo_context_search(graph_mode=expand)` must use graph only when graph status
allows it.

If graph update is needed but has not run and query-aware degraded graph is not
safe:

- `graph_used=false`;
- `skipped_reason="graph_update_required"`;
- diagnostics include update action;
- dense+sparse results still return.

If graph update is needed but the invalidated path set is known and does not
overlap the query/evidence path set, search may use degraded graph and include:

```text
graph_diagnostics.degraded=true
graph_diagnostics.update_required=true
recommended_next_actions += update_graph
```

Search must never run `update_graph` itself.

## 17) Test Plan

Unit tests:

- `GraphStore.update_paths` deletes/reinserts only affected path rows.
- Shared `env_var` nodes survive when another path still references them.
- Shared `route` and `module` nodes are not blindly deleted by path update.
- Orphan global nodes are pruned after last reference is deleted.
- Pruning the last shared `env_var`/`route`/`module` reference deletes
  `graph_node_terms`, `graph_node_chunks`, then `graph_nodes` without FK
  failures or stale terms.
- Shared route/module/env node canonical metadata never points at deleted or
  affected chunks after update.
- Incident cross-path edges are deleted or trigger bounded reverse-dependent
  update before path-owned nodes are deleted.
- Shared-node `graph_node_chunks` rows for affected chunk ids are deleted and
  rebuilt so env/route/module evidence cannot point at stale chunks.
- Shared candidate nodes do not cause unrelated incident edges from unaffected
  paths to be deleted.
- Metadata source contract updates after path update.
- Metadata-only update advances source contract when discovery is complete and
  no graph rows need mutation.
- Metadata-only update is blocked when any required graph input signature is
  missing or any `graph_files` row is non-ready/errored.
- Existing flat source contract is compared with hard/revision split correctly.
- Point-count/chunk-count/source hash drift recommends `update_graph`, not
  `rebuild_graph`.
- Update path discovery finds changed/new/deleted graph paths by comparing
  current indexed chunk graph input signatures to `graph_files`.
- Discovery treats old graph artifacts without graph input signatures as
  unknown/changed and does not false-clean them through metadata-only update.
- Discovery includes non-ready/error `graph_files` rows as required update
  paths unless proven zero-chunk/deleted.
- Zero-chunk paths do not keep graph stale.
- Deleted indexed path removes graph rows.
- Bounds are checked before mutation.
- Hard contract mismatch blocks update and recommends rebuild.
- Extractor contract mismatch blocks update and recommends rebuild.
- `index_status` recommends `update_graph`, not `rebuild_graph`, for bounded
  source revision drift.
- `repo_context_search` reports `graph_update_required` without running update.
- Newly resolvable references from changed public symbols/routes/modules are
  found by bounded indexed chunk/term scan, or metadata advancement is blocked.
- Truncated newly resolvable reference discovery blocks graph expansion instead
  of using degraded non-overlap mode.
- Batched update advances graph metadata only after the complete plan succeeds.
- Path-level `graph_files` errors are repairable by bounded `update_graph`;
  artifact-level graph errors still require rebuild.

Watcher tests:

- live watcher calls graph update after successful `reindex_paths`;
- startup reconcile calls graph update for touched paths;
- watcher continues if graph update fails safely;
- no graph update is attempted when graph is missing/incompatible;
- lifecycle counters prove no `build_graph`/`rebuild_graph`.
- repeated update with same idempotency key is a no-op/safe retry.
- idempotency key changes for dirty-worktree updates on the same git commit
  when source revision or update plan changes.
- watcher-internal graph update does not deadlock on lifecycle leases.
- safe recovery during a watcher-held graph update reports
  `lifecycle_operation_in_progress` and does not recommend rebuild.
- safe recovery during any active lifecycle mutation reports
  `lifecycle_operation_in_progress` and does not recommend build/rebuild.

Safe recovery tests:

- `ensure_ready --safe-recover --start-watcher` starts watcher and updates graph
  for bounded paths;
- `ensure_ready --safe-recover` updates graph when watcher is already running;
- `ensure_ready --safe-recover` updates graph without starting watcher when the
  vector index is already fresh and graph-only repair is bounded;
- unknown invalidated paths first attempt path manifest/watcher recovery;
- too many graph update paths returns permission-required action.

Fixture e2e tests:

- use a small temporary git repo, not the large private dogfood repository;
- initial explicit build_index/build_graph allowed only for fixture setup;
- commit change to one file;
- restart MCP container;
- run safe recovery;
- assert:
  - `search_available=true`;
  - watcher running;
  - `graph_status.update_required=false`;
  - `graph_status.state=ready`;
  - `stale_path_count=0`;
  - no source revision/count/hash mismatch warning codes;
  - `repo_context_search(graph_mode=expand)` returns `graph_used=true`;
  - forbidden lifecycle counters:
    - `build_index=0`;
    - `rebuild_index=0`;
    - `build_graph=0`;
    - `rebuild_graph=0`.

Use degraded graph assertions only for explicit incomplete or
reverse-dependent-over-bound scenarios, not for the successful bounded update
path.

Fixture matrix:

- restart container with bounded change -> graph update -> expansion allowed;
- branch switch with bounded diff -> watcher reconcile -> graph update ->
  expansion allowed;
- branch switch over auto bounds but under hard update bounds -> no rebuild,
  permission-required `update_graph`;
- branch switch over hard update bounds -> no rebuild, permission-required
  `rebuild_graph`;
- graph hard contract mismatch -> rebuild required, no auto update;
- watcher already running + stale graph -> safe recovery discovers and updates
  graph paths.

Large repo dogfood:

- no rebuild by default;
- use the large private dogfood repository only for no-rebuild smoke;
- verify graph update recovers after small committed changes;
- full graph rebuild on the large private dogfood repository only with explicit user permission.

## 18) Acceptance Criteria

This slice is done when:

1. Ordinary watcher catch-up keeps graph usable.
2. A graph built at commit N can be incrementally updated after commit N+1
   without `rebuild_graph`.
3. `rebuild_graph` is not recommended for bounded source revision drift.
4. `ensure_ready` can recover watcher + graph for bounded changed paths.
5. Search/status never execute graph lifecycle implicitly.
6. Watcher/safe-recovery graph updates are bounded, audited, and idempotent.
7. Graph metadata source contract matches the current indexed chunks after
   successful update.
8. Graph expansion stays blocked for real hard mismatches.
9. Small fixture e2e proves restart/branch/watcher/graph flow without using the
   large private-repository rebuild path.
10. Running `update_graph` with an incomplete path set cannot mark the graph
    clean.
11. Reverse-dependent stale evidence is either updated within bounds or exposed
    as degraded/blocked.
12. Internal graph update batches cannot advance metadata until the complete
    plan succeeds.
13. Dirty-worktree updates on the same commit produce distinct idempotency keys
    when source revision or update plan changes.
14. Graph-only stale repair works when the vector index is already fresh and
    watcher is not running.
15. Unknown/truncated reverse-dependent discovery fails closed and blocks graph
    expansion.
16. Path-level graph errors can be repaired incrementally without forcing a
    full graph rebuild.

## 19) Things Not To Build

Do not build these in this slice:

```text
automatic rebuild_graph from status/search
automatic build_graph when graph is missing
automatic rebuild_index
hidden repo/backend/profile switch
unbounded all-repo graph rewrite from watcher
graph schema migration
new extractor families
unbounded reverse dependency graph repair
```
