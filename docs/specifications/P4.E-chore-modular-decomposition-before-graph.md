# P4.E Chore: Modular Decomposition Before Graph Work

## 1) Purpose

This chore slice prepares `repo-semantic-search` for P5 graph work by reducing
large mixed-responsibility modules into stable, smaller modules.

The goal is not to redesign retrieval behavior. The goal is to make the current
behavior easier to preserve, test, and extend before adding SQLite graph
artifacts, graph status, seed binding, and graph expansion.

This is a structure-first specification:

```text
preserve behavior
  -> introduce compatibility facades
  -> extract pure helpers and contracts
  -> split tests by public contract
  -> create graph-ready seams
  -> only then implement P5 graph features
```

## 2) Current Problem Zones

The current implementation is functional, but recent P3/P4 slices have naturally
concentrated too many responsibilities in a few files.

Measured local size at the time of this spec:

```text
services/repo_semantic/search_service.py   ~3150 lines
services/repo_semantic/mcp_server.py       ~1100 lines
tests/test_search_contract.py               ~800 lines
services/repo_semantic/registry.py          ~620 lines
services/repo_semantic/models.py            ~560 lines
services/repo_semantic/sparse.py            ~550 lines
services/repo_semantic/qdrant_store.py      ~525 lines
services/repo_semantic/config.py            ~475 lines
services/repo_semantic/indexer.py           ~385 lines
```

The main risk is not file size by itself. The risk is that P5 graph work would
otherwise add graph lifecycle, graph status, graph branch retrieval, graph
evidence paths, and graph freshness into files that already combine unrelated
concerns.

### 2.1 `search_service.py`

`SearchService` currently owns:

- query validation and caps;
- filter normalization;
- Qdrant payload filter planning;
- client-side path/glob filtering;
- dense retrieval;
- sparse retrieval;
- local legacy BM25 fallback;
- RRF fusion;
- snippet and line match shaping;
- `semantic_search`;
- `hybrid_search`;
- `search_v2`;
- `repo_context_search`;
- exact-anchor action guidance;
- registry sync;
- index contract checks;
- retrieval status assembly;
- freshness policy;
- `index_status.v2`.

This is the highest-priority decomposition target. P5 graph expansion must not
be pasted into this class.

### 2.2 `mcp_server.py`

`mcp_server.py` currently combines:

- runtime singleton/bootstrap state;
- HTTP health routes;
- search tool wrappers;
- repo-context tool wrapper;
- lifecycle tool wrappers;
- backend selection/action planning;
- repo registry tools;
- watcher tools;
- resources.

The public MCP tool names and shapes must stay stable, but registration can be
split after service-layer contracts are protected.

### 2.3 `models.py`

`models.py` has become the public schema catalog for:

- chunk records;
- search rows;
- `search_v2` diagnostics;
- `repo_context_search`;
- status/freshness/lifecycle;
- registry entries;
- backend status.

This file should become a compatibility re-export layer over focused contract
modules.

### 2.4 `tests/test_search_contract.py`

`test_search_contract.py` currently covers:

- legacy filter behavior;
- hybrid sparse/RRF behavior;
- `search_v2`;
- `repo_context_search`;
- snippets and line matches;
- per-file caps;
- exact fallback guidance;
- find-similar behavior;
- legacy payload shape compatibility.

P5 graph tests would make this file brittle. Tests should be split by public
contract and shared fakes/helpers should be extracted first.

### 2.5 Secondary Targets

These are important, but should be handled after the search facade is stable:

- `qdrant_store.py`: collection naming, schema creation, payload codec,
  dense/sparse search, payload index introspection, and legacy collection
  fallback are currently in one class.
- `indexer.py`: file discovery, chunk normalization, embedding batching, sparse
  manifest lifecycle, collection writes, and incremental reconciliation are
  combined.
- `sparse.py`: analyzer, exact-anchor detection, BM25 manifest math, sparse
  encoding, and manifest persistence are domain-related but broad.
- `registry.py`: SQLite schema migration, repo registry, backend registry, role
  binding, and legacy cleanup are combined.

## 3) Non-Goals

Do not change retrieval behavior in this chore.

Out of scope:

- changing public MCP tool names;
- changing public Pydantic field names, defaults, or contract versions;
- replacing `SearchService` public methods;
- introducing graph retrieval;
- introducing graph lifecycle tools;
- adding rerank, ColBERT, tree-sitter, typed PPR, or SQL lineage;
- changing Qdrant collection schema;
- changing sparse vector math;
- changing lifecycle policy;
- adding automatic rebuild/reindex/update behavior;
- converting the whole test suite to a different testing style.

This chore must be boring in the best way: moved code, stronger seams, same
behavior.

## 5) Target Dependency Direction

The desired direction is:

```text
mcp_server
  -> application facades
       SearchService
       LifecycleService
       IndexStatusService
       ContextSearchService
  -> domain modules
       retrieval
       context
       status
       indexing
       lifecycle
       lexical
       graph
  -> ports
       ChunkStore
       ChunkSource
       SparseManifestRepository
       GraphStore
       GraphStatusProvider
       EmbeddingProvider
  -> infrastructure
       Qdrant
       SQLite
       filesystem
       git
```

Rules:

- MCP wrappers depend on application services, not on Qdrant or graph internals.
- Graph modules may depend on contracts, lexical helpers, and chunk/index reader
  ports.
- Graph modules must not depend on `SearchService`, MCP wrappers, or Qdrant
  payload internals.
- Retrieval may consume graph candidates later only through a branch/provider
  protocol.
- Status may consume graph status later through a `GraphStatusProvider`.
- Search paths should use a cheap readiness snapshot instead of full detailed
  status assembly once graph status exists.
- Qdrant client types should stay inside storage adapter modules where possible.

service needs a stable type boundary.

SQLite graph artifacts must also stay separate from registry storage. The repo
registry database may provide repo/profile identity and backend metadata, but
graph state will be a separate per-repo/profile artifact with its own schema and
migrations. Graph modules must not share registry tables, registry migrations,
or Qdrant payload internals.

## 8) Recommended Internal Protocols

Introduce protocols only when extraction needs them. Do not create empty
architecture objects for their own sake.

Useful protocol candidates:

```python
from dataclasses import dataclass
from typing import Iterable, Protocol


@dataclass(frozen=True, slots=True)
class FileIdentity:
    relative_path: str
    content_hash: str | None
    mtime: float | None


@dataclass(frozen=True, slots=True)
class IndexedChunk:
    chunk: ChunkRecord
    file_identity: FileIdentity


@dataclass(frozen=True, slots=True)
class ReadinessSnapshot:
    search_available: bool
    unavailable_codes: tuple[str, ...]
    dense_available: bool
    sparse_available: bool
    sparse_contract_compatible: bool
    stale_index: bool
    lifecycle_blocking: bool


@dataclass(frozen=True, slots=True)
class GraphStatusSummarySnapshot:
    available: bool
    state: str
    expansion_allowed: bool
    stale_path_count: int | None
    warning_codes: tuple[str, ...]


class RetrievalChunkStore(Protocol):
    def search(...): ...
    def search_sparse(...): ...
    def get_chunk(...): ...

class ChunkSource(Protocol):
    def iter_indexed_chunks(self, *, scope: str | None = None) -> Iterable[IndexedChunk]: ...
    def iter_file_chunks(self, relative_path: str) -> Iterable[IndexedChunk]: ...

class SparseManifestRepository(Protocol):
    def load(...): ...
    def save(...): ...

class ReadinessProvider(Protocol):
    def snapshot(self) -> ReadinessSnapshot: ...

class GraphStatusProvider(Protocol):
    def summary(self) -> GraphStatusSummarySnapshot: ...
```

The immediate value is not abstraction purity. The value is that P5 graph work
can plug into retrieval/status/context without importing implementation-heavy
modules or causing circular imports.

Graph builder/status code must not consume `QdrantStore.scroll_chunks()` or raw
Qdrant points directly. If indexed chunks are needed, they must come through a
typed `ChunkSource` or equivalent adapter that yields `ChunkRecord` plus file
identity/freshness metadata.

## 10) P5 Graph Readiness Criteria

P5.A graph artifact/status has a smaller prerequisite set than P5.B graph
retrieval expansion.

P5.A artifact/status can start after:

- lifecycle service extraction exists or has a clear small implementation plan;
- registry/SQLite separation is explicit;
- typed chunk source/reader boundary exists or is specified tightly enough for
  graph builder implementation;
- status readiness can accept a graph summary provider without full graph scans;
- contracts have a place for additive graph status models.

P5.B seed binding and graph expansion should wait until:

- `repo_context_search` assembly is outside the monolithic `SearchService`
  method body or has a clearly isolated assembler/service.
- retrieval branch execution has an explicit branch result type or equivalent
  seam;
- lexical exact-anchor analysis can be reused by graph seed binding;
- tests for search/status/context contracts are split enough that graph tests do
  not need to modify one massive file.

This does not mean every proposed package must be complete before P5. It means
the graph entry points must be obvious and boring, and P5.A should not be blocked
by refactors only needed for P5.B retrieval expansion.

## 11) Acceptance Criteria

For each chore implementation slice:

```text
1. py -m pytest -q passes.
2. No public MCP tool is renamed.
3. Legacy list-shaped tools keep their payload shape.
4. search_v2 contract remains stable.

7. Lifecycle operations do not run implicitly from status or search.
8. Existing import paths keep working through compatibility facades.
9. No graph retrieval behavior is introduced in this chore.
10. No graph implementation modules are scaffolded before P5.
```

## 12) Review Checklist

Reviewers should look for:

- over-large migration slices;
- accidental behavior changes hidden inside file moves;
- public Pydantic schema drift;
- import cycles between contracts, lexical, retrieval, and status;
- MCP registration side effects;
- full status scans on search paths;
- graph logic slipping into chore work;
- lifecycle orchestration remaining duplicated in MCP wrappers;
- graph code or status code consuming raw Qdrant points;
- Qdrant payload shape leaking into future graph modules;
- test moves that spread duplication instead of extracting helpers.

## 13) Immediate Next Step

The first implementation task after this spec should be small:

```text
P4.E.1
  -> add tests/helpers
  -> add model schema/default characterization tests
  -> add MCP wrapper signature/default characterization tests
  -> add import compatibility tests
  -> migrate the repo_context_search tests as the first coherent subset
  -> no production code extraction yet, unless needed for helpers
```

After that, move to early contract modules, then pure retrieval helpers. This
keeps the first chore commit low risk and gives later extraction slices a safer
test harness.
