# P5.D Rich Code Graph Edges

## 1) Purpose

P5.D makes the graph useful for everyday repository navigation by adding
structural code-aware edges on top of the P5.A graph artifact and the P5.B/P5.C
seed-bound expansion route.

The product goal is not "more graph data". The product goal is that a frontier
coding agent can ask a connected development question and receive grounded
context that would otherwise require several exact searches and file reads.

Target questions:

```text
where is this route implemented?
find tests for this endpoint
which docs/spec mention this handler or route?
what imports this module?
how does this config/env value reach runtime?
what code is affected by this policy/module context?
```

P5.D remains a retrieval substrate slice:

```text
dense+sparse retrieval
  -> strong seed pool
  -> graph binding
  -> bounded graph expansion over richer typed edges
  -> evidence paths
  -> repo_context_search envelope
```

The MCP still does not plan edits, generate final answers, summarize subgraphs,
or hide lifecycle operations.

## 2) Current Baseline

Already available after P5.A and P5.B/P5.C:

- SQLite graph artifact per repo/profile;
- `graph_status()`;
- `build_graph()` / `rebuild_graph()`;
- graph summary in `index_status.v2`;
- graph freshness and source-contract checks;
- read-only graph provider used by search;
- `repo_context_search(graph_mode="expand")`;
- seed binding by chunk/path/symbol/heading/selected terms;
- bounded expansion and graph branch fusion;
- evidence paths;
- fail-closed graph behavior for missing/stale/partial/building/error states.

Current graph nodes:

```text
file
chunk
symbol
doc_section
config_item
env_var
policy_scope
```

Current graph edges:

```text
file_contains_chunk
chunk_defines_symbol
file_contains_doc_section
chunk_mentions_path_or_symbol
config_defines_env
code_reads_env
doc_references_symbol      # contract-ready, not necessarily well populated
doc_references_config      # contract-ready, not necessarily well populated
policy_applies_to_path     # contract-ready, not necessarily well populated
```

Current graph extraction is intentionally conservative. It primarily uses chunk
metadata, Markdown headings, exact lexical scans, config/env heuristics, and
path/policy-like terms. It does not yet understand Python imports, routes,
tests, or docs-to-code references with enough structure.

## 3) Product Scope

P5.D adds the first production-useful package of richer code graph edges:

```text
Python import edges
basic route edges
basic test-target edges
docs-to-code/docs-to-route references
config/env extraction improvements
policy-to-path refinements
```

The priority order is:

1. Python imports and module/file ownership.
2. Route literals and route-to-handler ownership.
3. Test file/case to target module or symbol.
4. Markdown docs/spec references to code symbols, routes, paths, env vars, and
   config keys.
5. Config/env/policy polish that improves evidence quality without changing
   lifecycle or search contracts.

This slice should make these flows work in supported repositories:

```text
route -> handler chunk -> tests/docs
handler/module -> tests
docs/spec route mention -> runtime handler
module -> imports/imported-by context
env/config anchor -> runtime/deploy/docs context with better evidence
policy/module context -> affected paths
```

## 4) Non-goals

Do not implement these in P5.D:

- reranker;
- ColBERT/multivectors;
- tree-sitter as a required dependency;
- full call graph;
- full class hierarchy graph;
- whole-program dataflow;
- SQL lineage or migration graph;
- typed PPR;
- OpenIE triples;
- LLM-based extraction;
- hidden query planner or ReAct loop;
- automatic graph build/rebuild/update from search/status;
- default-enabled `graph_mode=auto`;
- graph expansion in legacy list-shaped tools;
- graph branch in `search_v2`;
- final-answer generation or GraphRAG summaries.

Tree-sitter, SQL lineage, richer framework-specific route extraction, and typed
PPR are later stages. P5.D should be useful without making any of them a
blocker.

## 5) Compatibility Contract

Public compatibility stays intact:

```text
semantic_search*
hybrid_search*
search_v2
find_similar_chunk
read_chunk
index_status
repo_context_search request shape
```

Only graph artifact content, graph diagnostics, and graph-based results inside
`repo_context_search` change.

Allowed additive public changes:

- add node/edge literal values used by evidence paths;
- add graph warning codes if needed;
- add graph diagnostics fields if they are optional and defaulted;
- add extractor coverage counts to `graph_status()` if optional/defaulted.

Not allowed:

- renaming existing tools;
- changing default `graph_mode`;
- changing `repo_context_search` contract version;
- exposing internal branch names such as `retrieval`;
- adding lifecycle side effects to search/status;
- changing legacy row shapes.

## 6) Node Contract Additions

Add these node types only if the implementation actually populates them:

```text
module
route
test_case
```

Defer:

```text
db_object
migration
callable_invocation
package
service
```

### 6.1 `module`

Represents an importable Python module or package-ish file owner.

Key:

```text
python.module.path
```

Payload:

```json
{
  "language": "python",
  "relative_path": "services/api/checkout_flow.py",
  "module_kind": "module | package",
  "import_root": "services"
}
```

Chunk mapping:

- primary chunk when the module is represented by a single file chunk;
- containing chunks for symbols defined in that file.

### 6.2 `route`

Represents a route literal or API endpoint pattern.

Canonical identity:

```text
route_kind + normalized_route + method_or_ANY
```

Examples:

```text
http|GET|/api/v1/connect
http|ANY|/api/v1/connect
telegram_bot|ANY|/start
miniapp|ANY|/connect
```

Rules:

- method-known handlers use method-specific route nodes;
- methodless docs/query mentions bind to the methodless `ANY` alias term and
  may expand to method-specific route nodes for the same normalized route;
- multi-method handlers create one method-specific node per method plus shared
  alias terms;
- GET and POST for the same path must not collapse into one handler identity;
- evidence paths must preserve both original surface and normalized route.

Payload:

```json
{
  "route_kind": "http | bot_handler | frontend_route | cli | unknown",
  "method": "GET",
  "framework": "fastapi | flask | django | aiogram | unknown",
  "normalized_route": "/api/v1/connect",
  "confidence": "high | medium | low"
}
```

HTTP method can be null when unknown. bot/frontend app routes should not pretend
to be HTTP routes.

Node terms:

```text
original surface:
  "/api/v1/connect"

normalized route:
  "/api/v1/connect"

method-qualified:
  "GET /api/v1/connect"

methodless alias:
  "ANY /api/v1/connect"
```

### 6.3 `test_case`

Represents a test function/class or a whole test file when function extraction is
not available.

Key:

```text
tests/test_checkout_flow.py::test_checkout_flow_happy_path
tests/test_checkout_flow.py
```

Payload:

```json
{
  "test_framework": "pytest | unittest | unknown",
  "target_inference": "path | symbol | import | naming | lexical",
  "confidence": "high | medium | low"
}
```

## 6.4 Chunk Projection Contract

Every node type that can be returned through graph expansion must have a
deterministic path back to indexed chunks.

Direct projection:

```text
chunk:
  graph_nodes.chunk_id = chunk id
  graph_node_chunks relation=primary

symbol:
  graph_nodes.chunk_id = defining chunk id
  graph_node_chunks relation=primary

doc_section:
  graph_nodes.chunk_id = section chunk id
  graph_node_chunks relation=primary

config_item:
  graph_nodes.chunk_id = defining chunk id when known
  graph_node_chunks relation=primary|containing

test_case:
  graph_nodes.chunk_id = test function/class chunk id when known
  graph_node_chunks relation=primary

route:
  graph_node_chunks relation=primary for defining route chunk when known
  graph_node_chunks relation=mention for docs chunks that mention the route
```

File projection:

```text
file:
  project through file_contains_chunk
  order by chunk_type priority, start_line, chunk_id
  cap per file projection before fusion
```

Required order for file node projection:

```text
1. symbol/route/test-bearing chunks
2. function/class chunks
3. markdown section chunks
4. generic chunks
5. file-start chunks
```

Edges that target file nodes must still produce real chunk results:

```text
file_imports_file:
  target file -> bounded file_contains_chunk projection

test_targets_file:
  target file -> bounded file_contains_chunk projection

doc_references_path:
  target file -> bounded file_contains_chunk projection
```

Acceptance tests must prove that file-target edges return real
`RepoContextResult` chunks, not just graph nodes.

## 7) Edge Contract Additions

Add these edge types:

```text
file_defines_module
module_imports_module
file_imports_file
route_defined_in_chunk
route_handled_by_symbol
test_targets_file
test_targets_symbol
doc_references_route
doc_references_path
doc_references_env
doc_references_config
```

Keep existing edge types.

Defer:

```text
symbol_calls_symbol
class_inherits_class
db_object_defined_by_migration
code_reads_table

```

### 7.1 Import Edges

```text
file_defines_module:
  file -> module

module_imports_module:
  module -> imported module

file_imports_file:
  file -> imported file when import resolves inside the indexed repo
```

Confidence:

```text
high:
  AST import resolved to an indexed file/module.

medium:
  AST import parsed but target module is not indexed or not resolvable.

low:
  lexical fallback only.
```

P5.D should populate `file_imports_file` only when resolution is deterministic.
Unresolved external imports may still create `module` nodes but should not flood
expansion. External imports are low-value for repo context and should be
excluded from expansion unless the query explicitly asks for dependency/package
context.

### 7.2 Route Edges

```text
route_defined_in_chunk:
  route -> chunk

route_handled_by_symbol:
  route -> symbol

doc_references_route:
  doc_section/chunk -> route
```

Confidence:

```text
high:
  direct decorator/call pattern recognized with route literal and handler symbol.

medium:
  route literal appears in a likely route/handler file.

low:
  route literal mention only.
```

Framework support in P5.D:

```text
FastAPI/Starlette-like decorators:
  @router.get("/path")
  @app.post("/path")
  router.add_api_route("/path", handler)

Flask-like decorators:
  @app.route("/path", methods=["GET"])
  @blueprint.route("/path")

Django-like path declarations:
  path("users/<id>/", view)
  re_path(...)

bot-framework/aiogram-ish handlers:
  Command("start")
  text/callback data literals when clearly handler-like

Generic fallback:
  slash-prefixed literals in files with route/api/handler/controller names.
```

Unsupported frameworks must degrade gracefully: route literal terms can still be
indexed, but no high-confidence handler edge should be fabricated.

### 7.3 Test Edges

```text
test_targets_file:
  test_case/test file -> file

test_targets_symbol:
  test_case -> symbol
```

Confidence:

```text
high:
  test imports the target symbol/module from repo code.

medium:
  path/name convention strongly maps tests/foo/test_bar.py to foo/bar.py or
  test_checkout_flow.py to checkout_flow.py.

low:
  lexical overlap only; do not create low-confidence graph edges by default.
```

P5.D should avoid noisy low-confidence test edges. If lexical-only test
association is needed, keep it as terms, not as `test_targets_*` edges.

### 7.4 Docs Reference Edges

```text
doc_references_symbol:
  doc_section/chunk -> symbol

doc_references_route:
  doc_section/chunk -> route

doc_references_path:
  doc_section/chunk -> file

doc_references_env:
  doc_section/chunk -> env_var

doc_references_config:
  doc_section/chunk -> config_item
```

Sources:

```text
Markdown links
inline code spans
fenced code blocks, bounded
route/env/path/config literals in prose
docs/spec headings and tables
```

Confidence:

```text
high:
  Markdown link or exact code span maps to indexed path/symbol/route/env.

medium:
  exact literal appears in docs and maps to a known graph term.

low:
  fuzzy prose overlap; do not create edge by default.
```

Docs edges must preserve evidence. A docs-to-code result should be able to show:

```text
seed docs/checkout-flow.md:12-20
  -> doc_references_route
  -> route:/api/v1/connect
  -> route_handled_by_symbol
  -> services/api/checkout_flow.py:...
```

### 7.5 Config/Env/Policy Refinements

Improve, but do not redesign, existing edges:

```text
config_defines_env
code_reads_env
policy_applies_to_path
doc_references_config
doc_references_env
```

P5.D should:

- better distinguish env definitions from env reads;
- avoid treating every uppercase token as an env var;
- attach config items from YAML/TOML/JSON/.env/compose paths;
- map policy modules/docs to paths only when path globs or exact path prefixes
  are present;
- store extractor source and confidence in edge payloads.

## 8) Extractor Architecture

Do not put all extraction logic into `graph/builder.py`.

Recommended package shape:

```text
services/repo_semantic/graph/
  extractors/
    __init__.py
    types.py
    python_imports.py
    python_routes.py
    tests.py
    markdown_refs.py
    config_refs.py
    policy_refs.py
```

The graph builder should orchestrate extractors and merge rows. Each extractor
should be deterministic, bounded, and testable on small fixtures.

### 8.1 Extractor Protocol

Use an internal protocol similar to:

```python
class GraphExtractor(Protocol):
    name: str
    version: str

    def extract(self, context: GraphExtractionContext) -> GraphExtractionRows:
        ...
```

Context should provide:

```text
repo_root
profile
chunks
chunks_by_path
known_files
known_symbols
known_routes
known_terms
include/exclude policy
```

Rows should be builder-neutral:

```text
nodes
node_terms
node_chunks
edges
file_errors
diagnostics
```

Extractor failures:

- must be isolated per file/extractor where practical;
- should mark affected extractor coverage as `partial` or `error`;
- must not crash the whole graph build unless the artifact would be corrupt;
- should surface bounded error codes in `graph_status()`.

### 8.2 Required vs Optional Extractors

P5.D must distinguish base graph readiness from optional rich-edge coverage.

Required base extraction:

```text
file nodes
chunk nodes
graph_node_chunks for chunks
file_contains_chunk edges
source index contract
metadata rows
```

If required base extraction fails or the artifact cannot be made internally
consistent:

```text
graph_status.state = partial | error
expansion_allowed = false
repo_context_search skips graph branch
```

Optional rich extractors:

```text
python_imports
python_routes
test_targets
markdown_refs
config_refs
policy_refs
```

If an optional extractor fails for one file:

```text
graph_status.state may remain ready when the base graph is valid
graph_status warning_codes includes the extractor warning
extractor_coverage marks file partial/error for that extractor
search may use other ready edge families
search must not use edge families marked failed for the affected file
```

This avoids permanently disabling all graph search because one Python file has a
syntax error or one Markdown file contains malformed reference text. Only base
graph corruption or source-contract incompatibility is search-blocking.

### 8.3 Ordering

Extractor order matters because some extractors need known nodes from earlier
passes:

```text
1. base file/chunk/symbol/doc/config/env extraction
2. Python module/import extraction
3. route extraction
4. test-target extraction
5. docs reference extraction
6. policy/config refinements
```

Docs reference extraction should run after symbols/routes/env/config nodes are
known so it can create typed reference edges rather than raw terms only.

### 8.4 Extractor Caps

Every extractor must have deterministic caps before retrieval-time graph caps.

Initial caps:

```text
python_imports:
  max import statements per file: 200
  max resolved file edges per file: 120
  max unresolved module nodes per file: 120

python_routes:
  max route literals per file: 120
  max handler edges per file: 120
  max generic lexical route candidates per file: 40

test_targets:
  max test_case nodes per file: 200
  max imported target edges per file: 160
  max naming-convention target edges per file: 20

markdown_refs:
  max code spans per chunk: 80
  max links per chunk: 80
  max route/env/config/path references per chunk: 120

config_refs:
  max config items per file: 200
  max env edges per file: 200

policy_refs:
  max path/policy edges per file: 160
```

If a cap is reached:

```text
emit bounded warning code:
  python_import_cap_reached
  python_route_cap_reached
  test_target_cap_reached
  markdown_ref_cap_reached
  config_ref_cap_reached
  policy_ref_cap_reached

preserve deterministic ordering before truncation
do not mark the whole graph error
```

Generated/vendor/build files should either be excluded before extraction or
processed with much lower caps.

### 8.5 No LLM Extraction

P5.D extractors are deterministic. Do not call an LLM, embedder, reranker, or
external parser service during graph build.

If an extractor cannot decide confidently, it should emit terms and diagnostics,
not fabricated edges.

## 9) Python Import Extraction

Use Python stdlib `ast` first.

For each Python file:

```text
parse AST
record module node for file
record import/import-from statements
resolve relative imports using package/file layout
resolve absolute imports to indexed repo files where possible
create module_imports_module edges
create file_imports_file edges only for resolved indexed files
```

Resolution rules:

```text
relative import:
  from .foo import bar
  from ..pkg import mod

absolute import:
  import services.api.checkout_flow
  from services.user.api import checkout_flow

candidate path:
  module/name.py
  module/name/__init__.py
```

The resolver must be conservative:

- no filesystem writes;
- no import execution;
- no Python path mutation;
- no importlib import of repo code;
- no resolving outside indexed repo paths.

Syntax errors:

- record `python_imports` extractor coverage as partial/error for that file;
- keep base chunk/file/symbol nodes if they are available;
- add extractor error code such as `python_ast_parse_failed`.
- do not make the whole graph search-blocking unless base graph extraction also
  failed.

## 10) Route Extraction

Route extraction should use AST where possible and lexical fallback only where
safe.

High-confidence AST patterns:

```text
@app.get("/path")
@router.post("/path")
@blueprint.route("/path", methods=["GET"])
router.add_api_route("/path", handler)
app.add_url_rule("/path", view_func=handler)
path("foo/", view)
re_path(r"^foo/$", view)
```

Medium-confidence lexical patterns:

```text
slash route literal appears in file path containing:
  api
  route
  routes
  router
  endpoint
  endpoints
  handler
  handlers
  controller
  views
```

Route normalization:

```text
strip duplicate slashes
keep leading slash for HTTP-like routes
normalize path parameters:
  {id}, <int:id>, :id -> {id}
preserve original surface in payload
preserve method if known
```

Do not normalize away meaningful API prefixes.

Route evidence should connect to:

- route node;
- defining chunk;
- handler symbol when known.

## 11) Test Target Extraction

Supported first:

```text
pytest-style test files:
  test_*.py
  *_test.py
  tests/**.py

unittest-style classes/functions:
  Test*
  test_*
```

Extraction steps:

```text
1. parse test file AST;
2. create test_case nodes for test functions/classes;
3. collect imports from repo modules;
4. map imported repo modules/files/symbols to targets;
5. apply naming convention fallback for target file;
6. create test_targets_file/test_targets_symbol edges only for high/medium confidence.
```

Naming convention examples:

```text
tests/test_checkout_flow.py -> services/**/checkout_flow.py when unique
tests/user/test_api.py -> services/user/**/api.py when unique
tests/services/user/test_checkout_flow.py -> services/user/**/checkout_flow.py
```

If multiple candidate target files exist and no import disambiguates them, do
not create a target edge. Store terms only.

Test-target extraction must not run tests or import code.

## 12) Markdown Docs Reference Extraction

For Markdown and docs-like text:

```text
extract inline code spans
extract Markdown links
extract relative file paths
extract route/env/config literals
extract dotted symbol-ish strings
extract fenced code blocks with bounds
```

Bounds:

```text
max code spans per chunk: 80
max links per chunk: 80
max fenced-code chars inspected per chunk: same as chunk text cap
```

Mapping:

```text
path literal -> file node when indexed path exists
route literal -> route node when known, otherwise term only
env var -> env_var node
config key -> config_item node when known
dotted symbol -> symbol node when exact key match exists
```

Do not create a docs edge from fuzzy symbol similarity. Exact or normalized term
match is required in P5.D.

## 13) Schema and Storage

Prefer preserving the current SQLite tables:

```text
graph_nodes
graph_node_terms
graph_node_chunks
graph_edges
graph_files
graph_metadata
```

P5.D should not require a graph schema migration unless absolutely necessary.

New node/edge types can be stored in existing text columns. Store richer
extractor-specific fields in `payload_json`.

If a migration is needed, it must be:

- additive;
- versioned through `GRAPH_SCHEMA_VERSION`;
- covered by compatibility tests;
- surfaced as `graph_schema_incompatible` until explicit rebuild.

Recommended `payload_json` fields for edges:

```json
{
  "confidence": "high | medium | low",
  "source": "ast | markdown_link | code_span | naming_convention | lexical",
  "extractor_version": "python_imports.v1",
  "surface": "...",
  "normalized": "...",
  "method": "GET",
  "framework": "fastapi",
  "target_resolution": "resolved | unresolved | ambiguous"
}
```

The scalar `confidence` column should remain numeric for sorting:

```text
high = 1.0
medium = 0.7
low = 0.4
```

Low-confidence edges should be rare. Prefer terms over low-confidence edges.

## 14) Extractor Versioning and Graph Contract

Every extractor must expose a stable name and version:

```text
python_imports.v1
python_routes.v1
test_targets.v1
markdown_refs.v1
config_refs.v1
policy_refs.v1
```

`GRAPH_EXTRACTOR_VERSIONS` must include all enabled extractors.

Changing extraction behavior that can change graph rows requires a version bump:

- new node/edge type emitted;
- changed confidence policy;
- changed route normalization;
- changed import resolution;
- changed test-target inference;
- changed docs reference mapping.

Graph status behavior:

```text
extractor version mismatch -> graph incompatible
search skips graph branch
explicit rebuild_graph recommended when graph was requested
```

No automatic rebuild.

## 15) Graph Status Additions

Additive optional fields may be added to detailed `graph_status()`:

```python
extractor_coverage: dict[str, ExtractorCoverage]
edge_type_counts: dict[str, int]
node_type_counts: dict[str, int]
warning_codes: list[str]
```

Suggested `ExtractorCoverage`:

```python
class ExtractorCoverage(BaseModel):
    files_seen: int = 0
    files_ready: int = 0
    files_partial: int = 0
    files_error: int = 0
    nodes_emitted: int = 0
    edges_emitted: int = 0
    warning_codes: list[str] = Field(default_factory=list)
```

Any optional `graph_status()` model additions must use stable defaults and
`default_factory` for mutable fields.

If adding this is too large for the first implementation, defer detailed
coverage but keep extractor versions and aggregate node/edge type counts.

`index_status.v2` should remain compact. Do not add full extractor coverage to
`index_status`; keep that in `graph_status()`.

## 16) Retrieval Behavior Impact

P5.D should improve graph branch candidates without changing the public search
route.

Graph provider changes:

- allow new edge types in expansion;
- update edge weights;
- preserve bounded expansion budgets;
- keep stale/non-ready graph fail-closed;
- keep evidence paths compact and grounded.

Recommended edge weights:

```text
route_handled_by_symbol: 1.10
route_defined_in_chunk: 1.00
test_targets_symbol: 0.95
test_targets_file: 0.85
file_imports_file: 0.75
module_imports_module: 0.65
doc_references_route: 0.90
doc_references_symbol: 0.85
doc_references_path: 0.80
doc_references_env: 0.85
doc_references_config: 0.80
policy_applies_to_path: 0.75
```

Existing weights stay as currently defined unless tests show they need a small
adjustment.

Expansion policy:

```text
route query:
  route -> handler symbol/chunk
  route -> docs references
  route -> tests when target edge exists

handler/module query:
  symbol/chunk -> test_targets_symbol/file incoming edges
  file/module -> imports/imported-by context when query asks "imports", "used by", or "dependencies"

docs/spec query:
  docs seed -> route/symbol/path/env/config node -> code chunks

test query:
  test seed -> target symbol/file -> runtime chunks
```

Do not let import edges dominate generic conceptual queries. Import graphs can
be high-degree and noisy. Use import edges primarily when:

- query mentions imports/dependencies/used by/module;
- seed is a module/file/symbol and target edge confidence is high;
- `graph_mode="expand"` is explicit.

### 16.1 Typed Expansion Templates

P5.D must not introduce arbitrary multi-hop graph traversal. It should add
explicit typed templates on top of the P5.B/P5.C bounded shared-node model.

Allowed templates:

```text
route_to_handler:
  seed chunk/symbol/doc -> route node
  route -> route_handled_by_symbol | route_defined_in_chunk
  project symbol/chunk to result chunk

route_to_tests:
  seed chunk/symbol/doc -> route node
  route -> route_handled_by_symbol | route_defined_in_chunk
  if handler target is symbol:
    incoming test_targets_symbol -> test_case
  if handler target is chunk:
    chunk -> containing file node
    incoming test_targets_file -> test_case/file
  if handler target is file:
    incoming test_targets_file -> test_case/file
  project test_case/file to result chunks

route_to_docs:
  seed chunk/symbol -> route node
  incoming doc_references_route -> doc_section/chunk
  project doc node to result chunk

docs_to_handler:
  if docs edge is doc_references_route:
    doc_section/chunk -> route node
    route -> route_handled_by_symbol | route_defined_in_chunk
    project handler symbol/chunk to result chunk
  if docs edge is doc_references_symbol:
    doc_section/chunk -> symbol node
    project symbol directly to defining chunk
  if docs edge is doc_references_path:
    doc_section/chunk -> file node
    project file through file_contains_chunk

module_import_context:
  if seed is module:
    module -> module_imports_module
    project imported module through owning file/chunks when resolvable
  if seed is file:
    file -> file_imports_file
    project imported file through file_contains_chunk
    optional file -> file_defines_module -> module_imports_module when module edge exists
  if seed is symbol/chunk:
    symbol/chunk -> containing file
    file -> file_imports_file
    project imported file through file_contains_chunk
  project target module/file to result chunks

module_imported_by_context:
  if seed is module:
    incoming module_imports_module -> importer module
    project importer module through owning file/chunks when resolvable
  if seed is file:
    incoming file_imports_file -> importer file
    project importer file through file_contains_chunk
  if seed is symbol/chunk:
    symbol/chunk -> containing file
    incoming file_imports_file -> importer file
    project importer file through file_contains_chunk
  project importer module/file to result chunks

test_to_runtime:
  seed test_case/chunk -> test_targets_symbol | test_targets_file
  project target symbol/file to result chunks
```

Template limits:

```text
max typed templates per request: 4
max pivots per template: 40
max support edges per pivot: 20
max projected chunks per template: 80
max total rich-edge projections: current graph projection budget
max evidence steps: 5
```

Traversal rules:

- every template starts from a bound seed node;
- every intermediate node type and edge type must match the template;
- no template can continue after projecting result chunks;
- no template can chain into another template recursively;
- all candidates pass normal `repo_context_search` filters;
- capped templates emit diagnostics such as `graph_template_cap_reached`.

Evidence path rules:

```text
route_to_handler evidence:
  seed chunk
  -> route edge
  -> route node
  -> handler edge
  -> handler symbol/chunk

route_to_tests evidence:
  seed chunk
  -> route node
  -> handler symbol/chunk
  -> containing file bridge when target is file-based
  -> incoming test_targets_symbol/test_targets_file edge
  -> test_case/file/chunk

docs_to_handler evidence:
  seed docs chunk
  -> doc_references_route or doc_references_symbol
  -> route node plus handler edge, or direct symbol node
  -> runtime chunk

module_import_context evidence:
  seed chunk/file/module
  -> containing file/module bridge when needed
  -> file_imports_file or module_imports_module
  -> imported file/module
  -> projected result chunk
```

### 16.2 Edge Policy Matrix

The graph provider must decide which new edge families are traversable based on
query intent, `graph_mode`, seed type, and edge confidence.

Initial policy:

```text
route edges:
  graph_mode=expand:
    allow high/medium confidence when route literal, endpoint, handler, docs,
    tests, or implementation intent is present.
  graph_mode=auto with flag enabled:
    allow only with route literal or endpoint/handler relationship intent.

test edges:
  graph_mode=expand:
    allow high/medium confidence when query mentions tests or the seed is a
    route/handler/module and relationship intent asks for tests.
  graph_mode=auto with flag enabled:
    allow only when query explicitly says tests/test coverage.

docs edges:
  graph_mode=expand:
    allow high/medium confidence when query mentions docs/spec/policy/guide or
    seed is docs and target is code.
  graph_mode=auto with flag enabled:
    allow only with docs/spec relationship intent.

import edges:
  graph_mode=expand:
    allow high confidence by default only for import/dependency/module/used-by
    intent; allow medium only with explicit import/dependency intent.
  graph_mode=auto with flag enabled:
    allow only with explicit import/dependency intent.

config/env/policy edges:
  follow existing P5.B/P5.C behavior, with high/medium confidence only.
```

Tests must prove that import edges do not flood route/docs/test queries and that
explicit import/dependency queries can use import edges.

## 17) Auto Mode Policy

P5.D still does not enable `graph_mode=auto` by default.

The existing compatibility flag remains:

```text
SEMANTIC_MCP_REPO_CONTEXT_GRAPH_AUTO_ENABLED=false
```

P5.D may add better deterministic auto triggers for future use, but they remain
inactive unless the flag is true.

New positive triggers when the flag is true:

```text
route literal + relationship intent
"handler for"
"tests for"
"docs for"
"where is this endpoint implemented"
"what imports"
"where used" with module/symbol/file seed
"spec for this route"
```

Suppression:

```text
plain exact path lookup
plain symbol lookup with one strong sparse hit
no graph-ready status
import expansion without import/dependency intent
test expansion with ambiguous target inference only
```

## 20) High-degree and Noise Controls

New edges increase graph density. P5.D must preserve boundedness.

Controls:

```text
max_graph_seed_chunks = current value
max_graph_seed_pool = current value
max_neighbors_per_seed_node = current value or lower for import nodes
max_graph_edge_projections = current value
max_graph_chunk_projections = current value
max_evidence_paths_per_result = current value
```

Additional controls:

```text
import edges:
  apply lower expansion weight by default;
  skip external/unresolved import edges for candidate projection;
  cap imported-by expansions more aggressively than route/test expansions.

route edges:
  prefer exact route surface/canonical matches;
  penalize generic route fragments such as "/" or "/health" unless exact query
  asks for them.

test edges:
  do not emit low-confidence lexical-only edges;
  skip ambiguous naming inference.

docs edges:
  ignore generic links to README/index unless exact path query asks for them.
```

Generated/vendor/build paths:

- continue excluding or penalizing as seed paths;
- do not create high-confidence edges from generated files unless file metadata
  explicitly says they are indexable source files.
