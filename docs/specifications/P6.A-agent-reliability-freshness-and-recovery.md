# P6.A: Agent Reliability, Precise Freshness, and Safe Recovery

Status: draft specification.

## 1) Purpose

This slice turns `repo-semantic-search` from a powerful retrieval MCP into a
reliable agent-facing development tool.

The main product goal is:

```text
A frontier coding agent should be able to depend on repo-semantic-search during
normal development without repeatedly asking the user to restart, rebuild, or
diagnose the MCP by hand.
```

The MCP must still keep lifecycle boundaries explicit. Search/status must never
silently rebuild an index or graph. But the system should distinguish expensive
or destructive lifecycle operations from safe recovery operations that an agent
can run by itself.

This spec focuses on:

- precise freshness detection;
- safe agent recovery;
- watcher startup reconciliation;
- transport resilience for Codex chats;
- graph degraded-mode availability;
- rebuild avoidance;
- e2e dogfood checks.

## 2) Background

Recent dogfood on a large private backend/control-plane repository exposed reliability gaps that are more damaging
than missing retrieval features:

1. A Codex chat could lose direct MCP access after container restart and report
   `Transport closed` or `tool implementation not available`.
2. `watcher.enabled=true` did not mean `watcher.running=true`, and agents could
   not always tell whether live indexing was active.
3. The watcher did not clearly own the "catch up files changed while I was
   stopped" use case.
4. `index_stale=true` mixed together very different states: harmless commit
   drift, dirty worktree, actual unindexed paths, sparse stats drift, graph
   source mismatch, and blocking contract mismatches.
5. Graph expansion was disabled for a soft source index contract mismatch even
   when the graph was built for the same commit and there were no stale paths.
6. Agents often proposed full rebuilds too early, even when startup reconcile or
   local exact verification would have been enough.

The current working tree already contains first fixes for several of these
issues:

- host-side stdio proxy for Codex transport resilience;
- HTTP tool-call fallback script;
- watcher startup reconcile;
- explicit watcher status fields;
- graph degraded mode for non-blocking source index mismatch.

This spec defines the full contract these fixes should grow into.

## 3) Product Principles

### 3.1 Agent-first readiness

The primary user is not an operator reading dashboards. The primary user is a
coding agent trying to gather repository context before editing code.

The agent needs stable answers to:

- Can I search now?
- Can I use graph expansion now?
- Are results fresh enough for context discovery?
- Which paths need exact verification?
- What can I safely fix myself?
- What requires explicit user permission?

### 3.2 Repair-first, rebuild-last

Auto-recovery must be repair-first and rebuild-last.

Allowed safe recovery actions should be tried before any rebuild is recommended:

```text
check backend
check readyz
reconnect through host proxy
start watcher
run watcher startup reconcile
retry status/search
fall back to HTTP tool call
use degraded graph mode when safe
recommend exact rg verification
```

Rebuilds are expensive, can hide real freshness bugs, and may disrupt other
agents. They must not be the default answer to `stale=true`.

### 3.3 Search availability is separate from freshness

`search_available=true` means the retrieval substrate can answer queries.

It does not mean:

- the working tree has no local changes;
- exact identifiers do not need verification;
- sparse corpus statistics are perfectly current;
- graph expansion is fully fresh.

Freshness must be reported as a separate, typed policy surface.

### 3.4 Stale must be precise

The MCP should not use one vague stale flag for every state. Agents need stable
codes and severity.

Commit mismatch is not enough to decide that search is unsafe. The more useful
question is:

```text
Which indexable paths differ from their indexed content state?
```

### 3.5 Status/search do not perform lifecycle

This remains a hard compatibility boundary:

- `index_status`
- `graph_status`
- `repo_context_search`
- legacy search tools

must not start watcher, rebuild index, rebuild graph, switch backend, or switch
repo by themselves.

Safe recovery belongs in explicit agent helper tools/scripts, not hidden inside
status/search.

## 4) Scope

This spec covers:

- freshness taxonomy and status fields;
- per-path index manifest requirements;
- watcher startup reconcile semantics;
- graph degraded freshness semantics;
- safe recovery policy;
- agent-facing `ensure_ready` helper;
- transport fallback behavior;
- e2e reliability checks.

This spec does not cover:

- new retrieval ranking features;
- reranker or ColBERT;
- tree-sitter extraction;
- graph schema expansion beyond current graph edges;
- automatic full rebuilds;
- hidden agent loops inside MCP;
- final-answer generation.

## 5) Definitions

### 5.1 Safe recovery action

A safe recovery action is non-destructive, bounded, and does not change model,
profile, schema, repo identity, or backend identity.

Examples:

- check `/readyz`;
- retry a failed call;
- connect through host-side stdio proxy;
- use HTTP fallback tool call;
- start watcher for the already active repo;
- run startup reconcile for changed paths;
- refresh registry state;
- mark soft graph stale as degraded if expansion is allowed.

### 5.2 Permissioned lifecycle action

A permissioned lifecycle action can be expensive, destructive, or change the
active retrieval contract.

Examples:

- `build_index`;
- `rebuild_index`;
- `build_graph`;
- `rebuild_graph`;
- backend switch;
- runtime switch;
- active repo switch;
- collection deletion;
- schema migration.

Agents must not run these without explicit user permission.

### 5.3 Freshness state

Freshness is the relationship between:

- source working tree;
- git HEAD;
- indexed path manifest;
- Qdrant collections;
- sparse manifest;
- graph artifact;
- runtime/backend contract.

Freshness is not a single boolean.

## 6) Freshness Taxonomy

Add a typed freshness summary to `index_status.v2`.

Recommended states:

```python
FreshnessState = Literal[
    "fresh",
    "soft_stale",
    "path_stale",
    "graph_degraded",
    "sparse_stats_stale",
    "contract_stale",
    "blocking_stale",
    "unknown",
]
```

These states are not mutually exclusive. Status should expose:

```python
class FreshnessSummary(BaseModel):
    primary_state: FreshnessState
    states: list[FreshnessState]
    reason_codes: list[str]
    path_coverage_complete: bool
    exact_verification_recommended: bool
```

`primary_state` is the highest-severity state according to the precedence in
section 6.9. `states` and `reason_codes` preserve every contributing condition
so agents do not lose diagnostic detail.

### 6.1 `fresh`

Use when:

- indexed repo root matches active repo root;
- current backend/index contract is compatible;
- no known indexable path differs from indexed content;
- graph is ready or graph is absent but not required;
- watcher state does not imply missing updates.

### 6.2 `soft_stale`

Use when search is allowed and no concrete stale paths are known, but the agent
should verify exact anchors.

Examples:

- git HEAD differs from indexed HEAD, but indexed path hashes still match;
- worktree is dirty but changed files are non-indexable;
- sparse stats are old but sparse branch remains usable;
- graph source index counts differ after an incremental update but no affected
  paths are stale.

### 6.3 `path_stale`

Use when specific indexable paths are known to differ from indexed content.

Examples:

- modified file content hash differs from path manifest;
- new indexable file is untracked and not indexed;
- deleted indexed file still has points;
- watcher startup reconcile failed for one or more paths.

`path_stale` should not automatically imply full rebuild. The preferred recovery
is incremental reconcile for the affected paths.

### 6.4 `graph_degraded`

Use when dense/sparse search is available and graph expansion is allowed, but
graph diagnostics require warnings.

Examples:

- `graph_source_index_contract_mismatch` caused by incremental index count
  drift;
- graph is globally stale but no seed paths are invalidated;
- optional graph extractor warnings exist.

Graph degraded mode must be visible in `repo_context_search.diagnostics`.

### 6.5 `sparse_stats_stale`

Use when BM25 document frequencies or sparse corpus stats are stale after
incremental changes.

Search remains available. Sparse branch remains available if vectors and
contracts are compatible. The status should recommend explicit rebuild when
convenient, but not block agent work.

Status should distinguish minor corpus-stat drift from incompatible sparse
state:

- minor document-frequency drift after bounded incremental updates:
  `sparse_stats_stale`, search allowed;
- sparse vocabulary/manifest/hash mismatch: `contract_stale` or
  `blocking_stale`;
- large delete/reindex churn beyond configured drift thresholds: warning plus
  explicit rebuild recommendation, but still permission-required.

### 6.6 `contract_stale`

Use when an index or graph artifact was built with an older but possibly
compatible contract.

This may be non-blocking or blocking depending on the mismatch:

- compatible old optional fields: warning;
- incompatible schema/model/profile: blocking.

### 6.7 `blocking_stale`

Use when search must not be trusted for semantic retrieval.

Examples:

- embedding model mismatch;
- embedding dimension mismatch;
- collection missing or corrupt;
- incompatible schema version;
- active repo mismatch;
- backend switch required;
- lifecycle operation currently mutating collections.

### 6.8 `unknown`

Use when the MCP cannot safely inspect git, filesystem, registry, or collection
state.

Search may remain available, but the agent should treat results as low
confidence and verify exact anchors before editing.

### 6.9 Primary state precedence

When multiple freshness states apply, use this primary-state precedence:

```text
blocking_stale
  > unknown
  > contract_stale
  > path_stale
  > graph_degraded
  > sparse_stats_stale
  > soft_stale
  > fresh
```

Detailed `states` and `reason_codes` must still include all contributing states.

Examples:

- `path_stale + sparse_stats_stale` -> primary `path_stale`;
- `contract_stale + graph_degraded` -> primary `contract_stale`;
- `unknown + path_stale` -> primary `unknown`;
- clean manifest plus sparse corpus drift -> primary `sparse_stats_stale`.

### 6.10 Agent decision matrix

Status responses must expose enough policy for an agent to decide without prose
parsing.

| Primary state | May search | May use graph | Agent may auto-recover | Must exact-verify before edit | Must ask user |
| --- | --- | --- | --- | --- | --- |
| `fresh` | yes | if `expansion_allowed` | no | for exact anchors only | no |
| `soft_stale` | yes | if `expansion_allowed` | start watcher/reconcile if applicable | yes | no |
| `path_stale` | yes, with warnings | only if stale paths do not overlap seed or expanded paths | bounded incremental reconcile | yes, especially stale paths | only if reconcile exceeds bounds or fails |
| `graph_degraded` | yes | yes, degraded | no rebuild | yes for graph evidence paths | no |
| `sparse_stats_stale` | yes | unchanged | no | normal exact-anchor policy | no |
| `contract_stale` non-blocking | yes, with warnings | only if graph compatible | no | yes | no |
| `blocking_stale` | no semantic search | no | diagnostics/fallback only | n/a | yes for lifecycle action |
| `unknown` | maybe, low confidence | no unless explicitly allowed | diagnostics only | yes; prefer `rg` and file reads | ask only if status cannot be recovered |

## 7) Path Manifest

Precise stale detection requires a path manifest.

Persist at least:

```text
repo_id
normalized_repo_root
git_common_dir
git_worktree_dir
index_profile
include_rules_hash
exclude_rules_hash
doc_prefixes_hash
manifest_schema_version
hash_algorithm
relative_path
path_casefold_key
scope
file_kind              # regular | symlink | submodule | other
content_hash
source_mtime
file_size
indexed_at
index_revision
index_epoch
collection_generation
chunk_count
point_ids
chunker_contract_id
dense_contract_id
sparse_contract_id
index_state       # ready | missing | stale | deleted | error | excluded
last_verified_at
delete_confirmed_at
last_error_code
last_error_detail
```

The manifest can live in the existing registry SQLite database or a dedicated
artifact. It should be updated by full index builds and incremental reconcile.

`source_mtime` and `file_size` are optimization hints only. Content hash,
contract ids, path identity, and persisted manifest state are the authority.

### 7.1 Stale path detection

For each indexable path discovered in the working tree:

```text
if not in manifest:
  state = missing
elif content_hash differs:
  state = stale
elif manifest.index_state == error:
  state = error
else:
  state = ready
```

For each manifest path missing from disk:

```text
state = deleted
```

Status should expose:

```python
class PathFreshnessSummary(BaseModel):
    coverage_complete: bool
    coverage_error_code: str | None
    changed_indexable_paths_count: int
    untracked_indexable_paths_count: int
    missing_from_index_count: int
    stale_indexed_paths_count: int
    deleted_indexed_paths_count: int
    path_error_count: int
    stale_paths_preview: list[str]
    deleted_paths_preview: list[str]
    error_paths_preview: list[str]
```

### 7.2 Authoritative coverage

A path freshness result may be reported as clean only when the manifest is
authoritative for the active repo identity, profile, include/exclude policy, doc
prefix policy, backend/index contract, and the filesystem scan completed without
timeout or read errors.

If path freshness cannot prove coverage, use primary state `unknown` with
warning code `path_freshness_incomplete`. Do not downgrade commit mismatch to
`soft_stale` from an incomplete manifest.

### 7.3 Deleted path rules

For deleted indexed paths, successful recovery requires both:

- all Qdrant points for the relative path are deleted from every scope;
- manifest state is persisted as deleted with `delete_confirmed_at`.

Until both are true, the path contributes to `path_stale`.
`repo_context_search` must omit known stale/deleted path results or return a
blocking warning for those result paths.

### 7.4 Commit mismatch policy

Commit mismatch should be reported, but it should not be the only stale
decision.

Recommended policy:

```text
commit mismatch + authoritative clean path scan -> soft_stale
commit mismatch + incomplete path coverage -> unknown
commit mismatch + stale paths -> path_stale
commit mismatch + contract mismatch -> contract_stale/blocking_stale
```

### 7.5 Path manifest storage decision

Decision for v1: the path manifest lives in a dedicated per-index SQLite
artifact, not in the main registry SQLite database.

The registry database remains control-plane state. It may store small manifest
metadata such as artifact path, manifest schema version, current index epoch,
current collection generation, summary counts, and lifecycle lease/audit state.
It must not store per-path manifest rows.

The path manifest artifact is data-plane/index state. It is part of the index
artifact set together with Qdrant collections, sparse manifests, and the graph
artifact. Its identity must include:

- repo id / repo key;
- normalized repo root;
- git common dir;
- git worktree dir;
- index profile;
- embedding backend/model/schema contract;
- chunker contract;
- include/exclude/doc-prefix policy hashes;
- Qdrant collection names and collection generation for every scope.

A path manifest is authoritative only when this identity matches the active
repo, active profile, active backend/index contract, include/exclude policy,
doc-prefix policy, and readable Qdrant collections.

Recommended artifact location:

```text
<registry_state_dir>/path_manifests/<repo_key_slug>/<profile_slug>/path_manifest_v<manifest_schema_version>.sqlite3
```

The exact path may change, but it must be deterministic from repo/profile/index
identity and recorded in registry summary metadata.

Concurrency requirements:

- all writes to the manifest run under the repo/profile/backend index mutation
  lease;
- the SQLite manifest should use WAL mode and a bounded busy timeout;
- status/search diagnostics may read snapshots while a writer is active, but
  paths currently being mutated, or paths whose mutation state cannot be proven,
  are not clean;
- different profiles use separate manifest artifacts and Qdrant collections;
- a single repo/profile/backend identity has at most one writer.

Crash consistency:

- the manifest must never claim Qdrant contains fresh points before Qdrant
  mutation succeeds;
- a path is marked ready only after old points are removed as needed, new points
  are upserted, and the manifest transaction commits the new content hash,
  point ids, chunk count, contracts, index revision, index epoch, and collection
  generation;
- a path is marked deleted only after all Qdrant points for that relative path
  are deleted from every affected scope and the manifest transaction commits
  `index_state=deleted` with `delete_confirmed_at`;
- if a process crashes after Qdrant mutation but before manifest commit, the
  next status/reconcile may report `path_stale` or `unknown`, but must not
  report a false clean state.

Compatibility:

- existing indexes without a path manifest remain searchable if their Qdrant
  collections are otherwise compatible;
- path freshness coverage is incomplete until the manifest exists;
- status must set `path_coverage_complete=false` and reason code
  `path_manifest_missing` or `path_manifest_incomplete`;
- status must not convert commit mismatch to `soft_stale` without an
  authoritative manifest;
- creating or migrating the manifest is an explicit lifecycle/artifact action,
  not a hidden side effect of status or search.

Portable index backup consists of Qdrant collections, path manifest artifact,
sparse manifests, graph artifact if present, and minimal registry metadata. If
an index is restored under a different absolute repo root or worktree path, the
manifest is not authoritative until an explicit rebind/migration verifies the
new normalized repo root and git worktree dir.

Git worktrees sharing the same git common dir must not share one authoritative
path manifest unless they are the same normalized worktree root.

## 8) Watcher Reconcile Semantics

The watcher has two responsibilities:

1. startup reconcile;
2. live event polling.

### 8.1 Startup reconcile

When `start_watcher` is explicitly called, it must first reconcile paths changed
while the watcher was stopped.

Required behavior:

```text
1. acquire the repo/profile/backend index mutation lease
2. capture scan_started_at and current filesystem snapshot
3. compare snapshot against path manifest / registry state
4. reindex stale or missing paths incrementally
5. remove points for deleted indexed paths
6. capture a post-reconcile snapshot
7. if any path changed between snapshots, run one bounded second pass
8. start live polling with the post-reconcile snapshot as watcher baseline
9. record index revision only if all required paths are ready/deleted-confirmed
   and paths_failed == 0
```

`start_watcher` must not full rebuild.

If the mutation lease cannot be acquired, `start_watcher` must stop before
mutation and return `start_blocked_reason="index_mutation_in_progress"`.

`start_watcher` response should include:

```python
class StartupReconcileSummary(BaseModel):
    ran: bool
    paths_scanned: int
    paths_reindexed: int
    paths_deleted: int
    paths_failed: int
    max_paths_scanned: int | None
    max_paths_reindexed: int | None
    max_points_deleted: int | None
    max_duration_ms: int | None
    bounds_exceeded: list[str]
    mutation_started: bool
    changed_code_paths: int
    changed_docs_paths: int
    duration_ms: int
    warning_codes: list[str]
```

### 8.1.1 Safe reconcile bounds

Startup reconcile is permissionless only when all preconditions hold:

- active repo root equals requested repo root;
- active profile/backend/model/schema match the indexed contract;
- no build/rebuild/drop/migration operation is in progress;
- a repo/profile/backend mutation lease is acquired;
- changed paths are path-level deltas, not contract changes;
- planned deletes affect only manifest paths missing from disk.

If any configured bound is exceeded, `start_watcher` must stop before mutation
and return a permission-required recommended action.

Default dogfood bounds should be conservative and configurable. Bounds protect
against accidental branch switches, policy changes, or broad filesystem churn
being mistaken for a small incremental repair.

### 8.1.2 Default dogfood reconcile bounds

For v1 dogfood, startup reconcile is permissionless only when the planned
mutation stays within these default bounds:

```text
max_reconcile_paths = 250
max_deleted_paths = 100
max_points_deleted = 5000
max_duration_ms = 180000
max_scan_paths = 50000
```

`max_reconcile_paths` counts changed or missing indexable paths that would be
reindexed. `max_deleted_paths` counts indexed manifest paths missing from disk.
`max_points_deleted` counts all dense/sparse points planned for deletion across
collections. `max_duration_ms` is a wall-clock bound for the whole startup
reconcile operation. `max_scan_paths` is a guardrail for pathological scans; it
must not be used as a substitute for changed-path bounds.

If any bound is exceeded, `start_watcher` must stop before mutation and return a
permission-required recommended action with reason code
`startup_reconcile_bounds_exceeded`. Bounds exceeded are not by themselves a
rebuild reason.

The bounds must be configurable:

```text
SEMANTIC_MCP_RECONCILE_MAX_PATHS
SEMANTIC_MCP_RECONCILE_MAX_DELETED_PATHS
SEMANTIC_MCP_RECONCILE_MAX_POINTS_DELETED
SEMANTIC_MCP_RECONCILE_MAX_DURATION_MS
SEMANTIC_MCP_RECONCILE_MAX_SCAN_PATHS
```

Profiles may override these defaults, but status and reconcile responses must
echo the effective values used for the decision.

### 8.2 Live polling

After startup reconcile, watcher continues polling for future changes.

Each successful incremental update should:

- upsert changed chunks;
- delete stale points for changed/deleted files;
- update path manifest;
- update indexed revision only when policy says the whole observed tree is
  caught up;
- mark sparse stats stale if corpus stats are not fully recomputed.

### 8.3 Watcher status

`index_status.v2.watcher` should expose:

```python
class WatcherStatusSummary(BaseModel):
    enabled: bool
    running: bool
    runtime_available: bool
    autostart_policy: Literal["manual", "backend_start", "disabled"]
    start_required: bool
    start_blocked_reason: str | None
    last_event_at: str | None
    last_error: str | None
    last_incremental_update_ts: str | None
    startup_reconcile_last: StartupReconcileSummary | None
```

### 8.3.1 Watcher autostart policy

Default community policy is `manual`.

Dogfood profiles may opt into `backend_start`, but only as backend startup
policy. `backend_start` means:

- runtime bootstrap completed;
- active repo/profile/backend identity already matches configured target;
- repo is indexed;
- search is available;
- startup path may call `start_watcher`, which first runs bounded startup
  reconcile.

Status and search tools must never autostart watcher.

### 8.4 Lifecycle lease and index epoch

All index mutations for the same repo/profile/backend contract must use a single
repo-scoped lifecycle lease. This includes:

- `build_index`;
- `rebuild_index`;
- `reindex_paths`;
- startup reconcile;
- watcher polling updates;
- graph updates that consume index state.

`index_status.v2.lifecycle` should expose:

```python
class LifecycleStatus(BaseModel):
    action_in_progress: bool
    operation_id: str | None
    owner: str | None
    phase: str | None
    index_epoch: int | None
    mutating_paths_preview: list[str]
```

Search remains available during narrow per-path incremental updates only when
known stale/deleted paths can be filtered from results. Search is blocked during
collection rebuild, schema migration, collection deletion, or unknown mutation
state.

### 8.5 Lease crash recovery and idempotency

The lifecycle lease must be resilient to process crashes and agent retries.

Lease metadata should include:

```python
class LifecycleLease(BaseModel):
    lease_id: str
    repo_id: str
    profile: str
    backend_contract_id: str
    owner: str
    operation_id: str
    fencing_token: int
    acquired_at: str
    heartbeat_at: str
    expires_at: str
    phase: str
    mutating_paths_preview: list[str]
```

Requirements:

- every index mutation writes with the current `fencing_token`;
- stale leases may be recovered only after `expires_at` and after verifying the
  owner process/container is no longer active;
- lease recovery must be recorded in the lifecycle audit log;
- repeated `start_watcher` or `ensure_ready` calls with the same idempotency key
  should return the existing operation result/status instead of starting a
  duplicate mutation;
- retry after transport failure must be safe: agents can repeat safe recovery
  calls without causing duplicate rebuilds, duplicate deletes, or split-brain
  manifest/Qdrant state.

## 9) Agent Recovery Policy

The MCP should expose recovery hints that are directly usable by coding agents.

Each recommended action should include:

```python
class RecommendedAction(BaseModel):
    code: str
    action_id: str | None = None
    idempotency_key: str | None = None
    severity: Literal["info", "warning", "error", "blocking"]
    title: str
    detail: str | None = None
    reason_codes: list[str] = []
    safe_auto_run: bool = False
    requires_user_permission: bool = True
    destructive: bool = False
    expensive: bool = False
    retryable: bool = True
    preconditions: list[str] = []
    stop_if: list[str] = []
    max_attempts: int = 1
    timeout_ms: int | None = None
    expected_result: str | None = None
    after_success: list[str] = []
    after_failure: list[str] = []
    permission_prompt: str | None = None
    tool_hint: str | None = None
    argv_hint: list[str] | None = None
    host_command_hint: list[str] | None = None
```

### 9.1 Safe auto-run actions

These may be run by an agent without asking the user when the active repo and
profile already match and the action preconditions hold:

```text
check_readyz
retry_status
use_http_fallback
start_watcher
run_startup_reconcile
refresh_registry_status
retry_repo_context_search
run_local_rg
```

`run_local_rg` is safe only as a read-only exact verification step.

`start_watcher` and `run_startup_reconcile` are safe auto-run actions only when
the repo/profile/backend identity matches, no lifecycle mutation is active, and
the reconcile plan stays inside configured bounds. Otherwise they become
permission-required or blocked actions.

### 9.2 Permission-required actions

These must require explicit user permission:

```text
build_index
rebuild_index
build_graph
rebuild_graph
activate_repo
switch_backend
switch_runtime
drop_collections
schema_migration
```

### 9.3 Rebuild recommendation criteria

Recommend rebuild only for strict reasons:

```text
embedding model/profile mismatch
embedding dimension mismatch
schema mismatch
collection missing/corrupt
sparse vocabulary/manifest incompatible
too many incremental reconcile errors
explicit user request
```

Do not recommend rebuild merely because:

- watcher is stopped;
- sparse stats are stale;
- graph is degraded but expansion allowed;
- git HEAD differs but path manifest is clean;
- worktree is dirty with exact verification available.

When a rebuild is recommended, the action must include:

```python
rebuild_reason_codes: list[str]
alternatives_attempted: list[str]
alternatives_blocked: list[str]
estimated_cost: Literal["low", "medium", "high", "unknown"]
user_permission_required: bool = True
```

### 9.3.1 Repeated reconcile failure threshold

In v1, `too_many_incremental_reconcile_errors` is emitted only after three
consecutive bounded incremental reconcile attempts fail for the same
repo/profile/backend contract and same index epoch, with no successful progress
between attempts.

A reconcile attempt counts as progress when at least one stale, missing,
deleted, or error path becomes `ready` or `deleted_confirmed`, or when total
stale/deleted/error path count decreases.

The first failed attempt should return a warning or error with safe retry
guidance. The second consecutive failed attempt should return an error and at
most one more safe retry if the plan remains inside bounds. The third
consecutive failed attempt with no progress may return a permission-required
`rebuild_index` recommendation.

Path-local source failures such as permission denied, decode errors,
file-too-large, file deleted during scan, or files that are still actively
changing must not count as rebuild evidence unless a rebuild can plausibly
repair the condition. Keep those as `path_stale` or `unknown` diagnostics with
exact verification guidance.

A rebuild recommendation from repeated reconcile failures must include:

```text
rebuild_reason_codes = ["too_many_incremental_reconcile_errors"]
alternatives_attempted includes each reconcile attempt id
alternatives_blocked explains remaining failed paths or index-write failures
safe_auto_run = false
requires_user_permission = true
expensive = true
```

Rebuild must never be executed automatically by status, search, watcher startup,
or ensure-ready safe-recover mode.

### 9.4 User permission prompt contract

For permission-required lifecycle actions, recommended actions must include a
concise permission prompt.

The prompt must include:

- exact action;
- repo root;
- stable blocking reason codes;
- why safe recovery is insufficient;
- whether the action is expensive or destructive;
- expected user-visible impact.

Example:

```text
Search is blocked for C:\repo because embedding_dimension_mismatch and
schema_mismatch cannot be repaired incrementally. I already checked backend
readiness and watcher reconcile is not applicable. May I run rebuild_index for
this repo? This is expensive and will rewrite the index collections.
```

### 9.5 Recovery audit and secret redaction

Safe recovery and permissioned lifecycle actions must write an append-only audit
record. This is needed for debugging, no-rebuild assertions, multi-agent
coordination, and user trust.

Recommended audit fields:

```python
class RecoveryAuditEvent(BaseModel):
    event_id: str
    timestamp: str
    actor: str
    repo_root: str
    repo_id: str | None
    profile: str | None
    action_code: str
    operation_id: str | None
    idempotency_key: str | None
    safe_auto_run: bool
    requires_user_permission: bool
    permission_granted: bool | None
    started_at: str | None
    finished_at: str | None
    result: Literal["success", "failed", "skipped", "blocked"]
    reason_codes: list[str]
    lifecycle_counters: dict[str, int]
```

Audit entries, diagnostics, status responses, and smoke output must not expose
secrets. Redact:

- environment variable values;
- bearer/session/refresh tokens;
- API keys;
- messaging bot tokens;
- database URLs with credentials;
- private keys and raw service configs.

It is acceptable to show variable names, relative paths, stable reason codes,
counts, hashes, and argv arrays that do not include secret values.

## 10) Agent Helper: `repo_semantic_ensure_ready.py`

Add an explicit agent helper script:

```powershell
py -3.12 scripts/agents/repo_semantic_ensure_ready.py --repo C:\path\to\repo
```

Recommended flags:

```text
--repo <path>
--profile <profile>
--mode diagnose|safe-recover|permissioned-lifecycle
--start-backend
--start-watcher
--diagnose-only
--json
--probe-query <text>
--require-graph
```

Default mode is `diagnose`:

- may check backend and `/readyz`;
- must not start backend containers/processes;
- must not start watcher or run startup reconcile;
- must not build/rebuild index or graph;
- must not switch repo, profile, runtime, backend, model, schema, or
  collections;
- JSON summary emitted.

`--mode safe-recover` is an explicit opt-in. In that mode the helper may start
existing known backend containers when `--start-backend` is passed and may start
watcher/startup reconcile for the already active matching repo/profile when
`--start-watcher` is allowed. It must still not build/rebuild index or graph.

`--diagnose-only` is an alias for default diagnose mode and disables all
mutations, including backend start, watcher start, and reconcile.

`--mode permissioned-lifecycle` is required before the helper may execute
build/rebuild/switch/drop/migration. The agent must still obtain explicit user
permission before running any permissioned lifecycle action.

Safe backend recovery may only start existing known containers/processes. It
must not run a compose operation that creates containers, builds images, resets
volumes, switches profiles, activates repos, changes role backend bindings, or
mutates collections.

### 10.1 Ensure-ready flow

```text
1. Locate repo-semantic deployment.
2. Check backend containers/processes.
3. If backend is stopped and --start-backend is allowed, start it.
4. Check `/healthz` for process liveness.
5. Wait for `/readyz` for HTTP transport and runtime bootstrap readiness.
6. Call `/statusz` or `index_status` for repo/search readiness.
7. Verify `search_available=true` before semantic probe.
8. Call index_status through direct HTTP fallback.
9. Verify repo_root and active_repo_root.
10. If mode is safe-recover and watcher.enabled and not watcher.running and
   --start-watcher is allowed, call start_watcher.
11. Re-check index_status.
12. Run a tiny repo_context_search probe.
13. Return machine-readable readiness result.
```

## 11) Transport Resilience

Codex registration must connect through a host-side stdio proxy by default.

Rationale:

- direct `docker exec` stdio dies when the container restarts;
- old Codex chats can hold a stale transport;
- host-side proxy can survive backend restarts and reconnect over HTTP;
- HTTP fallback gives agents an escape hatch even when direct MCP toolset is not
  registered in the chat.

Required behavior:

```text
Codex stdio command -> host-side proxy -> HTTP /mcp backend
```

Codex default registration must not use `docker exec` or a container-side stdio
proxy. `docker exec` stdio is allowed only as a manual/debug fallback because it
dies with container restart and causes stale-chat `Transport closed` failures.

The proxy should:

- keep stdio process stable;
- retry backend connection for transient failures;
- return clear JSON-RPC errors when backend is unavailable;
- never perform lifecycle actions by itself.

Acceptance for restart resilience:

```text
start one host stdio proxy process
call initialize, tools/list, index_status
restart repo-semantic-mcp container
without restarting the proxy, retry index_status until success
assert no host proxy process exit
assert downtime errors are JSON-RPC errors, not Transport closed
assert no lifecycle endpoint was invoked by the proxy
```

### 11.1 HTTP fallback tool contract

The fallback script must be a stable agent-facing path when direct MCP tool
registration is unavailable.

Required behavior:

- discover endpoint from explicit `--url`, environment, container metadata, then
  default `http://127.0.0.1:8011/mcp`;
- support `tools/list` and `tools/call`;
- support JSON and SSE responses if the backend transport uses either form;
- emit stable JSON:

```python
class ToolCallFallbackResult(BaseModel):
    ok: bool
    transport: Literal["http_fallback"]
    url: str
    tool_name: str | None
    result: object | None
    error: dict | None
    retryable: bool
    error_code: str | None
```

- use argv arrays and JSON input, never shell strings;
- work from PowerShell, cmd, bash, and WSL when Python is available;
- return stable error codes for backend down, timeout, tool unavailable,
  permission required, invalid JSON, and repo mismatch.

### 11.2 Host and deployment compatibility

Reliability behavior must work across the intended host environments:

- Windows host with PowerShell and Docker Desktop;
- bash/WSL shells when explicitly used;
- CPU profile;
- dogfood `gpu-pplx-v100-infinity` profile when V100/infinity prerequisites are
  present.

Requirements:

- examples must be safe for PowerShell and use argv/list form where possible;
- paths must normalize `C:\...`, `/mnt/c/...`, and container mount roots to the
  same logical repo root when explicitly configured;
- Docker context, container names, ports, and profile names must be configurable;
- V100 smoke must use longer cold-start timeouts and report `skipped` with a
  stable reason when hardware/model prerequisites are missing;
- no spec or script should hard-code one GPU UUID.

### 11.3 Direct MCP availability decision

Decision for v1: direct MCP tool availability is not a required in-Codex
detectable capability.

Codex chats may not expose a stable in-band API for inspecting MCP servers that
are not already present in the active toolset. Old chats can also retain stale
tool metadata after backend or container restarts. Therefore direct MCP
availability must not be part of the canonical readiness contract.

Canonical v1 readiness is determined through host-side HTTP fallback and
`repo_semantic_ensure_ready.py`. Direct MCP availability is reported only as a
best-effort tri-state:

```python
direct_mcp_available: bool | None
```

Semantics:

- `true`: a direct MCP tool call succeeded in the active Codex chat;
- `false`: an external smoke/harness explicitly probed the direct path and
  proved it unavailable;
- `None`: the agent cannot determine direct MCP availability from the active
  Codex context.

Agents must treat `direct_mcp_available=None` as normal, not degraded. If direct
MCP is absent or fails with transport/tool-registration errors, agents should use
HTTP fallback rather than asking the user to restart Codex. External smoke tests
remain responsible for validating host-side stdio proxy restart resilience and
direct-unavailable fallback behavior.

## 12) Graph Freshness and Degraded Mode

Graph freshness must be query-aware when possible.

Graph expansion should be blocked for:

- graph missing;
- graph incompatible;
- graph build in progress;
- graph error;
- built commit differs from current commit and affected paths are unknown;
- stale paths overlap seed paths or expanded paths;
- graph contract mismatch that changes node/edge semantics.

Graph expansion may be allowed in degraded mode for:

- source index count mismatch after incremental watcher update;
- optional extractor warnings;
- sparse stats drift;
- global graph stale with zero invalidated paths and complete path freshness
  coverage.

Graph degraded mode is allowed only when path freshness coverage is complete.
Graph expansion must not use seed, edge, evidence, or candidate paths whose
manifest state is `stale`, `deleted`, `error`, or `unknown`. If invalidated paths
are unknown, graph expansion is blocked with warning code
`graph_invalidated_paths_unknown`.

`repo_context_search` must expose:

```python
graph_diagnostics.status_state
graph_diagnostics.expansion_allowed
graph_diagnostics.used
graph_diagnostics.warning_codes
graph_diagnostics.degraded
graph_diagnostics.seed_path_states
graph_diagnostics.expanded_path_states
```

If graph is used in degraded mode, result evidence paths remain valid only as
retrieval hints. Exact verification before editing remains recommended.

### 12.1 Graph build permission policy

Decision for v1: `build_graph` and `rebuild_graph` are always
permission-required lifecycle actions.

There is no small-repo safe auto-run exception in v1. Repository size, estimated
duration, file count, or expected graph size may affect only `estimated_cost`,
diagnostics, and the permission prompt wording. They must not set
`safe_auto_run=true`.

When graph is missing, stale, incompatible, or errored:

- `index_status`, `graph_status`, `repo_context_search`, legacy search tools,
  and `ensure_ready` safe mode must not call `build_graph` or `rebuild_graph`;
- dense+sparse search remains available when the index itself is usable;
- graph expansion is skipped unless degraded-mode policy permits use of an
  existing graph artifact;
- `repo_context_search(graph_mode=expand)` returns graph diagnostics plus a
  permission-required recommended action;
- `ensure_ready --require-graph` returns `readiness="needs_user_permission"`
  when graph is required but cannot be used without building/rebuilding.

Recommended actions for graph lifecycle must use:

```text
safe_auto_run=false
requires_user_permission=true
destructive=false for build_graph when no graph artifact exists
destructive=true for rebuild_graph or build_graph(force_rebuild=true)
```

The permission prompt must include exact repo root, action (`build_graph` or
`rebuild_graph`), stable reason codes such as `graph_missing`, `graph_stale`,
`graph_incompatible`, or `graph_error`, why degraded/search-only mode is
insufficient for the current request, and estimated cost.

Dogfood profiles may prebuild graph through an explicit lifecycle step or a
human-approved `permissioned-lifecycle` helper invocation. They must not rely on
safe recovery, search, status, or smoke tests to build graph implicitly.

## 13) Exact Verification Policy

Exact identifiers, env vars, route names, SQL names, error strings, file paths,
and config keys still require local exact verification before editing.

This is not a failure of semantic search. It is the correct authority boundary:

```text
semantic/graph search finds context
local rg verifies exact working-tree state
file reads confirm edit targets
```

Recommended `repo_context_search` behavior:

- detect exact anchors;
- return `verification.required=true`;
- include `run_local_rg` recommended actions;
- use argv arrays, not shell strings.

## 14) E2E Reliability Harness

Add a dogfood smoke test that can run against a real target repo.

Suggested command:

```powershell
py -3.12 scripts/agents/repo_semantic_reliability_smoke.py --repo C:\path\to\large-private-repo --json
```

Test scenarios:

1. Backend is running and ready.
2. `index_status` works through HTTP fallback.
3. Active repo root matches target.
4. Search is available.
5. Watcher can be started explicitly.
6. Startup reconcile reports bounded work.
7. A probe file change is picked up without full rebuild.
8. `repo_context_search(graph_mode=expand)` returns `graph_used=true` when
   expansion is allowed.
9. Container restart does not permanently break host-side stdio proxy.
10. Direct MCP unavailable path still succeeds through HTTP fallback.
11. Read-only tools never start watcher, rebuild index/graph, activate repo, or
    switch backend/runtime.
12. Permission-required actions are returned as actions, not executed.

The smoke must not:

- run rebuild by default;
- mutate production code files;
- switch backend;
- switch repo;
- require secrets;
- print secret values in logs, JSON output, or failure messages.

Probe mutations may touch only an explicit scratch path under the target repo,
for example `.repo-semantic-smoke/`, or a temporary repo copy. The smoke must
clean up after itself and verify pre/post git status. The JSON result must
include per-scenario results, stable failure codes, lifecycle operation counters,
exit code semantics, and audit event ids for any safe recovery actions it ran.

The smoke matrix should include:

- a CPU profile when available;
- the dogfood `gpu-pplx-v100-infinity` profile when hardware/model prerequisites
  are present.

Missing V100 prerequisites should produce a skipped scenario with a stable
reason code, not a failure and not an automatic profile switch.

Rebuild, branch-switch, and destructive restart matrix tests must use a small
fixture repository or a temporary repo copy by default. The large private
dogfood repo is useful for realistic readiness/search checks, but it is too
large for routine rebuild reproduction: a V100 full index build can take around
ten minutes. Reliability tests should therefore separate:

- large-repo no-rebuild dogfood checks against the private dogfood repo;
- small-repo lifecycle/rebuild reproduction where full rebuilds are cheap and
  isolated;
- explicit human-approved large-repo rebuild checks only when the target issue
  cannot be reproduced on the fixture.

### 14.1 Testability and safety acceptance

All reliability behavior must be covered by executable tests with explicit
negative assertions. Passing tests must prove both the desired output and the
absence of forbidden lifecycle side effects.

Read-only tools (`index_status`, `graph_status`, `repo_context_search`, and
legacy search tools) must be tested with lifecycle spies. For each call, tests
must assert:

```text
build_index_calls == 0
rebuild_index_calls == 0
build_graph_calls == 0
rebuild_graph_calls == 0
activate_repo_calls == 0
switch_backend_calls == 0
switch_runtime_calls == 0
drop_collection_calls == 0
start_watcher_calls == 0, except explicit start_watcher
```

Every `RecommendedAction.code` must have a table-driven permission contract
test. Safe actions must use:

```text
safe_auto_run=true
requires_user_permission=false
destructive=false
expensive=false
```

Permissioned lifecycle actions must use:

```text
safe_auto_run=false
requires_user_permission=true
```

`drop_collections`, schema migration, rebuilds, backend/runtime switches, and
repo activation must never be returned as safe auto-run actions.

Any test or smoke scenario that says "without rebuild" must assert an operation
audit or test-double counter proving that no full index rebuild, graph rebuild,
collection drop, backend switch, runtime switch, or repo switch occurred.

Audit/redaction tests must assert that recovery output does not include known
secret fixture values while preserving useful variable names and reason codes.

### 14.2 Required negative cases

Add tests for:

- repo root mismatch;
- profile mismatch;
- active repo mismatch;
- backend mismatch;
- symlinked or differently cased repo paths;
- `--diagnose-only`;
- stopped watcher with `--start-watcher` absent;
- stopped watcher with safe bounds exceeded;
- permission-required next actions;
- partial startup reconcile failure;
- repeated `start_watcher`;
- file delete/recreate during reconcile;
- graph degraded with stale seed path overlap;
- transport restart with the same host stdio proxy process.
- stale lifecycle lease recovery after owner crash;
- duplicate safe recovery calls with the same idempotency key;
- secret redaction in status, audit, ensure-ready, and smoke outputs.

## 18) Resolved Decisions

1. Path manifest storage:
   use a dedicated per-index SQLite artifact. The registry DB stores only
   control-plane metadata, manifest pointer/summary, lease, and audit state.

2. Repeated reconcile failure threshold:
   emit `too_many_incremental_reconcile_errors` only after three consecutive
   bounded reconcile attempts fail for the same repo/profile/backend contract
   and index epoch with no successful progress.

3. Dogfood startup reconcile bounds:
   `max_reconcile_paths=250`, `max_deleted_paths=100`,
   `max_points_deleted=5000`, `max_duration_ms=180000`,
   `max_scan_paths=50000`. Bounds are configurable and echoed in status/reconcile
   responses.

4. Graph lifecycle:
   `build_graph` and `rebuild_graph` are always permission-required lifecycle
   actions in v1. Small repos may lower estimated cost, but never make graph
   build safe auto-run.

5. Direct MCP availability:
   not required as an in-Codex detectable v1 capability. Canonical readiness
   comes from HTTP fallback and `repo_semantic_ensure_ready.py`; direct MCP is a
   best-effort tri-state signal.
