# P4.B/P4.C: Lexical normalization, exact anchors, and payload filter pushdown

Status: Draft for review

## 1) Purpose

This specification defines the next implementation slice after P4.A.

P4.A established the structural hybrid route:

```text
dense raw query over Qdrant
  + sparse lexical query over Qdrant
  -> weighted RRF
```

P4.B/P4.C makes that route useful and predictable for agent work in large code
repositories:

- P4.B upgrades the sparse analyzer from a baseline tokenizer to a code-aware
  lexical normalization layer;
- P4.B adds deterministic exact-anchor detection for query-time diagnostics and
  required exact-heavy sparse weighting;
- P4.C moves supported filters into Qdrant query filters instead of relying on
  bounded post-filtering;
- unsupported glob filters remain client-side and explicitly best-effort.

The goal is still retrieval substrate quality, not an agent planner. The MCP
does not decide how to edit code, does not run shell `rg`, and does not generate
final answers.

Relevant P6 direction:

```text
Dense text remains raw.
Sparse text uses code-aware lexical normalization.
Exact anchors should be preserved.
Qdrant payload filters should be used where possible.
Local rg remains the authority for exact verification.
```

## 3) Current state after P4.A

Current implementation already has:

- Qdrant named dense and sparse vectors;
- deterministic sparse manifest persistence;
- weighted RRF;
- legacy dense-only compatibility;
- legacy local BM25 fallback for old indexes;
- payload fields and indexes for common filter fields;
- warning `qdrant_filter_post_filter_best_effort` when filters are active.

Current remaining limitations:

- `SearchFilters` are applied in Python after bounded dense/sparse retrieval;
- sparse query filtering can under-recall narrow `language`, `file_extension`,
  `chunk_type`, `domain_tags`, and `path_prefix` queries;
- analyzer behavior is not yet specified as the full P4.B code-search contract;
- exact anchors are preserved opportunistically by the analyzer but not exposed
  as first-class diagnostics;
- hybrid branch weights do not yet react to exact-anchor-heavy queries;
- search responses do not give a machine-readable exact verification hint.

## 4) Non-goals

Do not implement in P4.B/P4.C:

- `repo_context_search`;
- graph storage or graph expansion;
- `indexed_exact_search`;
- shell-backed `rg` inside MCP;
- LLM query planning, PRF, HyDE, or query rewriting;
- rerank or ColBERT;
- tree-sitter extraction;
- SQL lineage or framework route extraction;
- final-answer generation.

This slice may return safe `rg` argument hints as data, but it must not execute
them and must not return shell command strings.

## 5) Compatibility rules

P3 and P4.A compatibility remain active:

- legacy list-shaped tools keep returning list-shaped results;
- `search_v2` remains the envelope for response-level diagnostics;
- lifecycle operations do not run implicitly from status or search;
- old dense-only semantic search remains usable where possible;
- sparse contract mismatch does not block dense semantic search;
- exact verification remains host/local `rg` when the coding agent has
  filesystem access.

P4.B changes sparse analyzer behavior. Therefore:

- bump `LEXICAL_ANALYZER_VERSION` from the P4.A value to a new stable value,
  for example `code_lexical_v2`;
- update the sparse contract hash because analyzer output changes sparse vector
  vocabulary and document weights;
- do not necessarily bump `SEMANTIC_MCP_INDEX_SCHEMA_VERSION` unless Qdrant
  payload/vector schema changes require it;
- old sparse manifests become sparse-incompatible and should trigger dense-only
  search plus `explicit_sparse_rebuild_recommended`;
- analyzer mismatch must use the stable code
  `sparse_analyzer_version_mismatch` in status/retrieval diagnostics;
- a full explicit rebuild creates a fresh sparse manifest and sparse vectors;
- incremental reindex must not try to mix analyzer-v1 sparse vectors into an
  analyzer-v2 sparse manifest.

## 6) Target behavior

### 6.1 Query path

Hybrid search after this slice:

```text
query
  -> validate caps
  -> build normalized SearchFilters
  -> build FilterPlan
       pushdown_filter for Qdrant-compatible filters
       post_filter for glob/client-only filters
       diagnostics for best-effort parts
  -> detect exact anchors
  -> dense branch over raw query with pushdown_filter
  -> sparse branch over code-normalized query with pushdown_filter
  -> client-side post_filter only where needed
  -> weighted RRF
  -> shape snippets, line matches, matched terms, diagnostics, warnings
```

Dense query text stays raw. Only the sparse branch and exact-anchor analysis use
lexical normalization.

### 6.2 Index path

Full rebuild after this slice:

```text
chunk files
  -> write payload fields needed by filters
  -> analyze sparse document text with code_lexical_v2
  -> build sparse manifest
  -> upsert dense+sparse vectors and payload fields
  -> create payload indexes best-effort
```

Required payload fields:

```text
scope
relative_path
file_extension
language
chunk_type
domain_tags
is_generated
content_hash
path_segments
path_prefixes
```

P4.A already writes most of these. P4.B/P4.C should verify they are populated
consistently for every new point.

## 7) Code-aware lexical normalization

### 7.1 Analyzer contract

The analyzer must be deterministic, versioned, and shared by:

- sparse document vector encoding;
- sparse query vector encoding;
- matched-term extraction where cheap;
- exact-anchor detection where appropriate.

Token representation remains:

```python
class SparseToken:
    surface: str
    canonical: str
    token_type: str
```

Rules:

- `surface` preserves the observed or generated human-facing token;
- `canonical` is the lower-case vocabulary key;
- `token_type` explains why the token exists;
- dense input must not use these normalized tokens;
- output order is by source-span start, then token priority for that source;
- duplicate `(surface, canonical, token_type)` tuples are removed while
  preserving first occurrence order.

BM25 sparse term-frequency rules:

- for each observed source token/span, generated canonical terms are deduped
  before contributing to sparse term frequency;
- exact and normalized duplicates from the same source span count once;
- the same canonical term from separate occurrences in the document increments
  term frequency;
- document length is the count of emitted canonical terms after per-source-span
  dedupe;
- query encoding follows the same per-source-span dedupe rule.

### 7.2 Token families

The analyzer must preserve exact anchors and add normalized expansions for:

```text
snake_case
kebab-case
camelCase
PascalCase
dotted.names
slash/path/fragments
URL and route paths
SQL identifiers
env vars
CLI flags
quoted literals
error strings
file names and extensions
```

Expected token types:

```text
exact
normalized
part
case_part
dotted_part
path
path_segment
route
route_part
env_var
cli_flag
quoted_literal
error_literal
sql_identifier
file_extension
```

The implementation does not need a perfect language parser. It must be
deterministic, explainable, and covered by golden tests.

### 7.4 Stopwords and short tokens

Do not apply aggressive natural-language stopword removal in v1. Code search
often needs short tokens:

```text
id
db
ip
v1
io
go
```

The analyzer may drop single-character punctuation-only tokens, but it must not
drop alphanumeric 2-character code tokens by default.

### 7.5 Surface preservation

When a query contains exact-looking anchors, diagnostics should expose the
original surfaces even though sparse vocabulary uses canonical terms. This is
important for safe exact-search guidance.

## 8) Exact-anchor detection

### 8.1 Purpose

Exact-anchor detection is not exact search. It is query analysis that helps an
agent decide when local verification is needed and helps hybrid retrieval bias
toward the sparse branch.

Examples:

```text
DATABASE_URL
/api/v1/users/{id}
UserRepository.findByEmail
create_users_table
public.users
"permission denied"
--target-repo-path
services/user/api/connect_flow.py
```

### 8.2 Anchor model

Add an additive diagnostic model:

```python
class ExactAnchorCandidate(BaseModel):
    surface: str
    canonical: str
    start: int
    end: int
    anchor_type: Literal[
        "env_var",
        "route",
        "path",
        "file_name",
        "symbol",
        "sql_identifier",
        "cli_flag",
        "quoted_literal",
        "error_literal",
        "config_key",
    ]
    confidence: Literal["high", "medium", "low"]
    requires_verification: bool = True

class ExactAnchorAnalysis(BaseModel):
    anchors: list[ExactAnchorCandidate] = []
    exact_anchor_heavy: bool = False
    exact_fallback_recommended: bool = False
    local_rg_authority: Literal["local_rg"] = "local_rg"
    cwd_hint: Literal["repo_root"] = "repo_root"
    argv_hints: list[list[str]] = []
```

Add to `SearchDiagnostics`:

```python
exact_anchor_analysis: ExactAnchorAnalysis | None = None
```

Anchor ordering and caps:

- sort by `start`, then anchor-type priority, then longer surface first;
- priority is `env_var`, `route`, `path`, `file_name`, `cli_flag`,
  `quoted_literal`, `error_literal`, `sql_identifier`, `symbol`, `config_key`;
- dedupe by `(surface, canonical, anchor_type)`;
- return at most 20 anchors;
- return at most 5 `argv_hints`.

Minimum anchor golden cases:

```python
"DATABASE_URL" ->
  anchor_type="env_var", confidence="high", exact_fallback_recommended=True

"/api/v1/users/{id}" ->
  anchor_type="route", confidence="high", exact_fallback_recommended=True

"UserRepository.findByEmail" ->
  anchor_type="symbol", confidence="medium", exact_fallback_recommended=True

"services/user/api/connect_flow.py" ->
  anchor_type="path", confidence="high", exact_fallback_recommended=True

"--target-repo-path" ->
  anchor_type="cli_flag", confidence="high", exact_fallback_recommended=True

"\"permission denied\"" ->
  anchor_type="quoted_literal", confidence="high", exact_fallback_recommended=True
```

`exact_anchor_heavy=true` when:

```text
there is at least one high-confidence anchor
and non-anchor query terms outside anchor spans are <= 4
```

This predicate is intentionally simple and deterministic. It can be revised only
with tests.

Do not put raw shell command strings in diagnostics. `argv_hints` must be an
argument array, interpreted with `cwd_hint="repo_root"`. Use `-e` before the
pattern so anchors beginning with `-` cannot be parsed as `rg` options. Example:

```json
["rg", "--fixed-strings", "--line-number", "--max-count", "20", "-e", "DATABASE_URL", "."]
```

The hint producer should mirror MCP exclude policy when practical by adding
bounded `--glob` exclusions. If exclude mirroring is omitted, diagnostics must
not claim the hint exactly matches index scope.

### 8.3 Warning code

When exact anchors are detected, `search_v2` should add:

```text
exact_anchor_verify_with_local_rg
```

Severity:

```text
warning if query is exact-anchor-heavy or index freshness is stale
info otherwise
```

Legacy list-shaped search tools should not emit sentinel rows or fake warnings.

### 8.4 Anchor-heavy weighting

P4.B must adjust RRF branch weights for hybrid search when
`exact_anchor_analysis.exact_anchor_heavy=true`:

```text
default:
  dense: 1.0
  sparse: 1.2

exact-anchor-heavy:
  dense: 0.8
  sparse: 1.4

conceptual query with no exact anchors:
  dense: 1.0
  sparse: 1.2
```

Do not use raw sparse/dense score blending. The weight change applies only to
RRF branch contribution.

### 8.5 Exact verification policy

Exact-anchor detection should recommend verification, not claim verification.

Result text:

```text
Semantic/hybrid results are candidates. Verify exact anchors against the working
tree before editing.
```

The MCP must not run `rg`, must not mutate lifecycle state, and must not mark
results as exact unless a future indexed exact tool actually performs exact
matching.

## 9) Filter plan and Qdrant pushdown

### 9.1 Filter semantics

Existing `SearchFilters` semantics remain:

- filter families are ANDed;
- values within one family are ORed;
- `exclude_paths` always wins;
- `path_prefix="src"` matches `src` and `src/...`, not `src2/...`;
- include/exclude paths are repo-relative POSIX-style glob-like patterns;
- absolute paths, drive-qualified paths, empty segments, and `..` segments are
  rejected.

### 9.2 Pushdown fields

Build a `FilterPlan`:

```python
class FilterPlan(BaseModel):
    qdrant_filter: models.Filter | None = None
    pushed_families: list[str] = []
    post_filter_families: list[str] = []
    required_payload_fields: list[str] = []
    missing_payload_fields: list[str] = []
    best_effort: bool = False
    warning_codes: list[str] = []
```

Qdrant filter shape must use `qdrant_client.models` explicitly:

```python
models.Filter(
    must=[
        models.FieldCondition(
            key="path_prefixes",
            match=models.MatchValue(value=filters.path_prefix),
        ),
        models.FieldCondition(
            key="file_extension",
            match=models.MatchAny(any=filters.file_extensions),
        ),
        models.FieldCondition(
            key="language",
            match=models.MatchAny(any=filters.languages),
        ),
        models.FieldCondition(
            key="chunk_type",
            match=models.MatchAny(any=filters.chunk_types),
        ),
        models.FieldCondition(
            key="domain_tags",
            match=models.MatchAny(any=filters.domain_tags),
        ),
    ]
)
```

Include a condition only when the corresponding filter family is active.

Expected Qdrant array semantics:

```text
FieldCondition over an array payload matches when any array element satisfies
the condition.
```

Keep client-side:

```text
include_paths
exclude_paths
max_results_per_file
```

P4.C v1 does not push `include_paths`, even when a pattern has no glob syntax.
This keeps all include/exclude path semantics in one implementation until path
matching has a dedicated review. Do not push `exclude_paths` unless a later spec
proves Qdrant negation exactly matches current `fnmatchcase` glob behavior.

### 9.3 Payload capability detection

Filter pushdown is per collection, not global.

Legacy dense-only collections can lack P4.A derived payload fields such as:

```text
file_extension
path_prefixes
path_segments
```

Before applying a pushdown condition, build a per-scope payload capability
summary:

```python
class PayloadCapabilities(BaseModel):
    scope: Literal["code", "docs"]
    collection_name: str
    checked: bool
    available_fields: list[str] = []
    missing_fields: list[str] = []
```

Implementation may derive this from current schema/version or from a bounded
payload sample. It must not full-scroll the collection for status/search.

Rules:

- if required payload fields are present, push that filter family;
- if required payload fields are absent or unknown on a legacy collection, keep
  that family client-side;
- add `qdrant_filter_pushdown_partial`;
- if bounded post-filtering can under-recall, also add
  `qdrant_filter_post_filter_best_effort`.

### 9.4 Qdrant query contract

Extend Qdrant store methods:

```python
search(scope, query_vector, limit, query_filter=None)
search_sparse(scope, indices, values, limit, query_filter=None)
```

Both dense and sparse branches must receive the same Qdrant-compatible filter
plan.

Filtering must work for:

- named dense+sparse current collections;
- legacy unnamed dense-only read collections for semantic search where possible.

If a collection is legacy dense-only, sparse branch remains unavailable and
legacy fallback rules from P4.A still apply.

### 9.5 Diagnostics

Add to `SearchDiagnostics`:

```python
filter_pushdown_supported: bool = True
filter_pushed_families: list[str] = []
filter_post_families: list[str] = []
filter_best_effort: bool = False
filter_payload_capabilities: list[PayloadCapabilities] = []
```

Warnings:

```text
qdrant_filter_pushdown_used
qdrant_filter_post_filter_best_effort
qdrant_filter_pushdown_partial
```

Use `qdrant_filter_post_filter_best_effort` only when an active filter family
can still under-recall because it was applied after bounded retrieval.

After P4.C, simple pushed filters should not trigger that warning by themselves.

### 9.6 Candidate limits

With pushdown filters, branch candidate limits remain:

```text
dense_limit = min(max_dense_cap, max(50, top_k * 8))
sparse_limit = min(max_sparse_cap, max(100, top_k * 12))
```

Post-filtered glob families still use bounded expansion:

```text
start with the branch candidate limit;
if post-filtering plus max_results_per_file under-returns, double the limit;
stop at the existing dense/sparse caps;
if still under-returning, return available results and warn.
```

`max_results_per_file` is still applied after scoring and dedupe. It can cause
under-returning by design and should not be described as Qdrant filter failure.

## 10) Result shape and matched terms

`SearchResult` compatibility remains:

- `score` remains final score;
- `final_score` remains alias/extension;
- `dense_score` and `lexical_score` remain raw branch scores;
- `match_type` remains one of `semantic`, `hybrid`, `lexical`, `exact`.

P4.B should improve `matched_terms` for sparse/exact-like queries:

- prefer exact surfaces when the exact surface appears in chunk text;
- include canonical terms only when exact surface is unavailable;
- cap by existing `MAX_EXPLANATIONS`;
- keep `line_matches` bounded by existing caps.

Do not set `match_type="exact"` in P4.B/P4.C. Exact remains reserved for a
future indexed exact tool.

## 11) Status contract

`index_status.v2.retrieval` should remain additive from P4.A.

Add or verify:

```text
expected_lexical_analyzer_version
stored_lexical_analyzer_version
expected_sparse_encoder_kind
stored_sparse_encoder_kind
sparse_contract_compatible
sparse_unavailable_codes
filter_pushdown_supported
payload_filter_pushdown_supported
payload_index_status
```

Stable sparse unavailable codes:

```text
sparse_analyzer_version_mismatch
sparse_encoder_kind_mismatch
sparse_contract_mismatch
sparse_manifest_missing
sparse_vector_missing
legacy_dense_only_collection
```

Analyzer mismatch must be distinguishable from missing sparse state. Agents need
to know whether the fix is a normal explicit rebuild or a deeper runtime/schema
problem.

Payload index status can be compact:

```python
class PayloadIndexStatus(BaseModel):
    scope: Literal["code", "docs"]
    collection_name: str
    field_name: str
    expected: bool = True
    present: bool | None = None
    warning_code: str | None = None
```

Owner:

```text
RetrievalScopeStatus.payload_indexes: list[PayloadIndexStatus]
RetrievalContractStatus.payload_filter_pushdown_supported: bool
```

If reliable payload-index introspection is expensive or awkward, status may use:

```text
present = None
warning_code = "payload_index_presence_not_checked"
```

Search may still use Qdrant filters even when status cannot prove payload index
presence. Index presence affects performance, not filter correctness.

## 12) Lifecycle and freshness

No lifecycle operation runs implicitly.

Analyzer upgrade behavior:

```text
current dense vectors compatible + sparse analyzer mismatch:
  dense semantic search allowed
  sparse branch unavailable
  legacy BM25 fallback allowed for compatibility window
  explicit_sparse_rebuild_recommended warning

full build_index(force_rebuild=true):
  rebuilds sparse manifest/vector data with new analyzer
```

Implementation compatibility note:

```text
P4.B/C payload-filter fields are treated as a new payload contract.
The implementation may bump the physical index schema version so old
collections remain dense-readable but are not treated as pushdown-safe.
This prevents a mixed collection where one newly reindexed point has
path_prefixes/file_extension payloads and older points do not.
```

Incremental reindex behavior:

- if sparse manifest is compatible and current collection has sparse vectors,
  reindex touched chunks using the current analyzer and mark sparse stats stale;
- if sparse manifest is incompatible, do not produce partial mixed sparse state;
- if current collection is legacy or dense-only, do not upsert sparse vectors;
- status/search should recommend explicit rebuild for sparse enablement.

## 13) Tests

Add or update unit tests for:

### Analyzer

- golden examples from section 7.3;
- exact surface preservation;
- canonical vocabulary stability;
- no aggressive stopword/short-token removal;
- deterministic output order.

### Exact anchors

- env var detection;
- route detection;
- dotted symbol detection;
- path/file detection;
- quoted literal detection;
- argv hints are arrays, not shell strings, and use `-e` before the pattern;
- anchor ordering, dedupe, caps, confidence, and `exact_anchor_heavy`;
- warning `exact_anchor_verify_with_local_rg` appears in `search_v2`.

### Qdrant filters

- Qdrant store receives `query_filter` for dense and sparse branches;
- `path_prefix="src"` pushes `path_prefixes=src` and does not match `src2`;
- `file_extensions`, `languages`, `chunk_types`, and `domain_tags` push down;
- include/exclude glob filters remain post-filter and report best-effort;
- legacy collections missing derived payload fields fall back to client-side
  filters with `qdrant_filter_pushdown_partial`;
- pushed-only filters do not emit post-filter best-effort warning.

### Search behavior

- dense raw query is unchanged;
- sparse query uses analyzer output;
- exact-heavy query uses exact-heavy RRF weights;
- sparse manifest mismatch degrades to dense/fallback without lifecycle mutation;
- legacy list-shaped search still returns list rows.

### Status

- retrieval status reports analyzer version;
- sparse analyzer mismatch recommends explicit rebuild;
- payload filter pushdown support is visible;
- payload index status is present or explicitly unknown.

## 14) Acceptance criteria

P4.B/P4.C is complete when:

1. Sparse analyzer has a documented and tested `code_lexical_v2` contract.
2. Exact anchors are detected and exposed in `search_v2` diagnostics.
3. Exact-anchor queries recommend local `rg` verification without executing it.
4. Dense query text remains raw.
5. Sparse query text uses code-aware lexical normalization.
6. Qdrant-compatible filters are pushed into both dense and sparse searches.
7. Glob-only filters remain client-side with explicit best-effort diagnostics.
8. Pushed-only filters no longer claim post-filter best-effort.
9. Exact-anchor-heavy hybrid queries use the exact-heavy RRF weights from
   section 8.4.
10. Sparse analyzer mismatch does not block dense semantic search.
11. No search/status path runs lifecycle operations.
12. Legacy list-shaped tool compatibility is preserved.
13. Tests cover analyzer, anchors, pushdown, status, and compatibility.

## 15) Resolved implementation decisions

1. Exact-heavy RRF weighting is in scope for P4.B/P4.C and is required.
2. `include_paths` stays client-side in P4.C v1, even for non-glob values.
3. Payload index presence is reported per `RetrievalScopeStatus`; `present=None`
   is acceptable when introspection is not reliable.
4. `ExactAnchorAnalysis.argv_hints` lives in `SearchDiagnostics` for this slice.
   `SearchResponse.recommended_next_actions` remains deferred to
   `repo_context_search`.
5. `argv_hints` use argument arrays, `cwd_hint="repo_root"`, and `-e` before the
   pattern.
